# Deploying RecruitmentOS

> **Deployment is not authorized.** Release needs the owner's decision; independent review (DEC-02/DEC-03) and Production verification are still open. Hosted sign-in opens only when every readiness condition in [authentication.md](authentication.md#hosted-sign-in-readiness) holds, and Blob CV storage switches on only after the owner's steps in [§5](#5-cv-storage). Hosted database startup no longer has a blanket block: it fails closed on the precise checks in [§2](#2-neon-postgresql). In the owner's run on the Neon Preview database, the split runtime role template [postgres-split-runtime-roles.sql](../infrastructure/postgres-split-runtime-roles.sql) is applied, `scripts/db-role-evidence.ts` passes with zero drift, and `npm run test:live-roles` passes 27/27 through the transaction-mode pooler and 27/27 direct, with all fixtures removed. Do not run the template against Production before it is reviewed and approved, switch Blob on in Production before Preview passes the checks in §5 and §6, import real candidate data, or remove these gates. Follow [identity-boundary-plan.md](identity-boundary-plan.md) and [neon-database-runbook.md](neon-database-runbook.md) for the outstanding implementation and verification work.

The project is prepared for Vercel. No Neon database, Blob store, mail account, OAuth client or Vercel project is created by cloning or building the repository. Deployment uses the services you configure below.

## 1. Separate environments

Use separate Neon branches/databases, private Blob stores, email settings and auth secrets for production and previews. Do not attach preview deployments to production candidate data. Protect preview deployments in Vercel; a preview URL is not an access-control boundary. Use Node.js **24.x** and the Next.js framework preset. No static export is used: authentication, database operations and signed CV URLs require the server.

## 2. Neon PostgreSQL

Create a PostgreSQL database in the intended region. Keep its owner connection only in the administrator's local `MIGRATION_DATABASE_URL`; do not add that owner connection to the Vercel application's runtime environment.

After the deployment blockers are resolved and the exact target, migration state and role plan have been verified, follow the [Neon database runbook](neon-database-runbook.md) using the target database's direct owner connection. Do not run migrations yet. Migrations are transactional and tracked in `public.recruitment_migrations`. They include tenant composite foreign keys, uniqueness rules, append-only audit protection, last-owner protection and row-level security. Back up the database before future schema changes. Changes are forward migrations; do not edit migrations already applied to a deployed database.

The legacy shared-role fixture has been removed. [postgres-split-runtime-roles.sql](../infrastructure/postgres-split-runtime-roles.sql) creates the separately restricted `recruitmentos_data` and `recruitmentos_identity` roles with exact object-by-object grants and closes the database and the `public` schema to PUBLIC. `scripts/db-role-evidence.ts` reports their effective privileges read-only and exits 1 on drift from the template's grants; [neon-database-runbook.md](neon-database-runbook.md) lists exactly which classes it checks. Both are verified on PGlite, on a throwaway local PostgreSQL 18 cluster and, in the owner's run, on the Neon Preview database: there the template is applied, the evidence script passes with zero drift, and `npm run test:live-roles` passes 27/27 through the transaction-mode pooler and 27/27 direct, with all fixtures removed. INSERT INTO app.workspace_admins (workspace_id, user_id, level, areas, plan_access, granted_by, granted_at)
```sql
SELECT t.workspace_id, u.id, 'owner', '{}', false, NULL, now()
FROM auth."user" u
JOIN auth.member m ON m.user_id = u.id
JOIN app.workspace_teams t ON t.team_id = m.organization_id
WHERE lower(u.email) = lower('<owner email>')
LIMIT 1
ON CONFLICT (workspace_id, user_id)

```

Never expose these through `NEXT_PUBLIC_*`. The deployed `TENANT_CONTEXT_SIGNING_KEY` must be the key `npm run db:migrate` installed in that database; otherwise every team transaction is denied (403 `tenant_context_denied`). `ALLOW_LOCAL_DB=true`, `DEV_MAIL_MODE=console`, `DATABASE_MODE=pglite` and any `DEV_SEED_PASSWORD` make hosted startup refuse; do not configure them in a deployed environment. The build succeeds without credentials; private routes show setup-required until runtime services are configured. A successful build does not prove cloud credentials or provider permissions are correct.

**Function region.** `vercel.json` sets `"regions": ["fra1"]`, so the application's functions run in Frankfurt (`fra1`), next to Neon (`aws-eu-central-1`) and the Blob store (`fra1`). Before this, functions ran in Vercel's default `iad1` (US East) and every database statement crossed the Atlantic. The setting takes effect on the next deployment, which the owner runs; nothing in the repository deploys it.

Import `omarals95/RecruitmentOS` into Vercel and select the reviewed implementation branch. Run `npm ci` for install and `npm run build` for build. The repository includes Vercel's Node function duration configuration. Use a stable canonical production domain matching `BETTER_AUTH_URL`. Preview origins need their own corresponding isolated configuration; do not add arbitrary origins to auth.

## 4. Email and sign-in

Verify a sending domain with Resend and set `EMAIL_FROM`. Apply the initial-admin migration, then use `/create-admin` with the configured bootstrap email and setup token. See [authentication.md](authentication.md) for recovery and upgrade behavior.

For Google, configure the OAuth client and callback `https://YOUR-DOMAIN/api/auth/callback/google`, then set `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`. For Microsoft, configure `https://YOUR-DOMAIN/api/auth/callback/microsoft`, set `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET` and optionally `MICROSOFT_TENANT_ID`. Keep callback domains exact. Provider email is not permission to join an existing team, and automatic email-based account linking is disabled. Test each provider's email verification and invitation flow with your tenant before enabling it for recruiters.

## 5. CV storage

Hosted CVs are stored in private Vercel Blob only (DEC-01, resolved by the owner on 7 November 2026). The S3 path in [s3-setup.md](s3-setup.md) is legacy and dormant. The owner switches Blob on per environment, Preview first; none of these steps has been done yet:

1. Create a separate **private** Blob store for Preview and for Production, and connect each to the project for its own environment only. Never share a store between environments.
2. Set `BLOB_STORE_ID` to that environment's store id and set `CV_STORAGE_PROVIDER=blob` before the build. On Vercel an unset, empty or blank provider is refused on the server with 503 `STORAGE_SETUP_REQUIRED` (reason `not_configured`, job 038), matching the build-time CSP, which then allows no upload host. Remove `BLOB_READ_WRITE_TOKEN` from Preview and Production, including the value Vercel adds when a store is connected: the server then refuses Blob (503 `STORAGE_SETUP_REQUIRED`, reason `blob_token_present`). Hosted Blob uses only the request's Vercel OIDC token with the store named explicitly, never a static token or the SDK's fallback. Redeploy after changing the provider, because the CSP is fixed at build time.
3. Apply migrations `0018_blob_storage_enablement.sql` and `0019_blob_upload_abuse_controls.sql` after `0017`, rerun the role template, then rerun `scripts/db-role-evidence.ts` and `npm run test:live-roles` (see [§2](#2-neon-postgresql)).
4. Review the store-wide budgets in `storage_ledger.budgets` (Preview 200,000,000 bytes / 500 files, Production 600,000,000 bytes / 2,000 files); the owner changes them only with the SQL in [neon-database-runbook.md](neon-database-runbook.md#change-the-store-wide-cv-storage-budgets). Team limits and the upload rate limit are off by default and set by owners and admins in Team & access. All of these are application limits, not hard provider or billing caps ([residual risk](blob-security-design.md#residual-risk)).
5. Rejected, expired and abandoned uploads are deleted only after their tickets expired. There is no scheduler: the next Blob reservation of a team frees a few charges, each completed or rejected Blob upload starts the full cleanup automatically, and an owner or admin can run it with `POST /api/v1/cvs/storage-reconciliation` ([api-examples.md](api-examples.md#clean-up-cv-storage)); repeat it while `complete` is false. Both share one 10-minute cooldown per team (429 `STORAGE_RECONCILIATION_COOLDOWN` with `Retry-After`).
6. After deploying, check on Preview that responses carry `Strict-Transport-Security: max-age=63072000; includeSubDomains` and `Cross-Origin-Opener-Policy: same-origin`, and that a live Claude and ChatGPT connector still completes OAuth sign-in with COOP in place.

## 7. Version and build number

Every page footer, Settings > About and the sign-in page show the build, for example `Version 1.0.0 (build 20261108.1430)`; About also shows the commit, environment and build time (job 039).

- **Version rule.** The semantic version in `package.json`: the major number per release (Release 1 is `1.0.0`, Release 2 is `2.0.0`), the minor number per Preview feature drop, the patch number for fixes. Change it in `package.json` and in the root entries of `package-lock.json` in the release commit.
- **Build number.** The build time in UTC as `YYYYMMDD.HHMM`, for example `20261108.1430`. `next.config.ts` reads it once per build (`src/lib/build-info.ts`); the build workers reuse that time through `APP_BUILT_AT`, so every page and route of one build shows the same number.
- **Commit.** The first 7 characters, in lower case, of the first valid source: `VERCEL_GIT_COMMIT_SHA` (7 to 40 hex characters), then the `commit` in `build-info.json` at the repository root, then `dev`. An unreadable or malformed `build-info.json`, or an invalid `commit` in it, is ignored with one build-log warning that names the file without its contents; the build continues with `dev`.
- **Git-integrated Vercel deployments** need nothing extra: Vercel sets `VERCEL_GIT_COMMIT_SHA` for the build.
- **The owner's CLI deploys** upload a git archive without `.git`, so the deploy script writes the commit itself: it runs `git rev-parse HEAD` in the checkout, extracts the archive, writes `{"commit":"<full sha>"}` to `build-info.json` in the root of the extracted archive and then runs `vercel deploy` there. `build-info.json` is listed in `.gitignore` and never committed; `.vercelignore` does not exclude it.
- **Environment.** `Production` or `Preview` from `VERCEL=1` with `VERCEL_ENV` at build time, otherwise `Local development`.
- `NEXT_PUBLIC_APP_*` are generated by the build from these sources and inlined into the server and browser code. Do not set them by hand. None of them is secret.
- **Checks.** `GET /api/version` needs no sign-in and returns only `{ "version", "build", "commit", "environment" }` with `Cache-Control: no-store`. Every `/api/*` response carries `X-App-Version` with the semantic version, for example `1.0.0`. The MCP `serverInfo.version` is the same version. After a deployment, compare `/api/version` with the commit you deployed.

## Operations

Enable Neon backup/restore appropriate to your retention policy, and keep each Blob store private and limited to its environment. The [recovery runbook](recovery-runbook.md) covers failed migrations, release rollback and restoring into an isolated database. Monitor application failures, provider costs, upload reservations and rate limits without logging CV contents, passwords, tokens or signed URLs. Define retention, deletion, offboarding and incident response before real use. CV format validation is not antivirus scanning; if malware scanning is required, add a private quarantine/scanning gate before making files ready. See [security.md](security.md) for implementation limits and authorised network flows.
