# Using RecruitmentOS

## Start your day

Sign in with your verified email/password, or a configured Google/Microsoft provider. Select your team in the sidebar. **Overview** shows actual candidate, vacancy and workflow counts, upcoming interviews, overdue tasks and recent recruitment activity. Overdue tasks exclude tasks in buckets marked **Counts as completed**. The **Recruitment tasks** count also excludes them; its caption reads "Tasks not in a completed bucket". The **Open vacancies** count includes only vacancies with status Open. Candidate counts describe people; CV counts describe uploaded ready files and can differ. Dark, light and system themes are available in the top bar.

Use the top-bar search (Ctrl/Cmd+K) to find candidates, vacancies, roles and tasks. Search can use a quoted phrase or exclude a word with `-word`. Your team determines which records you can access.

## Candidates and source records

Open **Candidates** to search/filter facts, skills, certifications, source-folder categories, education, experience and review status. Review status is one of two values: **Needs review** (the default for a new candidate) or **Reviewed**; the editor and the **Review status** filter on **Candidates** and **My shortlist** offer only these. **Source review** always shows the candidates that need review, so it has no review status filter. Older free-text values were mapped once: "Verified", "Reviewed", "Complete" or "Completed" (any case) became Reviewed and anything else Needs review; imported source text is kept unchanged in the original source fields. **All of these skills** and **All of these certifications** match candidates holding every listed value, ignoring upper and lower case and surrounding spaces: "react" finds candidates with "React". As you type, each of these inputs suggests the skills or certifications already recorded on your team's active candidates, most common first; a value that differs only in case from one you already chose is not added again. **Education contains** matches text in the degree name, major or university. **Minimum/Maximum stated experience (years)** match the CV-stated years only: a candidate without stated experience is never included in a range, and the filter bar says so. Folder categories reproduce the folders used during import; they do not independently assess job suitability. Missing facts remain missing. When filters leave nothing to show, the list says "No records match these filters" with a **Clear filters** button; **Source review** says "Nothing needs source review" when every candidate has been reviewed.

Open a candidate for education/contact details, source evidence, CVs, related applications and recruitment tasks. The **Interviews**, **Offers** and **Onboarding** tabs list those records from all of the candidate's applications; each interview and offer row also says which application it belongs to ("For {candidate} · {vacancy}"). These tabs have no Add button: add interviews, offers and onboarding from one of the candidate's applications. The **Tasks** tab lists the candidate's active tasks with priority and due date; **Add task** there starts a task already linked to the candidate. Use **Create hire task** to add a task linked to this candidate and, optionally, a vacancy. Use **Assign to vacancy** or the directory's multi-select vacancy action to create applications. Creating a task does not create an application or change a hiring stage. A linked record that was archived shows its name followed by "(archived)"; one you cannot open shows "Unavailable record".

The **My follow-up** area and shortlist are private to your account. Use **Discussion** for shared comments. Save forms explicitly. When a record changes elsewhere, a conflict keeps your draft so you can review the latest version before retrying.

Upload CV files from the candidate's profile after private storage is configured. Until storage is set up, the CV area and **Import CVs** explain that CV uploads are not set up yet and show no file picker; candidate details can still be added and edited. Files upload directly to private storage, then undergo format checks before a download is available. A file's source path is relative historical metadata. In the cloud, Open/Download uses a short-lived private link; it cannot open Windows File Explorer. Multiple CV references can belong to the same candidate.

**Import CVs** on **Candidates** adds several new candidates, each with its CV, once private storage is configured. It works wherever single CV upload works; until then the dialog only explains why import is not available. Before you choose files it states the limits: up to 200 files per import, 10 MiB each, one CV upload at a time in this browser, and import progress kept on the server for 24 hours while the selected files and drafts stay only in this browser. Choosing more than 200 files adds only the first ones and says how many were not added. The selected CVs are listed 25 at a time with **Previous** and **Next**; the list shows the page of the CV you review or the one being imported. AI extraction is not configured, so enter each candidate's details from the CV yourself, check for possible duplicates and confirm both review boxes; the server checks those confirmations again, and if the possible duplicates changed since your check it asks you to check again before importing. If an approved AI service is connected in a later release, the dialog will show what is sent and to whom, ask for your consent, and label every suggestion as unverified until you accept, reject or edit it. Import always creates a new candidate: it cannot attach a CV to an existing candidate, so attach a CV to an existing candidate from that candidate's profile. While an import runs, **Cancel import** stops it after the current request; candidates already created stay in your directory. Another CV upload in a different tab of the same browser must finish first; a browser without the needed locking support cannot upload CVs. If your session, permission or storage setup is lost, the import stops before the next CV and the remaining CVs stay "Not started". If your team's CV upload rate limit is reached, the import pauses before the next CV: wait a minute, then select **Import reviewed** again to continue with the remaining CVs. When an import ends, an **Import summary** lists every selected file under Imported; Candidate created, CV pending; Not imported; Failed; or Outcome unknown. Retry an unknown or pending item with its unchanged draft; this never creates a second candidate. If a CV was rejected or its upload expired after the candidate was created, **Retry import** uploads the same selected file again; to attach a different file, open the candidate and upload it from the profile. A create whose result is uncertain cannot be retried once 24 hours have passed since the import started. **Recent imports (kept for 24 hours)** lists your other imports from the last 24 hours, ten at a time with **Previous** and **Next** when there are more (a later page that empties as imports expire offers **Go to first page**), with each file's outcome (25 at a time per import when it has more) and a link to its candidate; for "CV pending" or "CV rejected" open the candidate to attach the CV. Selected files are not kept, so a recent import cannot be resumed there. After 24 hours an import's progress is gone: check the candidate directory before importing those CVs again.

Use **Source review** to work through incomplete/ambiguous extraction information. Review evidence before correcting facts. The application does not infer sex/gender, national service completion, nationality or residence from a name or photo.

**Export** saves every record matching the current filters as `RecruitmentOS-{list}-{date}-{time}.csv` (Asia/Dubai time). The server builds the file from one consistent read of the records, so the row count always matches the rows. The file starts with labels: the list (for example Candidates; My shortlist and Source review appear in the filters as "My shortlist only" and "Needs source review"), when it was exported (Asia/Dubai), the environment (Production, Preview or Local development), the filters used, the row count and a data-protection notice, then a blank line and the usual columns. An export of more than 100,000 records is refused; narrow the filters instead. Every export is recorded in **Activity** (record type **export**): who exported, when, which list, how many rows and which filters were used, but never the filter values or search text. If that record cannot be written, no file is produced. Exports contain personal data and need the same care as the source CVs; store and share them only as your team's data-protection rules allow.

## Roles, vacancies and applications

Create reusable **Job roles** with title, department, description, requirements and skills. Create a **vacancy**, optionally copying a role's details into the draft; only vacancies with status Open count as open. The **Vacancies** screen lists every vacancy, from draft to closed. Changes to a role do not silently rewrite existing vacancies. To bring later role edits into a vacancy created from a role, open the vacancy and select **Review changes from role**. It lists each role detail that now differs, with the vacancy's and the role's current values, all unticked. Tick the ones to copy and select **Apply selected changes**; nothing else changes. If the role was archived, its details can no longer be copied.

Use **Applications** to link a candidate and vacancy. Move the application through the pipeline explicitly. Without a vacancy filter the board shows the current page only. Choose a vacancy in the filters to see its whole pipeline: the board then loads every matching application of that vacancy, the column counts add up to the total, and the footer reads "{n} matching applications · board shows all of them". A vacancy with more than 1,000 matching applications is not shown as a board; use **Show as table** or narrow the filters. If the pipeline changes while it loads, the board says so; refresh to see every application. Dragging has a keyboard-accessible Move alternative. If someone else changed a card since the board loaded, your move is not applied: the board reloads the latest version and explains what happened, and **Move to … again** repeats your move on the latest version (or **Dismiss** leaves it). Application stage, vacancy status, task bucket, offer status and onboarding status are separate choices. Marking an offer accepted does not automatically mark an application hired, and changing a vacancy's status leaves its applications as they are.

## Recruitment tasks

Use **Tasks** for your team's workflow. Add and reorder buckets; choose their names and colours. A bucket is a task's status. Tick **Counts as completed** on a bucket whose tasks are finished: those tasks no longer count as overdue and give no reminders. New teams get a **Done** bucket with the box ticked. Existing teams' buckets named Done were ticked once by the upgrade; tick the box yourself on any other finishing bucket. Add custom fields (text, number, date, dropdown, checkbox) and choose which are required. Archiving a field retains old values. Archiving a populated bucket asks for a destination and moves its tasks together; at least one bucket must remain.

Tasks can link candidates and vacancies, or retain a free-text context. Set an owner, due date and priority. Edit or move cards with buttons as well as dragging. Quick moves show at once: a moved card appears in its new column straight away while it saves, and its move control stays unavailable until the save finishes. If the save fails, the card goes back to where it was with a message saying the move was undone. The same applies to application stage changes, archiving and restoring, your private follow-up and marking reminders read. Tabs you have opened show their last data immediately when you come back and refresh in the background. Saved views retain filters so frequently used searches are easy to revisit; views are private to your account.

## Interviews, offers and onboarding

Schedule interviews against an application, with interviewer, duration, location or meeting URL. Calendar dates/times display in **Asia/Dubai (UTC+4)**. Use day, week, month or list views and update completion/cancellation manually. A month day shows its first 3 interviews and a week day its first 20; when a day has more, a **+N more** button opens that day's view with all of them.

Track offer amount/currency, pay period, dates, status and decline reason separately from the application stage. **Activity** shows each offer status change as two badges, for example Draft → Sent. Onboarding links to an application and contains document, orientation, training or other checklist items. Progress uses complete/waived items out of configured active items; an empty checklist is not automatically complete.

Notifications collect due tasks, interviews, expiring offers, vacancy targets and onboarding items. Tasks in a bucket marked **Counts as completed** give no reminders. Marking visible reminders read affects your account. Analytics distinguish current inventory from changes actually observed by RecruitmentOS. Imported records do not invent old transition dates or time-to-hire values. **Hiring analytics** states the range it shows, for example "Showing observed activity from 6 Oct 2026 to 4 Nov 2026 · Asia/Dubai (UTC+4)"; without a chosen range it is the last 30 days. **Export statistics** starts its file with the same date range, the timezone, the export time and the environment.

## Team and account settings

Owners/admins manage team details, invitations and permitted membership changes. Only owners manage ownership; a team retains at least one owner. Only the initial administrator and people who own a team can create another team (up to five); for everyone else the **Create a team** form is hidden, and someone who has not joined a team yet is asked to accept the email invitation from their team owner. Recruiters work with recruitment records; viewers read them. Team switching changes the active workspace. If you have unsaved changes (an open editor, a follow-up or comment draft, or unfinished CV imports) or a save is still running, the sidebar team picker first asks **Switch team?**. **Stay in {team}** keeps everything as it was; **Switch team** discards the drafts, stops waiting for running saves, and the new team shows a notice naming the team you left. A save that was running may or may not have completed, so check that team before redoing it. Changing a member's role, removing a member, revoking an API token, signing out a device and closing or removing CV import drafts also ask for confirmation in the same kind of dialog; Escape or **Cancel** changes nothing.

**CV storage settings.** Owners and admins see a **CV storage** panel in Team & access with the team's current usage: stored CVs, uploads in progress and files waiting for cleanup, in decimal MB and GB (1 MB = 1,000,000 bytes). **Limit this team's CV storage** sets a maximum storage (MB or GB, up to 3 decimal places) and a maximum number of CV files; **Limit CV upload requests** sets how many new CV uploads the team may start per minute. Both are off by default, and **Save** records each change in Activity as "Updated CV storage settings". A limit below current usage is allowed: existing CVs stay available, but new CV uploads are refused until usage is below the limit. **Connected AI apps can read CV contents** is on by default: apps connected through MCP with CV permission can then read the text of the team's CVs, and each read is recorded in Activity on the candidate. Turn it off and select **Save** to stop every connected app from reading CV contents; the change is recorded in Activity as "Changed whether connected AI apps can read CV contents". These are application limits, not hard provider caps; the store-wide budget set by the RecruitmentOS owner still applies. Rejected or abandoned uploads count as files waiting for cleanup until they are deleted, a little while after their upload time ran out.

**Speed.** Owners and admins see a **Speed** tab in settings. It lists how long common actions (moving a task, changing a stage, opening each main tab, opening and saving a candidate, scheduling an interview) and API requests take for your team, as the typical time (median) and the slow time (95th percentile), with the number of samples and, for API requests, the database time. It holds the last 30 days of timings and route names only, with no names, ids or content, and has no settings to change. Recruiters and viewers who open the page see that only owners and admins can view speed timings.

**Organisation levels and units.** Your company's structure is built from levels and units. A level is a layer such as Company, Division or Department: the top level has depth 0, and a company has at most 8 levels. A unit, such as Sample Division, sits on one level, either at the top or under a unit on a higher level; each unit has a name and a code that no other current unit uses. A company owner, or a company admin with the organisation area, creates and renames levels and units and archives a level no unit uses. Only a company owner moves or archives a unit, because in later releases who can see a record will follow the unit it belongs to and the units above it, so a move or archive changes who sees those records. A unit with current units below it cannot be archived; move or archive those first. Archiving is permanent. Every change appears in Activity. There is no screen for this yet: the changes are made through the organisation routes in [API examples](api-examples.md#organisation-levels-and-units), which need a signed-in session.

**Configured roles.** Besides the four team roles, a company can define its own roles, each a narrower version of admin, recruiter or viewer: for example a recruiter who cannot upload CVs. Only a company owner can give a member such a role, or take it away; team owners and admins, company admins and API tokens cannot. Giving the role also sets the member's team role to the role's level (admin, recruiter or viewer) when a team owner or admin could make that change; otherwise the role is saved and the narrower of the two applies until the team role is changed in **Team & access**. Taking the role away leaves the team role as it is. A member keeps only what both their team role and their configured role allow, and a configured role that is later archived or changed so it cannot be used gives the member no access until a company owner gives them another role or takes it away. Team owners always keep the Owner role. Roles limited to a unit or to assigned records, such as the hiring manager and interviewer templates, cannot be given to anyone yet. A company owner gives or takes away a role in **Team & access**: the **Configured role** column of the member list has, for each member who is not a team owner, a list of the published roles that can be given ("Team role only (no configured role)" takes the role away) and **Save configured role**, which asks you to confirm. Team owner rows say "Team owners keep the Owner role". Nobody else sees the column. Roles limited to a unit or to assigned records are never in the list; when one exists, a line above the list says they are not offered yet. A member whose role has been archived, unpublished or republished limited to a unit or to assigned records shows **Role no longer available** with the role's name: choose another role and **Save configured role**, or **Clear role**. Until then that member is refused every page and action with "Your role is no longer available. Ask a company owner to choose a role for you." If the role is saved but the team role could not be changed, the page says so; try again, or ask a team owner or admin to check the team role. Every assignment is recorded for the company owners, who see the last seven days of assignments in **Recent access changes (last 7 days)** on the **History** tab of the Admin portal, and activity about company structure and roles appears in the activity list only for people with company authority.

**Admin portal.** The Admin portal, at `/app/admin`, brings together the settings you manage. Team owners and admins also reach it with the **Admin portal** link in settings; a company owner or admin whose team role is recruiter or viewer opens `/app/admin` directly. It shows only the tabs you may open. Team owners and admins see four team tabs, each a short description and a button to the existing page: **Members** opens **Team & access**, **CV storage** opens the **CV storage** panel in **Team & access**, **Speed** opens **Speed** and **API tokens** opens **API tokens**. Company owners and company admins also see **History**, whatever their team role; a team role alone, even owner, never shows it. **Configuration history** lists the company configuration changes made in any team of the workspace, newest first, 25 at a time with **Show older changes**: the time, the change (Draft created, Published, Retired, Archived or Layout changed), what was changed (for example Workflow or Record fields, with its key), the version and who made it. It never shows the configuration itself. Company owners also see **Recent access changes (last 7 days)**: role assignments and home-unit changes in every team, with the members affected (named when they are in your current team, otherwise shown as "A member of another team"), the role and who made the change; when there were more changes than the list can hold it says only the latest changes are shown. Opening `/app/admin` takes you to your first tab. Company owners also see **Roles & permissions**, described below; company admins and team owners do not. **Organisation** shows for company owners and for company admins given the Organisation area, whatever their team role; a team role alone never shows it. **Directory** shows for anyone whose role includes viewing the directory, which today means team owners and admins (and configured roles copied from the Admin template that keep it). Both are described below. If you have no tab, or open a tab you may not use, the portal shows only "You do not have access to this page". The other company configuration tabs arrive in later releases.

**Roles & permissions.** Only company owners see this tab of the Admin portal; anyone else who opens `/app/admin/roles` sees "You do not have access to this page". **Roles** lists the built-in Owner, Admin, Recruiter and Viewer templates. **View … template** shows a template as text: its membership, pages, actions per resource, field rules and record scope. The Owner template cannot be edited or copied. **Copy to a new role** on Admin, Recruiter or Viewer asks for a name (1 to 120 characters, "Copy of …" at first) and creates a draft role; the role's key is made from the name, so choose a name no other company role uses. The draft opens in the editor, with standard checkboxes and lists: the role's name, the pages it can open, the actions it allows on each resource (open a resource to see its actions), a rule for each field of each kind of record (Default, Hidden, Read only or Can edit) and the record scope, which is All records for every group for now. A role keeps the membership (admin, recruiter or viewer) and permissions of the template it was copied from and can only narrow them, so the editor refuses a grant that membership cannot hold: ticking **Edit** on candidates for a viewer role, for example, shows "Viewer membership cannot hold a write action." next to it and a summary at the top, and the draft cannot be saved until it is unticked. Plan access is never part of a role; it is given per person in **Company authority**. Some checkboxes sit under a **Takes effect later** sub-heading: the pages other than Overview, Analytics and Activity, every action on Teams and on Two-step sign-in reset, and the Directory actions other than View, Create, Edit and Archive. Nothing checks those settings yet; they are saved with the role and apply once the screens and actions that use them arrive, so you can set them now. **Save draft** keeps your changes; **Publish**, offered once the draft is saved with nothing refused, asks you to confirm because publishing changes access for every member who holds the role. **Company roles** lists each role as "Draft", "Published (version N)" or "Published (version N), draft in progress", with **Edit draft**, **Publish** or **New draft**; a role limited to a unit or to assigned records is marked "Cannot be assigned yet". Roles limited to a unit or to assigned records, such as hiring manager and interviewer, arrive in a later release. Every draft and publish appears in **History** as "Role: <key>".

**Company authority.** The same tab lists the company owners and admins and lets a company owner change them. A company owner holds every company area and manages roles and company authority; a company admin manages only the areas given to them: Record fields, Workflows, Boards, Organisation and Templates (only Organisation has a screen or route today). Plan access is a separate per-person grant that only a company owner gives, to anyone holding a company level, themselves included; no role or team role brings it. To grant or change authority, choose a person (the members of your current team and everyone who already holds authority), a level ("No company authority", "Company admin" or "Company owner"), the areas for a company admin and whether they have plan access, then **Save company authority**. **Remove** takes someone's authority away after you confirm. The last company owner cannot be removed or made a company admin: "The last company owner cannot be removed. Make someone else a company owner first." Someone who leaves every team of the company is shown "Suspended: left every team of this company" and holds no authority; after they rejoin a team, **Restore authority** gives back what they held. Restoring someone who is still in no team says "This person is not a member of any team in this company. Invite them to a team first." "Nothing changed." means the grant was already in place. Every change is recorded in your team's activity, shown only to people with company authority; a list of authority changes across every team is not available yet.

**Organisation.** Company owners, and company admins given the Organisation area, see this tab of the Admin portal (`/app/admin/organisation`); anyone else sees "You do not have access to this page". **Levels** lists the layers of the organisation, top first, with their depth (0 is the top) and whether they are archived. **Add level** takes a name and one of the depths from 0 to 7 that no level uses yet; **Rename** and **Archive** sit on each current level, and Archive asks you to confirm. The **Org chart** is a list of units that loads one level at a time: at first only the top-level units, then, when you expand a unit with its button (Enter or Space), its positions and the units below it. Collapsing and expanding again does not reload. Each unit shows its name, code and level; each position its title, code and "Manager" when it is a manager position. With directory access, **Show employees** on a position lists the name and employee number of the people who hold it, 25 at a time with **Show more**; work email and phone never appear in the chart. Without directory access the chart says "You need directory access to see who holds these positions." **Add top-level unit** and **Add unit below** take a name, a code and a level; **Rename** changes a unit's name; **Add position** takes a title, a code and whether it is a manager position; **Edit** changes a position's title and manager mark; **Archive** on a position asks you to confirm. Moving and archiving a unit, and moving a position, change who can see which records once unit roles arrive, so only company owners see **Move** and **Archive** on units and **Move** on positions. **Move** picks the new place one level at a time ("Top level" for a unit); only the first 200 units of a level are listed, and the picker says so. Company admins can archive a position, but a position held by an employee linked to a user needs a company owner, and that refusal shows next to the position. Every refusal shows in plain words next to the form or row that caused it, for example when a code is already used, a unit's level is not below its parent's, or a unit would move under itself.

**Directory.** People whose role includes viewing the directory see this tab of the Admin portal (`/app/admin/directory`); anyone else sees "You do not have access to this page". Filter the employees by **Name or employee number** (part of either), **Unit** (pick it one level at a time; the units below it are included), **Level**, **Position** (the positions of the chosen unit, once a unit is chosen) and **Status** (Any, Active or Left), tick **Include archived employees** to see archived ones, and press **Search**. The table shows 25 employees a page with their name, employee number, positions (primary first), status, retention class, whether they are linked to a user account (never which account) and whether they are archived, with **Previous page** and **Next page** and a line naming the page. **Work email** and **Work phone** columns appear only when your role's directory rule is full; under the basic rule they are not shown at all. Each row has one **Actions** button, which opens the actions you may take on that employee in a dialog; a refusal shows in its own line under the row. With the matching directory actions you can **Add employee** (display name, employee number, work email and phone, status and retention class), **Edit** those facts (the work email and phone only under the full rule) and **Archive** an employee after confirming. **Positions** opens the employee's current positions: choose the primary one, **Remove** one, or add one by picking a unit and a position, then **Save positions**. Linking an employee to a user and changing a linked employee's positions set whose records a person can see once unit roles arrive, so only company owners see **Positions** on a linked employee and **Link to user** and **Unlink user**. **Link to user** lists the members of your current team and asks you to confirm before linking; **Unlink user** asks you to confirm. Company owners also see **Permanently erase employee** under each row's **Actions** and the **Retention review**, described below.

**About.** The footer of every workspace page and the sign-in page show the version you are using, for example "Version 1.0.0 (build 20261108.1430)"; the build number is the build time in UTC. Everyone who is signed in, in any role and also before joining a team, sees an **About** tab in settings with the version, build, commit, environment (Production, Preview or Local development) and build time in UTC. **Copy details** copies three lines for a bug report: the version with build and commit, the environment and the build time. It holds nothing secret and nothing about you, your team or your browser. If your browser cannot copy, copy the details shown on the page instead.

**Two-step sign-in.** Owners and admins must use two-step sign-in; for recruiters and viewers it is optional, but you need it to create API tokens or connect apps. To set it up, open **Turn on** under **Two-step sign-in** in My profile (owners and admins are taken there automatically): enter your password, scan the QR code with an authenticator app or type the setup key shown below it, enter the 6-digit code the app shows, then save the 10 backup codes and tick **I have saved my backup codes** before **Continue**. The codes are shown only once. From then on, signing in asks for your password and then **Enter your sign-in code**: type the current code, or choose **Use a backup code instead** if you do not have your phone; each backup code works once. Tick **Trust this device for 30 days** only on your own device: it skips the code there for 30 days after you last entered one, then asks again. **Create new backup codes** (with your password) replaces all your codes and forgets your trusted devices. **Turn off** asks for your password and a confirmation; owners and admins are asked to set it up again straight away, which is also how you move to a new phone. If someone's role changes to owner or admin, they set it up at their next sign-in. Someone who has lost their phone and codes can be helped by an owner of every team they belong to: in **Team & access**, **Reset two-step sign-in** on that member's row signs them out everywhere and removes their authenticator, so they set it up again; the reset appears in Activity. Five wrong passwords for one email in a row make the next sign-in wait a minute, and the wait grows after further wrong attempts; a correct password clears it.

Profile settings manage your name, password and sessions. Signed-in devices load only when you select **Show signed-in devices**. If your sign-in is not recent, the list asks you to sign out and sign in again before it shows your devices; **Sign out all other devices** works without loading the list. In **API tokens**, create a named token for one integration, choose the smallest necessary scopes and expiry, and copy it once to the integration's secret store. Revoke unused tokens. A token remains tied to your user and team and loses permissions when your role changes or your membership is removed. See [API examples](api-examples.md). To connect an AI assistant such as Claude, see [mcp.md](mcp.md); connected apps appear in the same list with an **OAuth app** badge and are revoked the same way. With CV permissions a connected AI app can read the text of PDF and DOCX CVs and upload CVs, one at a time or as a bulk import that you review in the app; an app that cannot send files gives you a link that opens **Import CVs** on **Candidates**. The app's analysis of a CV is not saved unless you ask it to add a comment or update the candidate's details.

## Data administration

An administrator prepares cloud services and imports legacy files using [deployment.md](deployment.md) and [migration.md](migration.md). The importer starts with a local reconciliation report and requires an explicit apply command. PostgreSQL becomes the canonical store; editing old Excel workbooks does not update the deployed application.

**Permanently erase a candidate (owners only).** For a data-protection request, a team owner opens the candidate's **Full profile** and, under the record details, chooses **Permanently erase candidate**. The dialog lists what is removed (candidate details, applications, interviews, offers, onboarding and checklist items, comments, every member's follow-up notes and shortlist, CV files and AI suggestion records), what is kept (tasks, unlinked from the candidate and with the name replaced; activity entries without personal details; a record of who erased the candidate and when) and what is not covered (CSV exports already downloaded). Type the candidate's name exactly as shown to enable **Permanently erase**. This cannot be undone; to keep the record but hide it, archive it instead. CV files are deleted from storage once their upload links have expired; the confirmation says when. Admins, recruiters and viewers do not see this action. Before and after erasing, follow [erasure-runbook.md](erasure-runbook.md), which also covers requests handled with the owner-run `npm run erase:candidate` script.

**Permanently erase an employee (company owners only).** For a data-protection request about someone in the company directory, a company owner opens **Admin portal > Directory** (`/app/admin/directory`). Type part of the name or the employee number in **Name or employee number**, tick **Include archived employees** and press **Search** or Enter; each row shows the status (Active or Left), retention class (Standard or Extended) and whether the employee is archived. **Actions** on the employee's row, then **Permanently erase employee**, opens a dialog that lists what is removed (the directory entry: name, employee number, work email and phone, status and retention class; the position history; the link to a user account), what is kept (positions and units, the user's account and team memberships, activity entries without personal details, a home-unit change entry for the unlinked user, and a record of who erased the employee and when) and what is not covered (copies outside the app, such as spreadsheets the directory was imported from). Type the employee's name exactly as shown to enable **Permanently erase**. This cannot be undone; for routine cases set the status to Left or archive the employee instead. The page then says "Employee permanently erased." and the directory page and the retention review reload. Company admins, team owners and admins without company authority do not see the action. Follow the "Erase an employee" section of [erasure-runbook.md](erasure-runbook.md#erase-an-employee) before and after erasing.

**Retention review (company owners only).** The **Retention review**, below the directory in **Admin portal > Directory**, lists the employees whose status has been Left for 12 months or more, oldest first, archived ones included, with the date they left and their retention class, 25 at a time with **Show more**. Nothing is erased automatically: review the list and erase an employee only after you have decided their data is no longer needed. The retention class is set when adding or editing an employee in the Directory or through the API (`retentionClass`, Standard by default) and is shown only; owners cannot yet set retention periods. Searching and the review need a team role with directory access (team owner or admin). Both are also available to a signed-in company owner as `POST /api/v1/employees/{id}/erasure` and `GET /api/v1/employees/retention-review` ([api-examples.md](api-examples.md#employee-erasure-and-the-retention-review)); API tokens and AI apps cannot use them.
