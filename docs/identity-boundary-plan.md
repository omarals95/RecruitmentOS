# Identity and tenant boundary: implementation plan

**Implemented and Preview verified; a protected Preview deployment exists ([ROADMAP.md](ROADMAP.md)), Production is not deployed.** Migration `0006_trusted_tenant_context.sql` replaces the GUC-based tenant policies with a signed per-transaction context (see [Signed tenant context](#signed-tenant-context)). It was tested on PGlite with synthetic nonowner roles and on a throwaway local PostgreSQL 18 cluster. In the owner's run on the Neon Preview database, the role template is applied, `scripts/db-role-evidence.ts` passes with zero drift, and `npm run test:live-roles` passes 27/27 through the transaction-mode pooler and 27/27 direct, with all fixtures removed. It has not been independently reviewed (DEC-02/DEC-03) or verified on Production. Blob CV storage is enabled in code through Vercel OIDC since job 030; its Preview switch-on waits for the owner's environment settings, migration `0018` and the role template. No role, credential or hosted database is changed by this document. The Production Marketplace resource's database contents and effective privileges have not been verified. Confirm them before any mutation.

The first staged code introduces separate data and identity pool interfaces and migration `0005_database_connection_marker.sql`, which creates an owner-controlled per-database marker. The two runtime roles would need read-only access to that marker; neither may alter it. Matching the endpoint and marker helps detect mismatched pools but does not prove environment separation when a database has been cloned or incorrectly configured. The legacy shared-role fixture has been removed. [postgres-split-runtime-roles.sql](../infrastructure/postgres-split-runtime-roles.sql) creates the `recruitmentos_data` and `recruitmentos_identity` roles with exact object-by-object grants (WP-02a). It is verified on PGlite, on a throwaway local PostgreSQL 18 cluster and, in the owner's run, on the Neon Preview database, where it is applied and `scripts/db-role-evidence.ts` passes with zero drift. It has not been verified on Production.

Hosted and `NODE_ENV=production` database startup (`createDbPair()` in `src/db/index.ts`) has no blanket block (WP-02e). It fails closed on precise checks, with no environment-variable override, before serving any request:

- `DATABASE_MODE=pglite` or `ALLOW_LOCAL_DB=true`: 503 `local_db_disabled`.
- `DEV_MAIL_MODE=console` or any `DEV_SEED_PASSWORD`: 503 `development_setting_refused`.
- A missing or malformed `TENANT_CONTEXT_SIGNING_KEY`: 503 `tenant_context_unavailable`.
- A missing `DATABASE_URL` or `IDENTITY_DATABASE_URL`, URLs for different endpoints or databases, missing credentials, any URL parameter other than one `sslmode=require|verify-full`, or a non-empty `PGOPTIONS`: 503 `unsafe_database_connections`, before any pool exists.
- Non-loopback pools always use `sslmode=verify-full` with certificate verification.
- A session login that differs from the effective role, or an unsafe result from the runtime role safety query (elevated attributes, broad `pg_*` roles, protected-object ownership, ownership of the current database, database `CREATE`/`TEMPORARY`, grant options, `public` schema access) or the marker and per-role boundary queries: 503 `unsafe_database_role`.
- A missing connection marker, the same effective role on both pools, mismatched markers, or a role able to assume the other: 503 `unsafe_database_connections`.
- A missing or different storage schema version: 503 `storage_schema_mismatch`.

Any failure ends both pools. Startup checks only that the signing key is set and well formed: an uninstalled or retired key is rejected per transaction by `tenant_context.install` (403 `tenant_context_denied`), because the runtime roles cannot read `tenant_context.keys`. Hosted sign-in opens only through the readiness checks in `getAuthOptions()` ([authentication.md](authentication.md#hosted-sign-in-readiness)), and hosted Blob CV storage accepts only the request's Vercel OIDC token with an explicit store id (`getStorage`, refused while `BLOB_READ_WRITE_TOKEN` is present). The role-boundary checks forbid callable non-system security-definer functions and accessible views/foreign tables, except an exact per-role allowlist of `tenant_context` helpers (`src/db/connection-boundary.ts`). The data role's list includes `tenant_context.lock_storage_allocation(text,text,text)`, which locks the CV storage ledger rows for the context's team (migration `0007`), and the Blob read-lease helpers `tenant_context.acquire_blob_read(text)` and `tenant_context.release_blob_read(uuid)`, which take and release a cross-instance provider read lease for the context's team only (migration `0009`), and since migration `0018` `tenant_context.set_storage_limits(bigint,integer,integer)`, which writes the team's storage limits and upload rate for an owner or admin session with one audit row per change, and `tenant_context.release_blob_charge(text,uuid)`, which frees one rejected Blob upload's retained charge of the context's team after its object was deleted, no earlier than 10 minutes after expiry (see [CV storage settings and Blob charge release](#cv-storage-settings-and-blob-charge-release)). A helper is allowlisted only when the `tenant_context` schema owner owns it and its `search_path` is fixed to exactly `pg_catalog, pg_temp` (temporary objects last). Local synthetic tests do not establish a completed SQL-compromise boundary.

## Security objective and limit

Prevent a caller with arbitrary SQL execution **on the recruitment-data database role** from changing authentication state, minting an accepted API token, impersonating a different team in a quota operation, or reading another tenant's recruitment data. This is defense against a compromised SQL access path, not compromise of the application process, trusted identity service, signing key, database owner or operator. It also does not establish that any public SQL injection exists.

Synthetic local tests reproduced both team-context forgery and authentication using a token inserted by the shared runtime SQL role; they did not use real candidate data or demonstrate an exposed HTTP exploit. Two distinct changes were necessary. Separating identity writes blocks the token-minting signer oracle. Every protected data path now also derives team, actor and access from a verified per-transaction assertion instead of `app.team_id`/`app.user_id`. A future quota command still needs its own signed command design (item 5). Do not claim strict isolation until the design is independently reviewed and tested on live connections.

## Proposed privilege separation

1. In **each** environment use independent credentials and pools for (a) a restricted identity role and (b) a nonowner recruitment-data role. Neither role may inherit, assume or obtain the other, the migration owner, `neon_superuser` or broad built-in data roles. Neon roles created through the Console/API/CLI may be granted `neon_superuser`; use a reviewed SQL provisioning method and verify effective attributes, membership, default ACLs and ownership. Do not print or commit passwords or connection strings.
2. Route Better Auth and account/session/team operations to the identity role. Route principal and API-token authentication through controlled identity access. Grant only operations verified necessary for the Better Auth adapter and token lifecycle, rather than `ALL TABLES IN SCHEMA auth`; deny direct access to setup-marker writes except through the reviewed owner-controlled trigger functions. Identity-role access to recruitment tables must be denied, except for the narrowly defined activity/audit write required below. This role remains powerful over identity; it must be isolated from the recruitment-data SQL path.
3. Route `withTeam()` recruitment operations to the data pool. Deny data-role identity mutations including token, session, user, account, member and invitation inserts, updates and deletes, both directly and through inherited or public grants. Restrict identity reads to the reviewed minimum; avoid exposing password hashes, token hashes, session tokens and other teams' identity information. Adapt create-admin, team selection, principal resolution and the activity-name join explicitly instead of preserving broad auth-table access.
4. **Implemented locally.** Token audit uses a same-transaction identity-side helper rather than an outbox (the DEC-03 choice; see [Token audit](#token-audit)). Token create/revoke and the append-only activity insert commit or roll back together in the identity-role transaction. The identity role gets no `app` table grants. The row passes FORCE RLS on `app.activity` because the transaction holds a verified signed context. Concurrent cap enforcement keeps the `liveHuman()` row lock. Multi-connection races are still unverified.
5. Only after the identity boundary is in place, design the quota operation. A candidate is a short-lived, domain-separated signed command generated by a trusted signer after validating the real session or API token, current membership and `cvs:write`. Bind environment, store, team, principal, auth type and token identity/scope, candidate, ticket/path, maximum size/type, expiry, nonce and idempotency fields; the database must act only on the verified payload. Protect verification keys from the data role; enforce atomic nonce/retry behavior, store/team locks and durable charges. The signer, its identity-state source, credential ownership, revocation timing, log redaction, rotation, TLS and function grants require independent review. An HMAC added to the current shared-role design is insufficient because that role can currently mint the token used to obtain a legitimate assertion. Alternatively, a separately authenticated quota role and service may use narrowly scoped grants after independently verifying the real identity and token scope; it must not be assumable by the data role, and a service accepting caller-selected identities without independent verification recreates the same flaw. Separate roles and processes add credentials, connections and operational complexity and are a candidate design, not a verified fix.

   **Local ledger (WP-04), pending review.** Migration `0007` does not use a separately signed quota command. `tenant_context.lock_storage_allocation(provider, environment, store)` requires the verified per-transaction context with `cvs:write` and charges only that context's team. It also releases expired S3 reservations on the same bucket for every team, so one team's abandoned tickets cannot hold the shared budget; it changes no amounts, only moves those tickets to `rejected`. Owner-run triggers on `app.uploads` then take the charge from the upload row itself, never from caller arguments. The context already binds team, actor, scopes and database. Nonces, a separate quota role and live verification are not implemented.

6. **Implemented locally.** All nine `app` tables (`records`, `candidate_states`, `activity`, `uploads`, `storage_usage`, `idempotency`, `notification_reads`, and since migration `0015` `bulk_intake_batches` and `bulk_intake_items`) keep FORCE RLS with context-derived policies. Every `USING` and `WITH CHECK` expression calls an owner-controlled predicate. The predicate finds the verified context for the current backend and transaction and ignores every GUC. Migration `0007` adds `ledger_owner_read` and `ledger_owner_update` on `app.uploads` and `app.storage_usage`, which match only when `current_user` is the `tenant_context` owner (inside the owner-run ledger helper and triggers); they never match a runtime role.
   - Reads need a context for the row's team.
   - Writes, including `SELECT … FOR UPDATE`, also need a write scope (see [Coarse write gate](#coarse-write-gate)).
   - Private rows also need the context actor: `candidate_states.user_id`, `notification_reads.user_id`, `bulk_intake_batches.created_by` and `bulk_intake_items.created_by`, saved-view `records.private_owner_id`, and `personal_state_updated`/`saved-view` activity. Candidate activity needs `candidates:read`.
   - A new activity row must name the context actor (`tenant_context.allows_event`). A `session` row carries no token id, a `token` row carries the context's own token id, and an `import` row needs `imports:write`. A caller therefore cannot forge an event under another member's id or plant one to read a user's name through `activity_actor_name`, which only resolves events the context may read.
   - Replay, rollback and pooling rules are below.

   A database principal or owner capable of changing policies or functions remains trusted.

## Signed tenant context

### Chosen mechanism and rejected alternative

**Chosen: a signed per-transaction assertion.** Each data transaction carries one HMAC-SHA256 signed assertion. An owner-controlled `SECURITY DEFINER` function, `tenant_context.install(payload, signature, cached)`, verifies it and stores the claims in an owner-only context table keyed by backend pid and transaction id, with the access state it derives from database rows. Policies read only that row.

**Rejected: per-principal or per-team database roles.** Every user or team would need its own role and credential. Pooled serverless connections would need a role switch per request, which the data role must not be able to do freely. Role grants would also have to track every membership change.

**Tradeoffs.** The signed design keeps one data pool, reuses the reviewed research fixtures and behaves the same on PGlite and PostgreSQL. Its costs are a signing key the application must protect, definer functions and an allowlist that need review, and two extra statements per transaction.

### Threat model and limit

The design covers arbitrary SQL on the recruitment-data role: forging settings, calling helpers directly, reading other teams' rows or other users' private rows, replaying assertions and reusing pooled connections. The application process, the signing key, the identity role and the database owner are trusted. Anyone holding the key or owner access can mint or bypass contexts.

### Payload fields

The application builds canonical JSON with these fields in this order, signs it with `TENANT_CONTEXT_SIGNING_KEY`, and passes the payload and the hex signature as bind parameters.

| Field    | Meaning                                                                 |
| -------- | ----------------------------------------------------------------------- |
| `aud`    | Fixed domain-separation string `recruitmentos-tenant-context-v1`        |
| `kid`    | Key id: the first 16 hex characters of the SHA-256 of the key bytes     |
| `env`    | `db_boundary.connection_marker.id` of the target database               |
| `pid`    | `pg_backend_pid()` of this connection                                   |
| `xid`    | `pg_current_xact_id()` (xid8) of this top-level transaction             |
| `team`   | Team id (bounded identifier)                                            |
| `actor`  | User id (bounded identifier)                                            |
| `auth`   | `session` or `token`                                                    |
| `token`  | Token id when `auth` is `token`; `null` for `session`                   |
| `scopes` | Effective scopes: a subset of the eleven known scopes, in a fixed order |
| `exp`    | Expiry in epoch milliseconds, computed from the database clock          |

`install` first checks the size (at most 2048 bytes) and verifies the signature with a known, unretired key, before it reads any identity state. It then requires all of the following:

- the canonical encoding and the exact field set;
- the audience and the environment marker;
- the current pid and xid;
- bounded identifiers, and a token id exactly when `auth` is `token`;
- known scopes;
- an expiry in the future and no more than 60 seconds ahead;
- no existing context for this pid and xid.

Under `FOR SHARE` locks it then rechecks that the user is email-verified and a current member of the team, and that the asserted scopes fit the member's current role. For a token it also checks that the token belongs to that user and team, is unrevoked and unexpired, and stores every asserted scope.

Since migration `0029_signed_context_workspace.sql` (job 043, Release 2 item R2a-02) the function is `tenant_context.install(text, text, text[])` and returns `jsonb`; the two-argument version is dropped. Every check above runs first, unchanged and in the same order, and the payload, its fields, its encoding and the audience are unchanged. Only then does `install` derive five more values and store them in new columns of `tenant_context.contexts`, for session and token contexts alike. Nothing in this step reads `member.role` for company authority or any payload field other than the verified team and actor:

| Column          | Source                                                                                                                 |
| --------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `workspace_id`  | `app.workspace_teams.workspace_id` of the verified team; a team with no mapping is rejected with `42501`               |
| `member_role`   | The `auth.member.role` the membership recheck above read                                                               |
| `company_level` | `level` of the actor's unsuspended `app.workspace_admins` row in that workspace (`owner` or `admin`); null without one |
| `company_areas` | `areas` of that row as stored; `{}` without one (a company owner's row lists none)                                     |
| `plan_access`   | `plan_access` of that row; false without one. Stored for later `allows_plan` use, not returned                         |

The `app.workspace_admins` read takes no row lock: an authority change committed before `install` applies to this transaction, and one committed after it applies to the next. The function returns `{scopes, workspaceId, memberRole, companyLevel, companyAreas}`: the stored scopes in canonical order, the workspace id, the team role, the company level or JSON null, and the stored areas (`[]` when none). `installTenantContext` (`src/lib/tenant-context.ts`) returns it as `TenantAccess`, and `withTeam` passes it to its work function as the second argument, in the same statement and round trip as before. The third argument, `cached`, is the unsigned configuration-version hint (R2a-05): since migration `0032` the application passes the version ids its instance cache holds, and the hint can only drop bodies from the result (see the `0032` paragraph below). Columns added to an existing table leave older context rows with nulls and defaults; those rows belong to ended transactions, and an xid8 is never reused, so they match nothing.

Since migration `0031_scope_ceilings.sql` (job 045, Release 2 item R2a-03) only the body of `install` changes; the signature, every check, the payload and the result are unchanged, and `CREATE OR REPLACE` keeps its grants. The known list is, in this order, `candidates:read`, `candidates:write`, `recruitment:read`, `recruitment:write`, `cvs:read`, `cvs:write`, `imports:write`, `directory:read`, `directory:write`, `plans:read` and `plans:write`, the same order as `SCOPES` in `src/lib/permissions.ts`. The role ceilings are explicit lists, so a scope appended later cannot widen them: owner and admin may assert all eleven; recruiter only `candidates:read`, `candidates:write`, `recruitment:read`, `recruitment:write`, `cvs:read` and `cvs:write`; viewer only `candidates:read`, `recruitment:read` and `cvs:read`. `roleScopes()` uses the same lists. The four new scopes grant no access on their own: no route, MCP tool, SQL policy or helper uses them yet, and they cannot be chosen for API tokens (`API_TOKEN_SCOPES`) or offered to MCP clients (`MCP_SCOPES`, D13). Plan access will also need the per-person `app.workspace_admins.plan_access` grant that only a company owner gives (R2d-12, D10).

Since migration `0032_config_versions_install.sql` (job 046, Release 2 item R2a-05, decision D1) only the body of `install` changes again: every existing check, error code and statement up to and including the context `INSERT` is unchanged, the signature and grants stay, and the result gains two keys after the five above.

- **`versions`** maps each configuration object id to its current version id (`{}` when there is none). It lists every `app.config_objects` row of the workspace `install` derived that is not archived and whose `current_version_id` names a `published` version of the same object and workspace, for company objects (`team_id` null) and the verified team's own task boards only, never another team's. It comes from the company tables alone: nothing beyond the verified team comes from the payload, and nothing from the hint.
- **`documents`** is a JSON array, ordered by version id, with one `{versionId, objectId, type, key, number, bodySha256, body}` object for each entry of `versions` whose version id is not in the hint. `bodySha256` is the stored `body_sha256` and `body` is the stored body's exact `jsonb` text as a JSON string, so the application checks the hash byte for byte.
- **The hint rule.** `cached` is unsigned and is read only after every check and the context row. It can only make the response smaller: ids are compared as text with a null-safe test, so a `NULL` array, `NULL` elements, duplicates, non-uuid strings and ids of another workspace, another team, a draft, a retired version or an archived object never raise and never change a check, the stored row, the scopes, the workspace, the company fields or `versions`. An id that is not a current version in `versions` is ignored.
- **The instance cache.** `ConfigBodyCache` (`src/lib/config-cache.ts`, exported from `src/lib/config-store.ts`) holds published bodies by version id, at most 8 MiB (8,388,608 bytes of UTF-8 body text), and evicts least recently used entries first; an evicted body is simply returned again by the next install. Published bodies are immutable, so an entry is never stale, and which version is current comes from the database every transaction. A body enters only when the hex SHA-256 of its text matches `bodySha256` and it parses to a JSON object; it is stored deep-frozen. `installTenantContext` snapshots the entries it names in the hint before signing and passes the ids as one bound `text[]` in the same statement. It then merges the response with those entries into `TenantAccess.documents`, keyed by version id and holding exactly the versions in `versions`. A hash mismatch, a current version with no body from either source or a body of another object fails the request as an internal error and caches nothing from the response. `currentConfigBody(access, type, key)` reads a current body from the access state and runs no statement.
- **Identity-side transactions** (`src/lib/api-tokens.ts`, `src/lib/two-step.ts`) and token contexts also receive `versions` and `documents` and share the instance cache. The bodies are company configuration with no record values that every context of the workspace may already read under `allows_workspace`; writes stay session-only. The migration raises the storage schema marker to 11.

Since migration `0035_member_roles.sql` (job 052, Release 2 item R2a-10, decision D1) `install` also narrows the stored scopes to the member's configured role (architecture §3.5). Every existing check, error code and statement up to the purge is unchanged and runs first, including the membership-ceiling rejection and the token checks; the signature, owner and grants stay. After the company authority read and before the context row, it reads the actor's `app.member_roles` row for the verified team:

- **No row.** The member holds the built-in template of `member.role`: `role_version_id` is that template's fixed version id from `src/domain/config-defaults.ts` (owner `…101`, admin `…102`, recruiter `…103`, viewer `…104`) and the stored scopes are exactly the asserted scopes, as before.
- **A usable role.** A non-archived `role` object of the context's workspace whose current version is `published` and whose `recordScope` groups (`pipeline`, `candidates`, `tasks`) are all exactly `"all"`. `role_version_id` is that version's id and the stored scopes are the asserted scopes intersected with the string elements of the body's `scopes` array, in canonical order. A body scope outside the asserted scopes, or above the membership ceiling, is never added: the intersection can only remove scopes.
- **An unusable role** (archived, unpublished, another workspace's, a record scope other than `all`, or a body without a `scopes` array or `recordScope` object) fails closed: no scopes and a null `role_version_id`, so every policy that needs a scope refuses and the application refuses every request.

The context row gains the nullable column `role_version_id`, and the result gains the key `roleVersionId` (the id as a string, or JSON null), keeping every earlier key; `scopes` in the result is the stored, narrowed list. `TenantAccess.roleVersionId` carries it. `accessContext` (`src/lib/authz.ts`) resolves the role from it with no statement: the built-in id of `access.memberRole` gives that template, any other id the verified document of that version parsed with the strict `roleBodySchema`, and a null or unknown id or a body the schema refuses gives no role. `withTeam` then binds the principal to the stored scopes: a scope it already passed with `requireScope` that was not stored refuses the request with `403 scope_required`, and every later scope check of the request sees only stored scopes. Identity-side transactions and token contexts are narrowed by `install` the same way, since the row is the actor's in the team.

Since migration `0037_record_scope.sql` (job 060, Release 2 item R2a-18) `install` also derives the member's record scope and home units, in the same statement, with the same signature, owner and grants; every earlier check still runs first and unchanged ([Record scope and assignments](#record-scope-and-assignments)):

- **Record scope.** No `app.member_roles` row gives `{"pipeline":"all","candidates":"all","tasks":"all"}`. A usable role is now a non-archived `role` object of the context's workspace whose current version is `published`, has a `scopes` array and a `recordScope` object whose three groups are each `"all"`, `"unit"` or `"assigned"`; its `recordScope` is stored. Roles limited to a unit or to assigned records are no longer failed closed. An archived, unpublished, other-workspace or malformed role (no `scopes` array, no `recordScope` object, or another value in a group) still fails closed, with no scopes, no role version and no record scope.
- **Home units.** The distinct `org_unit_id` of every current (`valid_to IS NULL`), non-archived `app.positions` row held through a current `app.employee_positions` row by the `app.employees` row of the derived workspace whose `user_id` is the actor ([security.md](security.md) "Home-unit derivation"). No employee status or archive filter applies: only the facts `app.guard_scope_sources()` reserves to company owners decide them. Every context gets them, for any record scope.
- **Storage and result.** `tenant_context.contexts` gains `record_scope jsonb` and `home_units uuid[]`. The result gains `recordScope` (the object, or JSON null when the role failed closed) and `homeUnits` (the unit ids as strings, sorted), keeping every earlier key; `TenantAccess.recordScope` and `TenantAccess.homeUnits` carry them, so record scope adds no round trip.

Every rejection raises SQLSTATE `42501` with the single message `Tenant context rejected`. `withTeam` maps that to `403 tenant_context_denied`. A missing or short key raises `503 tenant_context_unavailable` before any database call.

### Replay, savepoint and pool rules

- The assertion is bound to pid and xid8, and an xid8 is never reused. A later transaction on a pooled connection therefore has a different xid and sees no context, and a committed assertion cannot be installed again.
- `withTeam` installs exactly once, as the first statement after the snapshot query, and creates no savepoint before it. `ROLLBACK TO SAVEPOINT` only undoes work done after a savepoint, so it cannot remove the context.
- A second assertion for the same xid is rejected while the first exists, even a validly signed one for another team. Re-installing the same assertion is rejected and leaves the context unchanged.
- The signer never issues two assertions for one transaction.
- A full rollback ends the xid and discards its context row.
- `install` purges expired context rows, at most 100 per call, so the table cannot grow without limit.
- **Transaction pooling (WP-02d).** These rules hold behind a transaction-mode pooler such as Neon's PgBouncer. The context is read and installed inside the transaction, keyed by that transaction's backend pid and xid8. The setup lock is transaction-scoped (`pg_advisory_xact_lock`), and the ledger and lease locks are row locks. The application keeps no session state. The pooler pins one backend for a whole transaction, so a later transaction gets a different xid on whichever backend it runs, and never sees the earlier context. On the Neon Preview pooler, 6 of 27 live checks failed (direct endpoints: 27/27). Locally, behind PgBouncer in `pool_mode = transaction`, the same six failed in the backend-identity and lock-overlap conditions only. The cause was a harness assumption, not an application defect: the harness read backend pids in autocommit statements outside the transactions it checked. With in-transaction pid reads, the harness passed 27/27 through the pooler, locally and then in the owner's Neon Preview run (27/27 through the transaction-mode pooler and 27/27 direct, with all fixtures removed). Pooler requirements are in [neon-database-runbook.md](neon-database-runbook.md#4-connection-pooler-requirements).

### Expiry and revocation timing

Expiry is at most 60 seconds after the database `clock_timestamp()` read by the first statement, so application clock skew and fake test timers do not matter. Predicates compare against `clock_timestamp()` on every evaluation, so an assertion stops granting access mid-transaction once it expires.

`install` rechecks membership, verification and token state under `FOR SHARE` locks. A revocation or membership removal that commits before `install` is enforced immediately. One that commits afterwards takes effect at the next transaction.

### Key storage, rotation and retirement

- **Where the key lives.** In the server-only `TENANT_CONTEXT_SIGNING_KEY` environment variable (base64url, at least 32 random bytes), and as precomputed HMAC inner and outer pads in the owner-only `tenant_context.keys` table. Neither runtime role can read that table. The key, pads, payload and signature are never placed in a setting, logged, returned or written to activity.
- **Per environment.** Each environment needs its own key. There is no default, generated or fallback key in any mode.
- **Installation.** `npm run db:migrate` (owner connection) and local PGlite startup upsert the configured key by key id. A missing key fails with a message that names the variable and shows no value.
- **Rotation.** Set the new key in the environment, run `npm run db:migrate` so its pads are installed, deploy, then retire the old key.
- **Retirement.** An operator SQL step as the owner: `UPDATE tenant_context.keys SET retired_at = now() WHERE id = '<old key id>';`. Retired keys are rejected immediately.
- **Bearer value.** An assertion is a bearer value, but it is bound to one backend and one in-flight transaction for at most 60 seconds and cannot be installed twice.
- **Statement logging.** Statement or bind logging on the owner connection during key installation would record the pads, so disable it for that step. Runtime bind logs could record assertions; they are short-lived and single-use but should still be excluded.
- **No constant-time claim.** The signature comparison is ordinary text equality in PL/pgSQL.

### Coarse write gate

Database writes need any one of `candidates:write`, `recruitment:write`, `cvs:write` or `imports:write`. Per-kind gating would break existing cross-kind `SELECT … FOR UPDATE` locks, for example an application locking its candidate. Viewers and read-only tokens are still denied every write except their own notification read markers. The application's `authorize()` (`src/lib/authz.ts`) and `requireScope()` checks enforce the exact per-resource scopes.

### Token audit

`tenant_context.audit_token(token_id, event)` runs in the caller's identity transaction, which must hold a verified session context. It enforces these rules:

- It derives team, token id, prefix and scopes from the `auth.api_tokens` row as seen in that transaction.
- The action must match the token state, and at most one event of each action may exist per token.
- Create needs the token owner. Revoke needs the token owner or a current team owner or admin.
- The summary and metadata match the earlier application inserts.

Only this owner-run helper may insert `api-token` activity rows: the general write policy excludes that kind for every context, write scope or not. A data-role caller therefore cannot forge token events or pre-insert a `token.revoked` row that would make the helper reject a later real revocation. The helper also covers contexts without a write scope, such as a viewer's read-only token. A transactional outbox was not chosen because it would delay audit visibility and need delivery and retry semantics.

- **Tables.** `app.workspaces` (`id`, `name`, `created_at`); `app.workspace_teams` (`team_id` primary key referencing `auth.organization` with `ON DELETE CASCADE`, `workspace_id`); `app.workspace_admins` (`workspace_id`, `user_id` referencing `auth."user"` with `ON DELETE CASCADE`, `level` `owner` or `admin`, `areas text[]`, `plan_access`, `granted_by` with `ON DELETE SET NULL`, `granted_at`, `suspended_at`; primary key `(workspace_id, user_id)`). Table checks keep an owner row's `areas` empty (an owner holds every area by level) and an admin's areas a duplicate-free subset of `fields`, `workflows`, `boards`, `organisation` and `templates`, so a company admin never holds `roles` or `ai`. Plan access is never implied (D10): nobody has it by default, company owners included.
- **The fixed workspace.** The migration inserts one workspace, id `00000000-0000-4000-a000-000000000001` and name `Company`, maps every existing team to it and makes the initial administrator (`auth."user".initial_admin`) company owner when they are a member of a mapped team (`level 'owner'`, no areas, no plan access, `granted_by` null). All three inserts use `ON CONFLICT ... DO NOTHING`. An environment without a company owner uses the owner SQL step in [deployment.md §2](deployment.md#2-neon-postgresql).
- **Policies.** All three tables are under FORCE RLS with `REVOKE ALL ... FROM PUBLIC`. Runtime contexts get `SELECT` policies only, and no insert, update or delete policy: `app.workspace_teams` shows a context only its own team's mapping row (`tenant_context.allows(team_id, NULL, 'read')`), so no other team's id is revealed; `app.workspaces` shows the workspace of that mapping; `app.workspace_admins` uses the policy helper below. Owner-only `workspace_owner_select`, `_insert`, `_update` and `_delete` policies on each table, with the `ledger_owner_*` predicate, let the migration, both triggers, the helper and the owner SQL step work under FORCE RLS on a non-superuser owner; they never match a runtime role. The role template grants the data role `SELECT` on the three tables and `EXECUTE` on both helpers; the identity role gets nothing new, and neither role has any write privilege on them.
- **`tenant_context.allows_workspace_admin(row_workspace, row_user)`.** An owner-run `LANGUAGE sql STABLE SECURITY DEFINER` policy helper with `search_path = pg_catalog, pg_temp` and PUBLIC `EXECUTE` revoked. It is true only when the current, unexpired context of this pid and xid has a team mapped to `row_workspace` and either `row_user` is the context actor or the actor has an unsuspended `app.workspace_admins` row there, owner or admin. So company owners and admins read every row of their workspace, and any other member, including a suspended admin, reads only their own row, if any. It exists because a policy on `app.workspace_admins` that read the table itself would recurse; the policy also skips the helper for the owner, which reads through its owner-only policy.
- **`app.map_new_team()`.** An owner-owned `SECURITY DEFINER` trigger function (PUBLIC `EXECUTE` revoked), `AFTER INSERT ON auth.organization FOR EACH ROW`, so it runs in the transaction that creates the team; Better Auth's `createOrganization` commits the team, its owner member and the active team together. Unless exactly one workspace exists it raises `23514` with constraint `app_single_workspace` and a fixed message, so a second workspace makes every team creation fail (D15: no second company in Release 2). Otherwise it maps the team. When the creator is the initial administrator and the workspace has no owner row, suspended or not, it also makes them company owner; this covers environments migrated before the initial administrator signed up, and it can never restore or add authority once an owner row exists. Creating a team writes no other `app.workspace_admins` row.
- **`app.suspend_workspace_authority()`.** An owner-owned `SECURITY DEFINER` trigger function (PUBLIC `EXECUTE` revoked), `AFTER DELETE ON auth.member FOR EACH ROW`. For each unsuspended row of the removed user it locks the workspace row, then the admin row, rereads whether the user is still a member of any team mapped to that workspace, and if not sets `suspended_at`. It never raises, so a member removal is never blocked, and it leaves `level`, `areas` and `plan_access` as they were. A re-invitation restores no company authority: only a company owner clears a suspension through the helper (audited), or the owner through the owner SQL step. Suspension writes no activity row.
- **`tenant_context.set_workspace_authority(target_user_id, new_level, new_areas, new_plan_access)`.** An owner-run `SECURITY DEFINER` helper with `search_path = pg_catalog, pg_temp` and PUBLIC `EXECUTE` revoked, allowlisted for and executable by the data role only; the data role may now execute nineteen helpers (`dataRoleHelpers` in `src/db/connection-boundary.ts`). It needs a verified, unexpired **session** context for the current pid and xid whose actor has an unsuspended `level 'owner'` row in the workspace of the context's team; otherwise `42501`, so token contexts, team owners and admins without such a row, company admins and suspended owners are refused. It then locks the workspace row (the same lock order as the suspension trigger: workspace, then admin row) and rechecks the caller. Invalid arguments raise `22023`: a null target; a level other than null (remove), `owner` or `admin`; areas or plan access with a null level; non-empty areas for an owner; areas outside the five admin areas, with duplicates or nulls for an admin; a null plan access with a level. A grant or change for someone in no team of the workspace raises `RQ006`. Since migration `0029` that membership check takes `FOR SHARE` on the target's `auth.member` rows in mapped teams of the workspace, so a concurrent removal of the target's last membership cannot leave unsuspended authority behind: a removal that comes second waits for the grant to commit and its suspension trigger then sees and suspends the new row; a removal that comes first makes the grant wait and then fail with `RQ006`. Without the lock both statements ran without waiting, and the trigger could miss the uncommitted grant. Removing or demoting the last unsuspended owner raises `RQ005`. Since migration `0043`, any level for a target whose `auth."user".two_factor_enabled` is not true raises `RQ017` (see **Company authority two-step** below). An unchanged call returns false and writes nothing; otherwise it upserts or deletes the row (a grant sets `granted_by`, `granted_at`, sorted areas and clears `suspended_at`), inserts exactly one `app.activity` row and returns true. Workspace and actor come only from the context, and every statement filters by that workspace.
- **The audit row.** Context team and actor, `actor_type 'session'`, no token, no record, kind `workspace-authority`, action `workspace_authority.changed`, summary "Changed a member's company authority" and metadata `{targetUserId, before, after}`, each of `before` and `after` null (no row) or `{level, areas, planAccess, suspended}`; never a name or email. Migration `0028` recreates the `app.activity` `context_insert` policy with every `0026` branch unchanged, except that the general branch also excludes `workspace-authority`, plus one owner-only branch for `workspace-authority` / `workspace_authority.changed` / `actor_type 'session'` rows without a token. No runtime role can insert such rows directly.
- **Team roles stay team roles.** `auth.member.role` never confers company authority: team owners and admins keep exactly their team powers, and creating a team gives no company authority beyond the initial-administrator bootstrap above. The migration raises the storage schema marker to 7.

### Configuration audit

Migration `0030_config_store.sql` (job 044, Release 2 item R2a-04, decision D1) adds the company-level versioned store for configuration documents and its metadata-only audit. Team tables and their policies, `tenant_context.install` and the signed payload are unchanged. The service is `src/lib/config-store.ts`, with body schemas in `src/domain/config.ts`; no route, page or MCP tool uses it yet.

- **Tables.** `app.config_objects` (`id`, `workspace_id` referencing `app.workspaces`, `team_id` referencing `auth.organization` with `ON DELETE CASCADE`, `type`, `key`, `current_version_id`, `draft_version_id`, `created_by`, `created_at`, `archived_at`). `type` is one of `kind-schema`, `workflow`, `board`, `role`, `template`, `task-board` and, since `0045`, `job-architecture`, and `team_id` is set exactly for `task-board`. `key` matches `^[a-z0-9][a-z0-9-]{0,62}$`, and `(workspace_id, team_id, type, key)` is `UNIQUE NULLS NOT DISTINCT`. `app.config_versions` (`id`, `object_id`, `workspace_id`, `number`, `state` `draft`/`published`/`retired`, `body` a JSON object, `body_sha256`, `created_by`, `created_at`, `published_by`, `published_at`, `note` of at most 500 characters). `number` is null exactly while the state is `draft` and is unique per object, and a partial unique index allows one draft per object. `app.config_layouts` (`version_id` primary key, `workspace_id`, `layout` of at most 524,288 bytes as text, `updated_by`, `updated_at`). Composite foreign keys `(object_id, workspace_id)` and `(version_id, workspace_id)` keep a version and a layout in their object's workspace, both `ON DELETE CASCADE`. Every user column references `auth."user"` with `ON DELETE SET NULL`.
- **Policies.** All three tables are under FORCE RLS with `REVOKE ALL ... FROM PUBLIC`. Owner-only `config_owner_select`, `_insert`, `_update` and `_delete` policies use the `workspace_owner_*` predicate of `0028`. The runtime `context_read`, `context_insert`, `context_update` and `context_delete` policies call `tenant_context.allows_workspace(workspace_id, access, area)` with the object's area: `kind-schema` → `fields`, `workflow` → `workflows`, `board` → `boards`, `template` → `templates`, `role` → `roles`, `task-board` → `task-board` and, since `0045`, `job-architecture` → `organisation`. A task-board row also needs `tenant_context.allows(team_id, NULL, 'read')`, so only the context's own team reads or writes it. Versions and layouts take the type and team of their object through an `EXISTS` on `app.config_objects`. The role template grants the data role `SELECT, INSERT, UPDATE, DELETE` on the three tables and `EXECUTE` on the five helpers below; the identity role gets nothing.
- **`tenant_context.allows_workspace(row_workspace uuid, access text, area text)`.** An owner-run `LANGUAGE sql STABLE SECURITY DEFINER` policy helper. It is true only for the current, unexpired context of this pid and xid whose derived `workspace_id` equals the row's, and only for one of the seven areas. `read` is always allowed. `write` needs a session context and, for `roles`, `company_level = 'owner'`; for `task-board`, `member_role` `owner` or `admin`; for the five company areas, `company_level = 'owner'` or the area in `company_areas`. Any other access value or area is false. The workspace and authority come from the context row that `install` derived (`0029`), never from the payload.
- **Guards.** `app.guard_config_version()` and `app.guard_config_object()` are owner-owned `SECURITY INVOKER` trigger functions with `search_path = pg_catalog, pg_temp` and PUBLIC `EXECUTE` revoked, `BEFORE INSERT OR UPDATE OR DELETE`, like `app.prevent_activity_mutation`. They are invoker functions so `current_user` is the caller: a runtime role, or the schema owner inside an owner-run helper or the owner's own SQL. In a `SECURITY DEFINER` trigger `current_user` would always be the owner. For versions: no change of `body`, `body_sha256`, `number` or `object_id` once the state is `published` or `retired`, for anyone. The only state changes are `draft → published` and `published → retired`, and only as the owner. A runtime role may only insert a draft (no number, `published_by` or `published_at`) and only edit a draft's body and note. A runtime role cannot delete a published or retired version. A body over 524,288 bytes (`octet_length(body::text)`) raises `54000`. `body_sha256` is always recomputed as the hex SHA-256 of `body::text` in UTF-8 on insert and on every draft update. For objects, a runtime role can never change `workspace_id`, `team_id`, `type`, `key`, `created_by`, `created_at` or `current_version_id`, nor insert an object with a version pointer or `archived_at` set. `draft_version_id` must name a draft of the same object. `archived_at` only goes from null to a time. A runtime role cannot delete an object with a published or retired version, which also covers the versions such a delete would cascade to. Every other refusal raises `42501`. The owner may still delete published versions, so fixtures can be cleaned and a team with a task board can be deleted. A third, owner-owned `SECURITY DEFINER` trigger function, `app.stamp_config_actor()`, sets `created_by` on objects and versions and `updated_by` on layouts to the context actor, which a runtime role cannot read. A write with no context, the owner's own SQL, keeps its values.
- **`tenant_context.publish_config_version(version_id uuid) RETURNS integer`.** An owner-run helper. It needs a session context with write authority on the version's object in the context's workspace, as in `allows_workspace`, and for a task board the context's own team; otherwise `42501`. It locks the object row and raises `RQ007` unless the version is the object's draft and the object is not archived. It sets the next number (highest plus one), `state = 'published'`, `published_by` and `published_at`, moves `current_version_id` to the version and clears `draft_version_id`. It retires nothing, writes the `config.published` row through `audit_config`, and returns the number.
- **`tenant_context.retire_config_version(version_id uuid)`.** An owner-run helper with the same checks. It raises `RQ007` unless the version is published and is not the object's current version, so `current_version_id` always names a published version. It sets `state = 'retired'` and writes the `config.retired` row. It is a fifth helper beyond the four the feature names, because only an owner-run helper may change state and publishing retires nothing; it is open for review.
- **`tenant_context.audit_config(version_id uuid, action text)`.** An owner-run helper. It needs a session context with write authority on the version's object, as above, otherwise `42501`. An action other than `config.draft_created`, `config.published`, `config.retired`, `config.archived` and `config.layout_changed` raises `22023`. It raises `RQ007` when the rows do not show the action (a draft, a published version, a retired version, an archived object, an existing layout). It also raises `RQ007` for a second `draft_created`, `published` or `retired` row for the version, or a second `archived` row for the object. It inserts one `app.activity` row: the context's team and actor, `actor_type 'session'`, no token, no record, kind `config`, a fixed summary per action, and metadata `{workspaceId, objectId, type, key, versionId, number, fromVersionId}` built from the rows. `number` is null for a draft. `fromVersionId` is the object's current version for `draft_created`, the version published before (number minus one) for `published`, and null otherwise. The body, layout and note are never included. The publish and retire helpers write their own rows, so a state change cannot go unaudited; draft, archive and layout changes are audited by the service in the same transaction.
- **`tenant_context.config_history(object_id uuid, before timestamptz, page_size integer)`.** An owner-run helper for company owners and admins: it needs a session context with a company level, otherwise `42501`, and a page size of 1 to 100, otherwise `22023`. It returns `kind = 'config'` rows whose team maps to the context's workspace in `app.workspace_teams` and whose `metadata->>'workspaceId'` is that workspace. A task-board row is returned only when its team is the context's team. It filters by object when one is given, returns rows older than `before` when it is given, newest first, at most `page_size`. The definer reads activity of every team through the `erasure_owner_*` policies, so the helper filters by workspace itself. The only columns are `occurred_at`, `action`, `object_type`, `object_key`, `version_number`, `from_version_number` and `actor_name` (`auth."user".name`): no team, user, object, version or record id, token or body.
- **Activity insert policy.** Migration `0030` recreates the `app.activity` `context_insert` policy with every `0028` branch unchanged, except that the general branch also excludes `config`. It adds one owner-only branch for `config` rows with one of the five actions, `actor_type 'session'`, no token and no record. No runtime role can insert a config row directly. The helpers can find their one-shot rows through a partial index `activity_config_object_idx` on `(metadata->>'objectId', created_at DESC) WHERE kind = 'config'`.
- **All five helpers** are owner-owned `SECURITY DEFINER` functions with `search_path = pg_catalog, pg_temp`, PUBLIC `EXECUTE` revoked, allowlisted for and executable by the data role only. The data role may now execute twenty-four helpers. `config_history`'s signature is matched in catalog spelling, `(uuid, timestamp with time zone, integer)`, and the `dataRoleHelpers` pattern accepts multi-word type names. The migration raises the storage schema marker to 9.

### Organisation hierarchy

Migration `0033_org_levels_units.sql` (job 047, Release 2 item R2a-13, decisions D1, D13 and D15) adds the company's organisation levels and effective-dated units with a closure table, under the same workspace tenancy as configuration. `tenant_context.install`, the access state, team tables and their policies are unchanged, and no helper is added to `dataRoleHelpers`. The service is `src/lib/org.ts`, with body schemas in `src/domain/org.ts`, behind the session-only routes under `/api/v1/org-units`; there is no MCP tool (D13).

- **Tables.** `app.org_levels` (`id`, `workspace_id` referencing `app.workspaces`, `name` of 1 to 120 characters, `depth` 0 to 7 with 0 the top, `archived_at`), with `UNIQUE (workspace_id, depth)` (`org_levels_depth_unique`), so at most 8 levels per workspace. `app.org_units` (`id`, `workspace_id`, `parent_id`, `level_id`, `name` and `code` of 1 to 120 characters, `valid_from` defaulting to `now()`, `valid_to` not before `valid_from`, `created_by` referencing `auth."user"` with `ON DELETE SET NULL`, `archived_at`). Composite foreign keys `(level_id, workspace_id)` and `(parent_id, workspace_id)` keep a unit's level and parent in its workspace. The partial unique index `org_units_current_code` keeps `(workspace_id, code)` unique among rows with `valid_to` and `archived_at` null, and `(workspace_id, parent_id)` is indexed for reading one chart level. `app.org_unit_closure` (`workspace_id`, `ancestor_id`, `descendant_id`, `depth` from ancestor to descendant), primary key `(ancestor_id, descendant_id)`, indexed on `descendant_id`; both unit columns are composite foreign keys with `workspace_id` to `app.org_units`, `ON DELETE CASCADE`. Every unit has its own `(id, id, 0)` row.
- **Policies.** All three tables are under FORCE RLS with `REVOKE ALL ... FROM PUBLIC` and owner-only `org_owner_select`, `_insert`, `_update` and `_delete` policies with the predicate of `0028`. The runtime `context_read` policy on all three is `tenant_context.allows_workspace(workspace_id, 'read', 'organisation')`, so any unexpired context of the workspace reads, token contexts included. `app.org_levels` and `app.org_units` add `context_insert` with `allows_workspace(..., 'write', 'organisation')` and `context_update` with `USING` read and `WITH CHECK` write: a reader's update reaches the guards and fails with `42501` rather than matching no row, which is how a company owner's token context gets `42501` for a move. There is no runtime delete policy, and no runtime insert, update or delete policy on the closure. The role template grants the data role `SELECT, INSERT, UPDATE` on levels and units and `SELECT` only on `app.org_unit_closure`; the identity role gets nothing.
- **`app.guard_org_row()`.** `SECURITY INVOKER`, `BEFORE INSERT OR UPDATE` on levels and units, so `current_user` tells a runtime role from the owner. For everyone `archived_at` only goes from null to a time. A runtime role cannot insert an archived row or a unit with `valid_to`, or with a `valid_from` other than the column default; the trigger then sets `valid_from` to `clock_timestamp()`, so the rows of one code order by when they were written and a planted date cannot make `app.guard_scope_sources()` compare against the wrong row. After insert can change only a unit's `name`, `parent_id` and `archived_at` and a level's `name` and `archived_at`. Refusals raise `42501`.
- **`app.stamp_config_actor()`** (from `0030`, reused unchanged) is also a `BEFORE INSERT` trigger on units, stamping `created_by` from the context actor.
- **`app.guard_scope_sources()`.** `SECURITY DEFINER`, `BEFORE INSERT OR UPDATE` on units. Home units grant record scope (architecture §6.5), so a parent change, an archive, and an insert whose code's most recent row by `valid_from` has a different parent all need the current, unexpired context of this pid and xid to be a session context with `company_level = 'owner'` in the row's workspace. A token context is never accepted. With no context row, the owner's own SQL, the change is let through; a runtime role cannot write without a context. Refusals raise `42501`.
- **`app.maintain_org_closure()`.** `SECURITY DEFINER`, `AFTER INSERT` and `AFTER UPDATE OF parent_id` when it changed. It first locks the workspace's `app.workspaces` row `FOR NO KEY UPDATE` until the transaction ends, so inserts and moves in a workspace run one at a time and cannot form a cycle or copy stale ancestry. That mode does not conflict with the `FOR KEY SHARE` lock foreign-key checks take on the workspace row, so concurrent unit inserts cannot deadlock and inserts into other workspace-keyed tables do not wait for org work. It then raises `RQ009` for a parent that is the unit or in its subtree (before the level check, since such a parent also breaks the level order), `RQ008` for a parent whose level depth is not above the unit's, and `RQ010` for an archived or closed parent, or an insert on an archived level. On insert it writes `(id, id, 0)` and one row per ancestor of the parent; on a move it deletes the rows linking the moved subtree to its old ancestors and inserts the cross product of the new parent's ancestors and the subtree.
- **`app.guard_org_archive()`.** `SECURITY DEFINER`, `AFTER UPDATE OF archived_at` on levels and units when it changed. Under the same workspace lock it raises `RQ010` for a unit with a current child or a level with a current unit.
- **`app.audit_org_change()`.** `SECURITY DEFINER`, `AFTER INSERT OR UPDATE` on levels and units, so direct-SQL writes are audited too. It reads the context row of the row's workspace and with none writes nothing. Each create, rename, move and archive writes one `app.activity` row: the context's team and actor, `actor_type 'session'`, no token, no record, kind `org`, action `org.level_created`, `org.level_renamed`, `org.level_archived`, `org.unit_created`, `org.unit_renamed`, `org.unit_moved` or `org.unit_archived`, a fixed summary, and metadata `{workspaceId, levelId, depth}` for a level or `{workspaceId, unitId, levelId, fromParentId, toParentId}` for a unit (`fromParentId` null on create). A move or archive of a unit, and an insert that gives a code a new parent, also writes one kind `scope`, action `scope.home_units_changed` row with `{workspaceId, unitId, affectedUserIds}`; `affectedUserIds` holds user ids only and is empty until employees exist (R2a-14). Names and codes are never in the metadata.
- **Activity insert policy.** Migration `0033` recreates the `app.activity` `context_insert` policy with every `0030` branch unchanged, except that the general branch also excludes `org` and `scope`. It adds owner-only branches for `org` with the seven actions and for `scope` with `scope.home_units_changed`, each with `actor_type 'session'`, no token, no record and `tenant_context.allows(team_id, actor_id, 'read')`. No runtime role can insert either kind directly.
- **All five new functions** are owner-owned with `search_path = pg_catalog, pg_temp` and PUBLIC `EXECUTE` revoked, and filter by the row's workspace themselves; no role is granted `EXECUTE` on them. The migration raises the storage schema marker to 12.

### Record scope in row-level security

Migration `0038_record_scope_rls.sql` (job 061, Release 2 item R2a-19, architecture §3.5, §3.6 and §13.2, decisions D1, D4 and D16) enforces in the database the record scope `scopeFilter` applies in the service. A scoped member cannot read or write an out-of-scope record by arbitrary SQL on the data role under a valid signed context. A cached idempotent response is readable only by its own actor. It rewrites no business row and raises the storage schema marker to 17.

- **Five helpers.** Each is owner-owned, `SECURITY DEFINER`, `STABLE`, with `search_path = pg_catalog, pg_temp`, schema-qualified names and `REVOKE ALL ... FROM PUBLIC`. The role template grants `EXECUTE` on each to the data role only, so it may now execute thirty-five helpers (`dataRoleHelpers`). Each reads the context only from the verified row (`pid = pg_backend_pid()`, `xid = pg_current_xact_id_if_assigned()`, `expires_at > clock_timestamp()`); without one it returns false, or null for the actor key.
  - `tenant_context.scope_is_all()`: true only when the context's `record_scope` is `all` in all three groups. A null record scope (a role that failed closed) or a partial one is false.
  - `tenant_context.in_scope(row_team text, row_kind text, row_id uuid, row_org_unit uuid, row_candidate uuid, row_scope_vacancy uuid, row_scope_application uuid, row_created_by text, row_vacancy uuid, row_parent uuid)`: the rule of `scopeRule` and `anyRecordScopeRule` in `src/lib/authz.ts`, kind by kind, from the context's `record_scope`, `home_units` and actor. It is false for another team or a null record scope, and true for kinds without a rule. A vacancy is in scope under a home unit (`unit` only, through `app.org_unit_closure`) or with an assignment of the actor on it. A pipeline row is in scope the same way, with an assignment on itself, its application or its vacancy. A candidate needs an application in scope under the candidates group's scope (through `records_application_candidate_idx`). A task is in scope when the actor created it, is assigned to it or, for `unit`, when it is linked to a candidate or vacancy in scope. A comment takes the rule of its nearest non-comment ancestor in the same team. The two trailing arguments (the backlog named eight) carry the task's `vacancy_id` and the comment's `parent_record_id`, because a `WITH CHECK` cannot read the new row back from the table.
  - `tenant_context.record_in_scope(row_team text, record_id uuid)` and `tenant_context.candidate_in_scope(row_team text, candidate_id uuid)`: lookups by primary key and by the partial index. Since `0039` the candidate itself is found through `records_candidate_id_idx` (below). A missing, other-team or out-of-scope id is false alike.
  - `tenant_context.context_actor_key()`: `actor_id || ':' || auth_type || ':' || coalesce(token_id, 'session')`, byte for byte the key `idempotencyActorKey` builds in `src/lib/records.ts` for `idempotent` and the CV upload path.
- **Restrictive policies.** One `AS RESTRICTIVE FOR ALL` policy per table, with the same expression in `USING` and `WITH CHECK`, beside the unchanged permissive policies:
  - `app.records` (`record_scope`): `(SELECT tenant_context.scope_is_all()) OR tenant_context.in_scope(team_id, kind, id, org_unit_id, candidate_id, scope_vacancy_id, scope_application_id, created_by, vacancy_id, parent_record_id)`;
  - `app.activity` (`record_scope`): the fast path, `OR record_id IS NULL OR tenant_context.record_in_scope(team_id, record_id)`;
  - `app.uploads` (`record_scope`): the fast path, `OR candidate_id IS NULL OR tenant_context.candidate_in_scope(team_id, candidate_id)`;
  - `app.record_assignments` (`record_scope`): the fast path, `OR tenant_context.record_in_scope(team_id, record_id)`;
  - `app.idempotency` (`actor_only`): `actor_key = (SELECT tenant_context.context_actor_key())`, with no fast path, under every context.
- **Owner clause, no recursion.** Every expression starts with the owner clause of `0021` (`current_user` is the owner of schema `tenant_context`). The helpers read `app.records`, `app.record_assignments` and `app.org_unit_closure` as the owner, so their own probes pass that clause and never re-enter a policy (no `42P17`). For the same reason, owner-run helpers run as the owner and are not limited by these policies: candidate and employee erasure, `add_assignment` and `remove_assignment`, `set_workspace_authority`, `publish_config_version` and the `app.maintain_record_scope()` cascade. Each applies its own checks.
- **InitPlan fast path.** `(SELECT tenant_context.scope_is_all())` and the owner clause are uncorrelated scalar subqueries, evaluated once per statement. A scope-all context (every member without a configured unit or assigned role) never calls the per-row helpers and sees exactly what it saw before. The fixture timings are in [validation.md](validation.md).
- **Comment cycle guard.** The ancestor walk in `in_scope` and the comment CTE in `scopeRule` both carry `CYCLE id SET looped USING path`. A loop of comments that direct SQL re-pointed into each other ends with no non-comment ancestor and is out of scope, while an acyclic chain of any depth is walked to its end as before. Neither the service nor the database depends on the other to terminate.
- **Writes out of scope.** A `WITH CHECK` sees the row as the before trigger left it, so an insert or update whose new row is outside the writer's scope fails with `42501`. Examples are a vacancy without an in-scope unit, a candidate with no application yet, or a vacancy moved outside the home units. An update of an out-of-scope row matches nothing. For a caller whose record scope is not all, the records insert and update in `src/lib/records.ts` answer `42501` with 403 `record_out_of_scope`. For scope-all callers the error is unchanged.
- **Actor-only idempotency and the role-version replay.** `app.idempotency` gains a nullable `role_version_id`. `idempotent` and the CV reservation store the transaction's role version with each response. A replay whose stored version differs from the context's, or is null (rows written before `0038`), is handled like an expired key: `reconcile` (or `work`) runs, the row's response, version and expiry are renewed, and the cached body is never returned. The payload-hash check still runs first. Every response returned from a stored row goes through `redact` under the current role (`createRecord` and `bulkApplications`; employee erasure returns no record fields). The CV path now uses the shared actor key, so CV idempotency rows written before `0038` become unreadable and expire.
- **Scoped-member speed (`0039`).** Migration `0039_candidate_scope_index.sql` (job 063, backlog item R2-PERF-01) adds only the partial index `records_candidate_id_idx` on `app.records(team_id, id) WHERE kind = 'candidate'`. Without planner statistics, `candidate_in_scope` read its candidate through `records_team_kind_idx`, walking the team's candidates up to that one on each call. It now reads the one row. No policy, helper, grant or business row changes, and the storage schema marker stays at 17. In the service, the statements over many rows (lists and exports, the overview's counts and groups, and candidate suggestions) take `scopeFilter(..., { once: true })`. That is the same §3.5 rule, written as a test of the row's id against the ids in scope (`scopedIds` in `src/lib/authz.ts`). PostgreSQL computes those ids once per statement. Each test is leakproof and cheap, so PostgreSQL applies it before the restrictive policy and calls `in_scope` only for rows in scope. Statements about a few records keep the per-row probes, and so do the activity feeds, whose newest-first index scan stops early. The fixture timings are in [validation.md](validation.md).

### Job architecture

Migration `0045_job_architecture.sql` (job 079, Release 2 item ADM-24, architecture §14.5, decisions D1, D13, D20 and D22) adds the company job architecture (job families, grades and titles) as one more configuration type, and a job title key on positions. It applies after `0044` and needs no rerun of the role template: the data role's table-level grants on `app.positions` cover the new column, and `CREATE OR REPLACE` keeps every replaced helper's signature, owner and grants. No row is rewritten, and the storage schema marker goes to 23.

- **The type.** `config_objects_type_check` is dropped and added again with `job-architecture`. The twelve runtime `context_*` policies of the three configuration tables are dropped and created again exactly as in `0030`, except that the type-to-area `CASE` maps `job-architecture` to `organisation`; the owner-only `config_owner_*` policies are untouched. `tenant_context.audit_config`, `tenant_context.publish_config_version` and `tenant_context.retire_config_version` are replaced with their `0030` bodies plus the same branch. `tenant_context.allows_workspace` already accepts `organisation`, so reads are open to every context of the workspace (D22) and writes need a session whose derived `company_level` is owner or whose `company_areas` hold `organisation` (D20); team owners and admins without company authority, other company admins, recruiters, viewers and every token or OAuth context get `42501`. An unmapped type still gives a null area, so every runtime read and write of it is refused.
- **One object per company.** The service writes only the key `company` (`JOB_ARCHITECTURE_KEY`; any other key is 400 `invalid_input` before any write). Its strict body (`jobArchitectureBodySchema`) holds families `{key, name}`, grades `{code, name, order}` and titles `{key, name, familyKey, gradeCode}`, names, codes and order only: no pay figure, bracket, record id or record value. `install` already returns every current published company object, so every member's context carries it, read by `jobArchitectureFor` with no statement.
- **`app.positions.job_title_key`.** A nullable `text` column with `positions_job_title_key_check`, the configuration key pattern. The database checks only the format: `createPosition` and `updatePosition` check the key against the published version in the same transaction, after the organisation write check (400 `invalid_reference`). `app.audit_directory_change()` is replaced with its `0036` body plus the field name `jobTitleKey` on an insert that sets it and on an update that changes it, never the value. Vacancies hold the same key in `data.jobTitleKey`, checked the same way when it is set or changed; MCP vacancy tools take and show it, and no MCP tool reads the job architecture itself (D13).
- **Service and routes.** `src/lib/job-architecture.ts` (`jobArchitectureFor`, `getJobArchitecture`, `requireJobTitle`) behind the session-only routes under `/api/v1/job-architecture`. The draft is read and returned only to a caller who may write it (`mayWriteConfig` in `src/lib/config-store.ts`).

### Workspace person

Migration `0043_workspace_person.sql` (job 076, Release 2 item ADM-08, architecture §14.3 and §14.14, decisions D1, D20 and D29, TST-005) lets company owners and company admins holding `people` open one person of the workspace, for the Admin portal's user detail page. They see that person's profile, teams and roles in this workspace, company authority, two-step flag, signed-in device count and configuration and access-change events by ids, codes and names only; company authority never opens another team's data. No table, policy, trigger or other function changes, and the storage schema marker goes to 21.

- **`tenant_context.workspace_person(target_user_id text)`.** Owner-owned, `SECURITY DEFINER`, `STABLE`, with `search_path = pg_catalog, pg_temp`, schema-qualified names and `REVOKE ALL ... FROM PUBLIC`. It reads the context only from the verified row (`pid = pg_backend_pid()`, `xid = pg_current_xact_id_if_assigned()`, `expires_at > clock_timestamp()`, `auth_type = 'session'`) and raises `42501` unless that row exists, its `workspace_id` is set and its derived `company_level` is `owner`, or `admin` with `people` in `company_areas`, exactly as `workspace_people`: company admins without `people`, team owners and admins without company authority, recruiters, viewers and every token or OAuth context are refused. A null or empty id, or one longer than 128 characters, raises `22023`. It returns no row when the target has no `auth.member` row in a team mapped to the context's workspace, so an unknown id and a person only in another workspace look the same. Otherwise it returns one row `(user_id, name, email, last_sign_in, two_step, signed_in_devices, teams, company_level, company_areas, plan_access, authority_suspended, authority_since, events)`:
  - the user id, name and email, the start of the newest `auth.session` row (null when none is stored), `two_factor_enabled`, and the number of the target's `auth.session` rows with `expires_at > clock_timestamp()`;
  - `teams`, a JSON array ordered by team name then slug of `{team, slug, teamRole, configuredRole}` for the person's memberships in this workspace's teams only, the configured role computed as in `workspace_people`;
  - the level, areas, plan access, whether `suspended_at` is set and `granted_at` of the target's `app.workspace_admins` row in the context's workspace, all null when there is none;
  - `events`, at most 50 `app.activity` rows of teams mapped to the context's workspace, newest first by `(created_at, id)`: `config` rows whose actor is the target and whose `workspaceId` is the workspace, other teams' `task-board` rows left out as `config_history` leaves them out; `role.assigned` and `role.cleared` rows whose `affectedUserId` is the target and `scope.home_units_changed` rows whose `affectedUserIds` contain the target, both with the workspace id check; and `workspace_authority.changed` and `two_step.reset` rows whose `targetUserId` is the target, which carry no workspace id and are bound through `app.workspace_teams`. Each element has only `occurredAt`, `action`, `actorId`, `actorName` (`auth."user".name` or null), `objectType` and `objectKey` (configuration rows only) and `roleName` (role rows only, the name in the role version the row names, as `role_assignment_changes` computes it).
    It never returns a team id, record, candidate, upload, storage figure, token, session id, IP address, user agent, two-step secret, change summary or metadata body, unit, position or employee id, nor any team, authority or event of another workspace: a person who is also in another workspace's team appears with this workspace's teams, authority and events only. The role template grants `EXECUTE` to the data role only (the identity role and PUBLIC get nothing), so the data role may now execute thirty-eight helpers (`dataRoleHelpers`, listed after `workspace_people`).
- **Service.** `getWorkspacePerson` in `src/lib/admin-users.ts`, behind the session-only `GET /api/v1/admin/users/[user]` (`runApi` with `humanOnly`, no query parameters, the id 1 to 128 characters), shares `listWorkspacePeople`'s wrapper: inside one `withTeam` it refuses anyone `authorize()` refuses for the `people` area (403 `people_forbidden`, as is a `42501` from the helper), calls the helper, and answers no row with 404 `user_not_found`. It returns the row in camelCase with ISO dates and `status: "active"`.
- **Invite to teams.** The Users page's several-team invitation adds no route, helper or grant: it sends one ordinary Better Auth invitation per chosen team from the browser, and Better Auth's organization plugin, the `before` hook and `validateInvitationRole` refuse every team where the caller is not owner or admin, as for Team & access.

## Preview-first migration and verification

1. Before provisioning, inspect the exact target Vercel project, environment, Neon project/branch/database identifiers, current data and role memberships, migration ledger, ownership, default privileges, grants and backup/recovery requirements without revealing credentials. Confirm Preview and Production are distinct and do not automatically copy real data. Stop if either is unexpected or nonempty; do not alter unrelated roles or databases.
2. Review the implementation and new migrations before execution. Use the dedicated Preview database's direct non-pooler migration-owner connection; the existing migration script uses a session advisory lock. Apply only the reviewed, explicit grants of [postgres-split-runtime-roles.sql](../infrastructure/postgres-split-runtime-roles.sql) to the intended database. The role names `recruitmentos_data` and `recruitmentos_identity` are the same in each environment's separate database; each environment has distinct credentials, and the connection marker tells the databases apart. Configure separate secret connections securely in the matching Vercel environment only after approval and verification. Keep the owner connection out of deployed runtime settings. Review migration `0004_protect_initial_admin_claim.sql`: it removes marker-write grants from every nonowner grantee, including any maintenance roles in the targeted database.
3. Use two or more independent connections and fictional users, teams and CVs. Verify initial-admin setup, verification and interrupted recovery; email/password sign-in, reset and sign-out; OAuth behavior when configured; team creation, invitations, acceptance, owner protections and membership removal; token create/list/authenticate/rate-limit/revoke, concurrent token caps and atomic audit. Test that rejected writes and failed audit roll back together, while rate-limit counters retain their intended commits.
4. Under the actual restricted data role, try direct and inherited grants, `SET ROLE`, writable identity views/functions, `PUBLIC` and default privileges, session/token/member/account mutation and the forged-token signer-oracle scenario. Assert denial. Attempt arbitrary team/user GUCs, guessed tenant and candidate IDs, invalid/expired/replayed/changed-field assertions, read-only or revoked tokens, concurrent revocation, quota oversubscription, cross-tenant reads/writes, private activity and forged audit. Verify all are denied at the intended boundary with independent connections. Check identity role cannot read candidate/CV content.
5. Run synthetic private Blob tests only after the trusted boundary and durable accounting are implemented: replay, duplicate/concurrent PUT, exact path/type/size and no-overwrite, late in-flight completion, crash/retry and retained charges, cleanup/reconciliation, changed or missing objects, per-slice reauthorization and 10 MiB assembly. Confirm provider guarantees with current documentation or provider support; tests alone cannot prove undocumented behavior. Job 030 enabled Blob in code after the owner's live run of 7 November 2026 ([blob-security-design.md](blob-security-design.md#live-provider-verification)); independent review of these controls, limits and rollback procedures and the hosted Preview verification are still required before real CV data.
6. Review preview evidence and effective privileges, then apply the equivalent reviewed process separately to Production only when its environment is configured and the existing deployment authorization applies. Never reuse Preview credentials, data, signing keys, storage or operator connection. Live verification, actual provider behavior and a protected deployment access check remain open.
