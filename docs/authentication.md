# Authentication and team setup

> **Hosted sign-in opens only behind the readiness checks below, and release still needs the owner's decision.** Code no longer blocks hosted sign-in outright; it stays unavailable unless every condition in [Hosted sign-in readiness](#hosted-sign-in-readiness) holds. Live Vercel behaviour, Resend delivery and HTTPS cookies on a real deployment are unverified. See [identity-boundary-plan.md](identity-boundary-plan.md) for the remaining verification.

RecruitmentOS uses Better Auth with database-backed sessions, verified email/password sign-in, and team invitations. A team is a Better Auth organization. Candidate data is protected by additional live membership and permission checks on every request.

## Configuration

Set these server-only values in the deployment environment:

| Variable                | Purpose                                                                                                         |
| ----------------------- | --------------------------------------------------------------------------------------------------------------- |
| `BETTER_AUTH_URL`       | Exact HTTPS application origin, with no path. Local development accepts localhost/127.0.0.1 HTTP.               |
| `BETTER_AUTH_SECRET`    | Random secret of at least 32 characters. Keep stable across deployments.                                        |
| `DATABASE_URL`          | Runtime PostgreSQL connection, using the separate restricted runtime role described in deployment instructions. |
| `IDENTITY_DATABASE_URL` | Separate restricted identity connection to the same database; the role design is not yet deployment-ready.      |
| `RESEND_API_KEY`        | Transactional email delivery credential.                                                                        |
| `EMAIL_FROM`            | Verified sender, for example `RecruitmentOS <recruitment@example.org>`.                                         |
| `BOOTSTRAP_OWNER_EMAIL` | Email allowed to create the first administrator account without an invitation. It still must be verified.       |
| `BOOTSTRAP_SETUP_TOKEN` | Random, secret base64url token generated from at least 32 random bytes, unique to each environment.             |
| `ALLOW_PUBLIC_SIGNUP`   | Default false. Set exactly `true` only to intentionally allow public account registration.                      |

The public website remains accessible when configuration is incomplete. Sign-in pages show setup-required state. Private operations fail closed; the app never substitutes fake production users or a local database.

## Hosted sign-in readiness

A process is hosted when `NODE_ENV=production` or `VERCEL` is set. `getAuthOptions()` in `src/lib/auth.ts` reports hosted sign-in configured only when all of these hold; otherwise sign-in pages show setup-required, `getAuth()` and the auth route return 503 `AUTH_NOT_CONFIGURED`, and API tokens are refused. Which condition failed is never shown or logged.

- **H1:** `NODE_ENV=production` and `VERCEL=1`. A hosted process outside the Vercel production runtime (self-hosted, `vercel dev`) stays unavailable.
- **H2:** `BETTER_AUTH_URL` is an `https:` URL that is exactly its origin (an optional trailing `/` only; no path, query, fragment or credentials). Plain `http:` is refused when hosted, including localhost.
- **H3:** `BETTER_AUTH_SECRET` is usable: at least 32 characters, no whitespace, not one repeated character and not a placeholder.
- **H4:** `DATABASE_URL` and `IDENTITY_DATABASE_URL` are both set and pass `prepareConnectionTargets()`: the same host, port and database, a username and password in each, at most a single `sslmode=require|verify-full` parameter, and no non-empty `PGOPTIONS`.
- **H5:** `DATABASE_MODE` is not `pglite` and `ALLOW_LOCAL_DB` is not `true`.
- **H6:** `DEV_MAIL_MODE` is not `console` and `DEV_SEED_PASSWORD` is unset or empty.
- **H7:** `TENANT_CONTEXT_SIGNING_KEY` is canonical base64url of at least 32 bytes.
- **H8:** `RESEND_API_KEY` and `EMAIL_FROM` are both set. Console mail never counts when hosted.
- **H9:** the check reads only the environment: it contacts no service and opens no pool. H4 to H7 reuse `prepareDbPairTargets()` in `src/db/index.ts`, the same synchronous refusals `createDbPair()` runs before it creates a pool. The connection-time role, marker, boundary and storage-schema checks still run at first database use and still fail closed with 503.

`ALLOW_UNSAFE_TENANT_ISOLATION` has no effect. Local (non-hosted) readiness is unchanged: HTTP localhost/127.0.0.1, PGlite with `ALLOW_LOCAL_DB=true`, and console mail count. The bootstrap variables are not part of readiness; `/create-admin` reports separately when they are missing.

## Client IP, API tokens and the invalid-token budget

`src/lib/client-ip.ts` resolves one client IP for both Better Auth and the API. On Vercel (`VERCEL=1`) it reads only `x-vercel-forwarded-for`; elsewhere (local development and tests only, since H1 makes hosted sign-in Vercel-only) only `x-forwarded-for`. The value must be a single valid IPv4 or IPv6 address (IPv6 collapsed to /64, Better Auth's own parsing). A missing, multi-valued or invalid value means no client IP; `x-forwarded-for` on Vercel, `x-real-ip`, `forwarded` and the first value of a list are never used. Better Auth's `advanced.ipAddress.ipAddressHeaders` is set to the same header, so its database-backed auth rate limits and session addresses use the same client IP. Session addresses (`auth.session.ip_address`) are stored as Better Auth writes them; rate-limit rows never hold an address (see [Rate-limit keys and retention](#rate-limit-keys-and-retention)).

API tokens are refused with 503 `AUTH_NOT_CONFIGURED` wherever sign-in readiness is false, locally too, before any format check or identity-database access. An `Authorization` header never falls back to session auth. A malformed token is a 401 `invalid_token` without database access. The order is always readiness 503, format 401, then the database.

- **Guess budget:** only a well-formed token whose hash matches no row at all is a guess. It uses one unit of the client's budget, stored in `auth.api_rate_limits` as `api-guess:<client key>` (or `api-guess:no-client-ip`). A known hash that no longer authenticates gets the same 401 `invalid_token` and charges nothing: a revoked or expired API token, an OAuth grant presented as an API token, an unverified user or a non-member, and for `ros_oat_` tokens an expired access token, a refresh token or a wrong audience. Stale credentials, such as the expired access tokens MCP clients send before they refresh, therefore cannot lock out everyone behind a shared egress address like Claude.ai's.
- **Over budget:** after 10 unknown hashes in a 60-second window, the client key is over budget. A well-formed token whose hash matches a live, active row (a verified user who is still a member, unrevoked and unexpired, and for `ros_oat_` tokens an access token for the right audience) is still admitted, uses its 60 per minute limit and updates `last_used_at`: tokens carry 256 random bits, so admission tells a guesser nothing usable, and a shared egress address (Claude.ai's, ChatGPT's or an office NAT) must not lock out its valid tokens (job 031, SEC-04). Every other token from that key (unknown, revoked, expired, wrong kind or wrong audience) gets 429 `token_guess_rate_limited` with `Retry-After: 60`, and the count does not grow past its current value. Under budget, responses are unchanged: 401 `invalid_token`, and only unknown hashes are charged. The check holds the budget row lock in the identity transaction, and refused attempts commit before the error is thrown.
- **No in-process pre-check:** recognising a live token needs the lookup, so the per-instance map that refused over-budget clients before any database access is gone. Each request from an over-budget address costs one indexed identity lookup; the database budget and the per-token 60 per minute limit remain the throttle.

## Rate-limit keys and retention

- **Keyed hashes:** no rate-limit row stores a client address. `rateLimitClientKey()` in `src/lib/client-ip.ts` returns the base64url HMAC-SHA256 of the address under a key derived from `BETTER_AUTH_SECRET` with the fixed label `recruitmentos:rate-limit-key:v1`, or the literal `no-client-ip`. The `auth.api_rate_limits` keys are `api-guess:<client key>`, `api-token:<token id>`, `oauth-register:<client key>`, `oauth-token:<client key>`, `oauth-token:<client key>:<client_id>` and `sign-in-email:<keyed hash of the trimmed, lower-case email>` ([Per-email sign-in backoff](#per-email-sign-in-backoff)); no key holds an email address. Rotating the secret only resets the counters.
- **Better Auth limiter:** `createAuth()` passes a `rateLimit.customStorage` instead of `storage: "database"`, with the same 60-second window, default maximum of 100 and per-path rules (per client and minute: sign-in 10, sign-up 5, password reset 3, verification resend 3). It keeps Better Auth's semantics in one atomic upsert on `auth.rate_limit`: allowed while the count is below the maximum within the window since the last allowed request, reset to 1 once the window has passed, and on refusal a retry-after of the seconds until the window frees. A refused row is marked at maximum + 1 and its window is unchanged. The key is stored only as `ba:` plus the same keyed hash of Better Auth's `<address>|<path>` key under the Better Auth secret.
- **Retention:** `purgeExpiredAuthRows()` in `src/lib/auth-purge.ts` deletes at most 500 rows per table, oldest first: `auth.api_rate_limits` rows untouched for 15 minutes (API windows last 60 seconds and the per-email sign-in backoff resets after 15 quiet minutes); `auth.rate_limit` rows untouched for 10 minutes (every Better Auth window is at most 60 seconds); `auth.oauth_codes` and `auth.oauth_tokens` one day after they expire, so a replayed used code or refresh token still revokes its grant until then; and `auth.oauth_clients` older than a day that no grant references. Rows another transaction has locked are skipped (`FOR UPDATE SKIP LOCKED`), except clients: `FOR UPDATE` needs `UPDATE`, which the identity role does not hold on `auth.oauth_clients`, so the client `DELETE` takes its row locks itself. Grants and revoked tokens in `auth.api_tokens` are never purged; they stay visible in Settings. Older rows that still hold raw addresses go the same way once their window has passed.
- **When it runs:** there is no scheduler. Each server instance runs the purge at most once a minute, after the main transaction of a request that uses a rate-limit window (API and OAuth token authentication, registration, the token endpoint and the Better Auth limiter), in two transactions of its own under the database deadlines: rate-limit rows first, then OAuth rows. A failure never changes the response, including `42501` where the role template has not been re-applied for the OAuth `DELETE` grants. It logs one line, `auth_purge_failed category=<class>[ sqlstate=<SQLSTATE>]`, and the rate-limit purge still commits. After a quiet period, rows stay until the next such request.

## Two-step sign-in

Better Auth's built-in `twoFactor` plugin (`createAuth()` in `src/lib/auth.ts`, and `twoFactorClient` in `src/lib/auth-client.ts` without its automatic redirect) adds an authenticator-app code (TOTP: issuer `RecruitmentOS`, 6 digits, 30 seconds) and 10 one-time backup codes to email and password sign-in. There is no SMS or email code. The plugin stores the secret and the backup codes encrypted with `BETTER_AUTH_SECRET` in `auth.two_factor` (migration `0022_two_step_sign_in.sql`) and sets `auth."user".two_factor_enabled` only after the first code is confirmed.

- **Who must use it:** a user who has two-step sign-in off and is `owner` or `admin` in any team, or a company owner or company admin with an unsuspended `app.workspace_admins` row (ADM-16, IAM-034), is "setup-required" (`twoStepSetupRequired(twoFactorEnabled, roles, companyAuthority)` in `src/lib/auth-policy.ts`). The check uses live values on every cookie-session request, never a cached one. `/app` pages redirect to `/two-step-setup?next=/app` (`getWorkspaceContext()`, from the memberships it already loads). API routes answer 403 `two_step_setup_required` ("Set up two-step sign-in to continue. Owners and admins must use it.") from `requirePrincipal`, which now reads all of the user's memberships in its one query, so the gate adds no round trip. Better Auth's `hooks.before` refuses every endpoint called with that user's session with the same code and message, except `/get-session`, `/sign-out`, `/two-factor/enable` and `/two-factor/verify-totp`; requests without a session cookie skip the check. `/oauth/authorize` sends a setup-required user to setup and back. Promoting a member to owner or admin gates them from their next request. For recruiters and viewers without company authority it is optional, in Account settings.
- **How company authority is read:** the identity role cannot read `app.workspace_admins`, so `companyAuthorityHeld` in `src/lib/two-step.ts`, shared by all five gates (`hooks.before`, `requirePrincipal`, `getWorkspaceContext()`, `/two-step-setup` and `/oauth/authorize`), installs a session context for one of the user's teams on the **identity pool** (`withDeadlinesAndSnapshot` and `tenant_context.install`, as the owner reset does) and reads the `companyLevel` it derives, which ignores suspended rows. It runs only when two-step is off, no team role already requires it and the user has a membership; one workspace per environment, so any team gives the same answer. No grant, function or table was added. Its cost is one extra identity transaction (two statements) per gated request, only for a member with two-step off and no owner or admin team role; users with two-step on, and team owners and admins without it, take the same path as before, so the round-trip counts (6, 11 and 15) are unchanged. A lookup error fails the request; it never counts as "not required". Existing company owners and admins without two-step on an upgraded database keep their row and are gated at their next request. The helper `tenant_context.set_workspace_authority` also refuses to grant a level to anyone without two-step (`RQ017`, 409 `authority_two_step_required`, migration `0043`).
- **Setup and challenge:** `/two-step-setup` asks for the password (`/two-factor/enable`), shows the QR code of the `otpauth://` URI (drawn as SVG in the browser by the pinned `uqr` encoder; no image service) and the base32 key in groups of four, confirms one code (`/two-factor/verify-totp`) and then shows the backup codes once. The URI, key and codes stay in component state only. Turning it on deletes every other session of the user (`databaseHooks.user.update`), so no password-only session survives; only the session the code created remains. At sign-in, a correct password returns `twoFactorRedirect` and a 10-minute challenge cookie instead of a session, and the sign-in form continues on `/two-step`, which takes an authenticator code or a backup code.
- **Limits:** the plugin's defaults apply: 5 code attempts per challenge, then "Sign in again."; after 10 consecutive failed codes the account is locked for 15 minutes; and 3 requests per 10 seconds per client on `/two-factor/*`.
- **The key is shown once:** the plugin's `/two-factor/get-totp-uri`, which would return the stored secret again, is refused for everyone with 403 `two_step_key_hidden`. To move to a new authenticator, turn two-step sign-in off and on again.
- **Backup codes:** each works once. Account settings → Two-step sign-in creates 10 new ones with the password (`/two-factor/generate-backup-codes`); the old ones stop working.
- **Trusted device:** "Trust this device for 30 days" stores a `trust-device-*` row in `auth.verification` and a signed cookie. A trusted device skips the code for at most 30 days after the code was last entered on it: a trusted sign-in may re-issue the cookie, but `databaseHooks.verification.create` clamps the new row to the expiry of the row it replaces, so trust never slides. Turning two-step off or creating new backup codes deletes every `trust-device-*` row of the user.
- **Turning it off:** in Account settings, with the password and a confirmation (`/two-factor/disable`). Owners and admins are sent straight back to setup; turning it off and on again is the way to move to a new authenticator.
- **Sessions only from two-step paths:** for a user with two-step on, `databaseHooks.session.create` allows a session only from `/sign-in/email` (challenged, or a valid trusted device), `/two-factor/verify-totp`, `/two-factor/verify-backup-code` and `/change-password`. Every other path, including the Google and Microsoft callbacks (Better Auth 1.7.18 does not challenge social sign-in), is refused with "Sign in with your email, password and authenticator code." (code `two_step_sign_in_required`). With that and the session deletion above, "a session that has passed two-step sign-in" is exactly "the session's user has two-step on"; there is no session column.
- **Tokens and app connections:** `createToken()` and `createOAuthGrant()` refuse with 403 `two_step_required` ("Turn on two-step sign-in in your profile before creating API tokens or connecting apps.") when the user row they already lock has two-step off, for every role. Settings → API tokens shows that notice and a "Turn on two-step sign-in" link instead of the form, and `/oauth/authorize` shows "Turn on two-step sign-in first". Listing, revoking and denying stay available. Bearer API tokens, MCP OAuth access and refresh tokens and `/oauth/token` do not check two-step state, so existing tokens keep working.
- **Owner reset:** an owner of the active team who also owns every other team the member belongs to can reset that member's two-step sign-in in Team settings (`POST /api/v1/teams/two-step-reset`, session only). In one identity transaction the owner-run helper `tenant_context.reset_two_step(text)` (migration `0023_two_step_reset.sql`) requires a verified session context of an owner with two-step on, deletes the member's `auth.two_factor` row, turns the flag off, deletes all their sessions, trusted devices and pending challenges, and writes one `account-security` activity row `two_step.reset` with `{"targetUserId"}`. An admin gets 403 `owner_required`, your own account 400 `cannot_reset_self`, a non-member 404 `member_not_found`, a member who also belongs to a team you do not own 409 `member_in_other_team` (the helper refuses the same case with `RQ004`) and nothing to reset 409 `two_step_not_enabled`. The reset is account-wide, so it never removes a second factor that protects a team the owner does not own; it is audited in the owner's active team. Such a member recovers with a backup code or the recovery script.
- **Recovery script:** the last owner without an authenticator or backup codes is recovered by the database owner with `npm run two-step:reset -- --email <address> --confirm` ([recovery-runbook.md](recovery-runbook.md#two-step-sign-in-recovery)). It uses PGlite only when `DATABASE_MODE=pglite` and `ALLOW_LOCAL_DB=true`, otherwise `MIGRATION_DATABASE_URL` with `verify-full`, performs the same deletions and update in one owner transaction and writes one `two_step.reset` row per team ("Two-step sign-in reset by the database owner", `{"targetUserId","method":"owner-script"}`). It prints "Two-step sign-in was reset for 1 account." or "No account matched." (exit 1) and never a secret.
- **Nothing secret in logs:** no TOTP secret, `otpauth` URI, code or backup code appears in logs, errors or API responses other than the one enable or new-codes response to the user. Better Auth's single-line logger is unchanged.

### Re-authentication for sensitive admin changes

ADM-06 (job 070) adds a fresh-session rule against threat T-R2-30 (architecture §14.14 and §14.15). It adds no policy page, sidebar entry or setting (D29).

- **The rule:** a change is accepted only from a browser session younger than Better Auth's `freshAge`, 15 minutes, measured from the session's creation (`auth.session.created_at`). `SESSION_FRESH_AGE_SECONDS` (900) in `src/lib/auth-policy.ts` sets both `session.freshAge` in `createAuth()` and the app's check. `requireFreshSession(principal)` in `src/lib/fresh-session.ts` refuses when `now - createdAt >= 900 s`, Better Auth's own comparison, and when the start time is missing or invalid. It runs no database statement: `requirePrincipal` copies `identity.session.createdAt` from the session it already verified into `Principal.sessionCreatedAt`, on the cookie path only. Token and MCP principals never carry it.
- **The seven guarded changes**, all session only:
  - configured role publish, `POST /api/v1/roles/{id}/publish`;
  - configured role assignment and clearing, `POST /api/v1/teams/member-roles`;
  - company authority grant, change, removal or restore, `POST /api/v1/company-authority` (the only caller of `tenant_context.set_workspace_authority`);
  - a member's two-step sign-in reset, `POST /api/v1/teams/two-step-reset`;
  - deactivating or reactivating a person, `PUT /api/v1/admin/users/{user}/status` (ADM-09);
  - signing a person out everywhere, `POST /api/v1/admin/users/{user}/sign-out` (ADM-09);
  - clearing a person's sign-in lockout, `POST /api/v1/admin/users/{user}/clear-lockout` (ADM-09).
- **The refusal:** a stale session gets 403 `{"error":{"code":"SESSION_NOT_FRESH","message":"This change needs a recent sign-in. Confirm your password and two-step code, then try again.","correlationId":"…"}}`. `runApi` checks it after `requirePrincipal` and before the handler, so the body is not read and no service or database transaction runs. The code is upper case, like Better Auth's own `SESSION_NOT_FRESH`.
- **Tokens, MCP and reads:** a Bearer token is refused with 403 `session_required` before any token is looked at, as before, and MCP has no tool for these changes. The check adds to `authorize()`, the service checks and the `tenant_context` helpers and replaces none of them; a caller without permission and with a stale session sees the dialog first and is then refused as before. Viewing never asks: no `GET` route, including `GET /api/v1/company-authority`, `GET /api/v1/teams/member-roles` and `GET /api/v1/roles`, and no Admin portal or Team & access page checks freshness.
- **The dialog:** on that refusal the page opens **Confirm it's you** (`src/components/settings/fresh-session-dialog.tsx`). It asks for the password and, when the user has two-step sign-in on, the current authenticator code, both before any call. It then uses Better Auth's own endpoints: `signIn.email`; when that answers `twoFactorRedirect`, `twoFactor.verifyTotp({ code, trustDevice: false })` against the challenge; then `organization.setActive` with the page's team, because a new session has no active team. No new provider or route is involved and no email is sent. On success the same request is sent once more; the action's own confirmation is not asked again. A wrong password ("That password is not correct.") leaves the cookies as they were. A wrong code ("That code is not correct.") keeps the dialog open, and the next **Confirm** sends only the code against the pending challenge. An ended challenge shows "Sign in again." with a sign-in link, a lock "Too many incorrect codes. Try again in 15 minutes." and a 429 the server's message. None of these retries the change.
- **Trusted devices:** the code is checked only when Better Auth challenges for it. On a device trusted at sign-in, `signIn.email` creates the fresh session from the password alone and the code field goes unused, as at sign-in. The client cannot see the HttpOnly trust cookie, and a client-side code check after the session exists would not be a control; asking for the code every time would need a server change.
- **Cancelling during a challenge:** `signIn.email` with a correct password for a challenged user deletes the new session and expires the browser's session cookie before the code is checked. Cancelling after the password was accepted but before a code was therefore leaves the browser signed out, and the page says "You are signed out on this device. Sign in again to make this change." with a sign-in link. Asking for both fields before the first call keeps that window to the wrong-code case.
- **The previous session** stays in place after re-authentication. It ages out, or the user signs it out from the device list, as after any repeat sign-in.
- **Reuse:** later items that name this check (granting groups, domain, mail and anonymisation) pass `{ humanOnly: true, freshSession: true }` to `runApi` and wrap their page request with `withFreshSession` from `useFreshSession()`, as deactivation does.

### Deactivation, sign out everywhere and clear lockout

ADM-09 (job 082, migration `0047_user_deactivation.sql`) lets a company owner, or a company admin holding the `people` area, act on one person for the whole company from the user detail page's **Security** tab. It answers threat T-R2-32 (architecture §14.3 and §14.15). Nothing of the person is deleted.

- **Who may do what:** a company owner on anyone else; a company admin with `people` only on a person without company authority (no `app.workspace_admins` row in the workspace, suspended or not). Nobody acts on their own account (400 `cannot_change_self`, "You cannot change your own account here."). A company admin on a company owner or admin gets 403 `company_owner_required` ("Only a company owner can change a company owner or admin."); anyone else, Bearer tokens included, gets 403 `people_forbidden` or `session_required`. A person in no team of the company gets 404 `user_not_found`. Every change needs a recent sign-in (above).
- **Deactivate and reactivate:** `PUT /api/v1/admin/users/{user}/status` with `{"active": false}` or `{"active": true}` calls the owner-run helper `tenant_context.set_user_active` on the data pool. It locks the workspace row, rechecks the caller's authority (unsuspended, not deactivated), refuses the last active company owner (409 `last_company_owner`, "The last active company owner cannot be deactivated. Make someone else a company owner first.") and sets or clears `deactivated_at` and `deactivated_by` in `app.workspace_users`. A repeat returns `changed: false` and writes nothing. Memberships, team roles, configured roles, record assignments, company authority, API tokens, OAuth grants, sessions and history stay as they were, so reactivating restores exactly the access the person had.
- **Every request refused:** `tenant_context.install` refuses a context for a deactivated actor with `42501` and the message `Account deactivated`, in the statement it already runs. `installTenantContext` maps it to 403 `account_deactivated` ("Your account has been deactivated. Ask a company owner or admin to reactivate it."); every other refusal stays `tenant_context_denied`. Sessions, API tokens and MCP OAuth grants are therefore refused on every route and on `/api/mcp`, from the next transaction after the change commits. Their sessions are kept, so Better Auth's `hooks.before` also checks every gated endpoint called with a session cookie (every path except `/get-session`, `/sign-out`, `/two-factor/enable` and `/two-factor/verify-totp`): it asks `install` for the session's user, whatever their team role or two-step state, and refuses a deactivated person with 403 `account_deactivated`. So a deactivated team owner or admin cannot invite, change roles, remove members, create a team or change their password with a surviving session; approving an app connection or creating an API token is refused by `install`, as every app route is. This adds one identity transaction to each such Better Auth call; the app's API routes and their round-trip counts are unchanged.
- **Sign-in refused:** `databaseHooks.session.create.before` asks `tenant_context.install` for a session context in one of the user's teams on the identity pool (`accountDeactivated` in `src/lib/user-account.ts`, the `companyAuthorityHeld` approach) and refuses with 403 `account_deactivated`, "This account has been deactivated. Ask a company owner or admin to reactivate it.". It runs after Better Auth has checked the password or code, on every path that creates a session (email and password, two-step verify and social callbacks), so a wrong password still gets the usual error and never reveals the state. Any other error fails the request; a user with no membership is not checked. A password change creates its new session inside Better Auth's own transaction, where no second transaction may open (one connection on PGlite), so the session hook relies on the `hooks.before` check of the session's user above, and fails the request when that check did not run. The per-email backoff row is not cleared by this refusal. Password reset by email (IAM-091) is unchanged.
- **Sign out everywhere:** `POST /api/v1/admin/users/{user}/sign-out` runs one identity transaction under the caller's session context: the `people` check, then `tenant_context.user_account_action(<id>, 'sign_out')`, which deletes every `auth.session` row of the person. API tokens, OAuth grants and trusted devices are not touched (Reset two-step sign-in forgets trusted devices).
- **Clear lockout:** `POST /api/v1/admin/users/{user}/clear-lockout` runs the same transaction with `'clear_lockout'`, then deletes the person's per-email backoff row (below), whose keyed hash only the app can compute (`signInBackoffKey` in `src/lib/client-ip.ts`). It shows nothing about whether a lockout was active.
- **Audit:** each change writes exactly one `app.activity` row of kind `user-account` (`user.deactivated`, `user.reactivated`, `user.signed_out_everywhere` or `user.lockout_cleared`) in the caller's active team, with `metadata` `{"targetUserId": "<id>"}` only and a summary without names. Sign out everywhere and Clear lockout always write their row. Only the owner-run helpers can insert these rows, the activity feed shows them only to sessions with company authority, and the person's **Activity** tab lists them.

## Per-email sign-in backoff

Every `/sign-in/email` attempt is charged to its email address before the password is checked, in one atomic upsert on `auth.api_rate_limits` under `sign-in-email:<keyed hash>`. `window_start` is the time of the last counted attempt and `count` the attempts since the last success. Attempts 1 to 5 proceed at once; after the 5th, 6th, 7th and 8th failure the next attempt waits 1, 2, 4 and 8 minutes, and after 9 or more 15 minutes. A refused attempt gets 429 with `Retry-After: <seconds>` and "Too many sign-in attempts. Wait a few minutes and try again.", is not checked and does not change the count; concurrent attempts cannot all pass, because the upsert only updates while the attempt is allowed. A correct password (a 200, including a two-step challenge) deletes the row, and 15 quiet minutes start the count again. Existing and unknown addresses behave identically, and changing client addresses does not reset the count. The per-IP limits above are unchanged. The trade-off: someone who knows an address can delay its owner's password sign-in by at most 15 minutes at a time. A company owner, or a company admin with `people`, can end the wait at once with **Clear sign-in lockout** on the person's Security tab, which deletes the row (ADM-09, above).

## OAuth authorization server for MCP clients

RecruitmentOS includes a minimal OAuth 2.1 authorization server, in `src/lib/oauth.ts`, only so that AI assistants such as Claude.ai and ChatGPT can connect to `/api/mcp` ([mcp.md](mcp.md)). Better Auth 1.7.18 ships no MCP or OIDC provider plugin, and a separate provider package would need its own token tables and the same glue code, so the server is in-repo. It follows the same readiness as sign-in: every endpoint below returns 503 `AUTH_NOT_CONFIGURED` while `getAuthOptions().configured` is false. Every URL comes from `BETTER_AUTH_URL`, never from `Host` or forwarding headers.

- **Endpoints:** `/.well-known/oauth-protected-resource/api/mcp` and `/.well-known/oauth-protected-resource` (RFC 9728), `/.well-known/oauth-authorization-server` (RFC 8414), `POST /oauth/register` (RFC 7591), `GET /oauth/authorize` (the consent page), `POST /api/oauth/consent` (the page's cookie-only decision) and `POST /oauth/token`. `issuer()` (the origin) gives the metadata `issuer`, the protected-resource `authorization_servers` entry and the `iss` response parameter, so all three are the same string; the metadata advertises `authorization_response_iss_parameter_supported: true` (RFC 9207), `code_challenge_methods_supported: ["S256"]` and `token_endpoint_auth_methods_supported: ["none"]`.
- **PKCE and clients:** authorization code with S256 PKCE only (`plain` or a missing method is refused); public clients only, with no secret, registered only through dynamic client registration (no Client ID Metadata Documents, so the server fetches no remote URL). `redirect_uri` must string-equal a registered URI that still passes the registration allowlist, so clients registered before it are refused. `resource` (RFC 8707), when sent at authorize or with either token grant, must be exactly `<origin>/api/mcp` (`invalid_target`); a missing `resource` is accepted. Access and refresh tokens are stored with audience `<origin>/api/mcp`; `/api/mcp` checks the access-token audience and the refresh grant only finds refresh tokens with that audience (`invalid_grant` otherwise). `/oauth/authorize` never redirects to a client: an unknown client, a refused redirect URI and every later problem (repeated parameters, a `state` over 1000 characters, `response_type`, PKCE, `resource`, `scope`) show the "This connection cannot continue" page with the OAuth error code, signed in or not.
- **Registration limits:** 5 attempts per minute per client address (`oauth-register:<client key>`, every attempt counts; there is no client identity before registration). While 1,000 or more registered clients have no grant, registration returns 429 `rate_limited` ("Too many client registrations. Try again later.") and stores nothing; with the one-day purge of unapproved clients this bounds how many can pile up, at the cost of refusing registrations while the cap is full. Then a 16 384-byte JSON body, 1 to 5 redirect URIs, each exactly `https://claude.ai/api/mcp/auth_callback`, `https://claude.com/api/mcp/auth_callback` or `https://chatgpt.com/connector_platform_oauth_redirect` (no normalisation; ChatGPT's per-connection `https://chatgpt.com/connector/oauth/<id>` is refused), or `http:` loopback (`127.0.0.1`, `[::1]`, `localhost`, any port and path) without fragments or credentials; any other URI gives 400 `invalid_redirect_uri` and stores no client. The client name is cleaned by `cleanClientName()` (`src/lib/client-name.ts`): control, format (bidi overrides, zero-width), private-use, surrogate and unassigned characters and invisible fillers and variation selectors are removed, runs of Unicode spaces and line or paragraph separators become one space, and the result is trimmed. It may then be at most 100 characters; an empty result becomes `Unnamed app`. Registration creates no grant, code or token.
- **Consent:** with no session, `/oauth/authorize` sends the browser to `/sign-in?next=…`, which returns to the same request after sign-in (`safeNext` allows `/oauth/authorize`). An unverified account goes to `/verify-email`; a user with no team sees "Create or join a team first" with a link to team settings when they may create a team (the initial administrator or an owner, `canCreateTeam`), and otherwise "Join a team first", which asks them to accept the email invitation from their team owner and links only to their workspace. The page names the client (as supplied by the app, cleaned again so older clients show clean names too), the return host, a team select and each requested scope, described by what the MCP tools do (`mcpScopeDescriptions`; the REST token form keeps `scopeDescriptions`). Scopes the selected team's role does not allow are shown as "Not available to your role"; the user can untick but never add scopes. Approve and Deny call `POST /api/oauth/consent` with `fetch` and then navigate, because the CSP's `form-action 'self'` would block a form redirect to the client. The server re-checks every authorize rule and the live role; Deny writes nothing. Approve and Deny are the only ways the browser reaches the client's redirect URI: approve returns `code`, `state` (when sent) and `iss`, deny returns `error=access_denied`, `state` (when sent) and `iss`.
- **Lifetimes:** an approval creates a grant row in `auth.api_tokens` that expires in 120 seconds with its one-time code; redeeming the code extends the grant to 30 days. Access tokens (`ros_oat_…`) last at most an hour and never outlive the grant. Refresh tokens (`ros_ort_…`) rotate on every use and expire with the grant. Reusing a redeemed code or a used refresh token revokes the grant and, in the same transaction, `tenant_context.audit_grant_reuse()` writes one `token.revoked` row (actor type `token`, reason `authorization_code_reused` or `refresh_token_reused`); an already revoked grant gets no row. Every failed token request costs one unit of a budget of 10 per minute, checked before any code or token lookup. A registered `client_id` (looked up first by primary key) has its own budget per address, `oauth-token:<client key>:<client_id>`, so one misbehaving connector behind a shared egress address cannot exhaust the others'; a malformed or unregistered `client_id` uses `oauth-token:<client key>`.
- **Revocation:** grants appear in Settings → API tokens with an "OAuth app" badge; the existing `revokeToken` (own grants, or any team grant for owners and admins) stops their access and refresh tokens on the next request and writes `token.revoked`. A grant revoked here and later replayed keeps only this row.

## Local development

For explicit local development only, use `DATABASE_MODE=pglite`, `ALLOW_LOCAL_DB=true`, and an optional `PGLITE_DATA_DIR`. `DEV_MAIL_MODE=console` prints local verification/reset/invitation messages to the development terminal. Never use this with real accounts or share the terminal output. Console mail is disabled in production and whenever Vercel hosting is detected. Local and production authentication have the same verification requirements.

## First account and invitations

1. Apply all database migrations and configure the bootstrap email, a unique setup token, and mail sender. Keep the token in the deployment secret store and provide it to the intended administrator through a secure channel. Generate it locally with `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"`; never commit it or place it in a URL.
2. Open `/create-admin` and provide the exact bootstrap email, name, password and setup token. Open the verification email and sign in. The token alone does not verify the email. The first team created by this verified account gives it the owner role.
3. Open Team settings, create a team, and invite colleagues with their intended role. Only the initial administrator and owners of an existing team can create a team: `allowUserToCreateOrganization` reads the user row and owner memberships from the database through `canCreateTeam` (`src/lib/auth-policy.ts`), and everyone else gets 403 from `/api/auth/organization/create`. The settings page shows the **Create a team** form only to them; others without a team are told to accept their team owner's invitation. Users who join by public sign-up (`ALLOW_PUBLIC_SIGNUP=true`, off in Release 1) can create a team only once they own one. Invitation mail passes the team name through `cleanClientName`, so control, bidi and zero-width characters never reach the subject or body; an empty result reads "a RecruitmentOS team".
4. Each colleague creates an account using the invited email, verifies it, signs in, and accepts the invitation link. An existing verified account can accept directly.

Registration is invite-only by default. For privacy, the auth library can return a generic successful signup response even when registration is denied or the account already exists. An unsolicited attempt does not create a user or send mail. Invitations expire after 48 hours. A user can create at most five teams; a database guard enforces the cap. The final team owner cannot be removed or demoted, including simultaneous database operations.

Setup is claimed once per database in the same transaction as the initial user insert, with an advisory transaction lock and a durable claim that remains after deletion. It remains pending until the designated user verifies their email and creates a team in which they are the owner; other account registrations are blocked until then. A migration marks deployments with existing users or teams as already initialized. If delivery fails, use the verification page to resend the email for the existing account; if account creation rolled back, retry the setup. A database outage or missing setup configuration fails closed. No automatic reset is provided; an operator must investigate and explicitly handle any exceptional recovery. Preview and production require separate databases, secrets, setup tokens and email addresses where appropriate.

Roles are owner, admin, recruiter, and viewer. Only owners can grant or change ownership. Recruiter/viewer roles do not administer team memberships. Unknown or combined role strings are rejected. Personal API tokens use a separate scope policy and cannot administer authentication or teams.

### Team roles and configured roles

`member.role` (owner, admin, recruiter or viewer) is the membership ceiling: the most a member can hold in that team. Since migration `0035` (Release 2 item R2a-10) a company owner can also give a member a configured role, a published `role` configuration object of the company whose body names its membership (admin, recruiter or viewer; owner is reserved for the Owner template), scopes, pages, actions and field rules. The assignment is the member's `app.member_roles` row; a member without a row holds the built-in template of `member.role`, exactly as before.

- **Who assigns.** Only a company owner (company authority from `app.workspace_admins`, never a team role), signed in, through `POST /api/v1/teams/member-roles` (`src/lib/member-roles.ts`). Team owners and admins without company authority, including the owner of a newly created team, company admins, API tokens and OAuth grants are refused with 403 `role_assignment_forbidden` or `session_required`, and the database refuses the same writes. Team owners keep the Owner role and cannot be given a configured role (409 `team_owner_role`). Only company owners publish role versions.
- **Write order.** The `app.member_roles` row is written first. Only then, when `member.role` differs from the role's membership, the service calls Better Auth's `updateMemberRole` with the caller's own request headers, so every existing organization rule and hook applies: members are updated by team owners and admins only, and only a team owner changes ownership. If Better Auth refuses, the row stays and the response is 409 `team_role_unchanged`. Clearing a role deletes the row and leaves `member.role` unchanged.
- **The narrower wins.** If the two disagree, for example after such a refusal, `tenant_context.install` stores the asserted scopes (which never exceed `member.role`'s ceiling) intersected with the role's scopes, and the permission engine also takes the stricter of the two memberships, so a viewer membership never writes. A role that cannot be used (archived, unpublished, or without valid scopes or record scope) gives the member no access until a company owner reassigns or clears it.
- **Record scope.** Since R2a-18 (job 060) roles limited to a unit or to assigned records, including copies of the built-in hiring manager and interviewer templates, are assigned like any other; the service limits the member to the records of their org unit and below or assigned to them ([security.md](security.md#identity-and-tenancy)). A member promoted to admin by a role with admin membership sets up two-step sign-in at their next sign-in, as for any admin.

## Optional providers

Google requires `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, with callback `${BETTER_AUTH_URL}/api/auth/callback/google`. Google must report a verified email.

Microsoft requires `MICROSOFT_CLIENT_ID` and `MICROSOFT_CLIENT_SECRET`; optionally set `MICROSOFT_TENANT_ID` to restrict the tenant. Callback: `${BETTER_AUTH_URL}/api/auth/callback/microsoft`. Microsoft identity uses its provider identifier, and its email claim is not treated as proof of email ownership. New Microsoft accounts must complete local email verification before any private team action. Do not grant access based on an email domain alone.

Provider buttons appear only when their credentials are configured. Existing local accounts are never silently linked to OAuth identities by email. A signed-in user can explicitly link a provider only using the library's protected account-linking flow. OAuth callback and provider email behavior need staging checks with configured test accounts before enabling them for production use.

## Security behavior and validation

Authentication writes require the exact app Origin; OAuth callback routes retain Better Auth's state checks. Trusted origins do not include wildcard Vercel preview domains. Database session caching is disabled, so revocation does not wait for a cached cookie expiry. Password reset revokes existing sessions. A session's active-team field is a selection preference; data routes still check live membership.

Auth HTTP rate limits persist in PostgreSQL under keyed hashes ([Rate-limit keys and retention](#rate-limit-keys-and-retention)). Direct server `auth.api` calls do not receive those HTTP limits, so do not add custom unauthenticated sign-in proxy endpoints without their own throttling. API bearer tokens have a separate durable limiter.
