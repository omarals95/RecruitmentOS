# Security and data flows

RecruitmentOS is a cloud application. Its authorised service connections differ from the earlier offline desktop dashboard. This document describes implemented controls and remaining deployment checks; it is not a guarantee that no vulnerabilities exist.

## Intended connections

| Connection                                                                               | Data and purpose                                                                                                                                                                                                                                                                                                                                     |
| ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Browser → same-origin Next.js `/api/auth/*`, `/api/v1/*`, `/api/settings/*`              | Sign-in, team-scoped recruitment records, personal settings and upload tickets                                                                                                                                                                                                                                                                       |
| Vercel server → Neon PostgreSQL, TLS                                                     | Auth sessions, teams, recruitment facts, personal notes, audit records, token hashes and upload references                                                                                                                                                                                                                                           |
| Browser → configured private S3 bucket (**legacy, dormant**)                             | Only with an explicit `CV_STORAGE_PROVIDER=s3`, never in hosted environments: direct, size/type/key-constrained upload using an expiring signed form; private version-specific download                                                                                                                                                              |
| Browser → Vercel Blob API `https://vercel.com/api/blob/`                                 | Exact-path, size/type-limited private PUT only, valid for at most 5 minutes inside a 15-minute reservation                                                                                                                                                                                                                                           |
| Vercel server → Vercel Blob API                                                          | Signed-token issuance for upload tickets, private uncached reads, and head, delete and list under the team's own `teams/<team>/cvs/` prefix, always with the request's Vercel OIDC token and an explicit store id. A static read-write token is refused in hosted environments; it is used only by tests and the owner's Preview verification script |
| Vercel server → AWS STS/S3 (**legacy, dormant**)                                         | OIDC role credentials, versioning/metadata/range checks and download signatures, only for an explicit `s3` provider                                                                                                                                                                                                                                  |
| Vercel server → Resend                                                                   | Account email verification, password resets and team invitations; no CVs or recruitment records                                                                                                                                                                                                                                                      |
| Browser/server → Google or Microsoft                                                     | Only when an administrator configures that optional sign-in provider and the user chooses it                                                                                                                                                                                                                                                         |
| Administrator-run importer → chosen application origin and its signed upload destination | Only with explicit `--apply`; dry-run reads locally and reports reconciliation                                                                                                                                                                                                                                                                       |
| Browser → same-origin `/_vercel/speed-insights/*` (Vercel Speed Insights, free tier)     | Web Vitals for the signed-in app and the landing page only, with the URL and route reduced to a pattern: no query string, no fragment, and every path segment that is not a plain lowercase word replaced by `[id]`; production builds only                                                                                                          |
| AI client (for example Claude) → `/api/mcp`, `/oauth/*` and `/.well-known/oauth-*`       | The assistant calls MCP tools with an API token or a consented, short-lived OAuth access token; team-scoped, scope-limited records come back as labelled untrusted JSON ([mcp.md](mcp.md))                                                                                                                                                           |

No external AI provider, advertising library, remote font or product analytics service is integrated; Vercel Speed Insights receives only scrubbed Web Vitals, as above. API tokens and OAuth connections let an independently authorised AI client call this application; the application does not send its records to that client on its own. Next.js anonymous build telemetry is disabled by the project's command wrapper. Dependency installation contacts npm; that is a development operation, not a candidate-data flow.

**AI extraction contract.** The code for optional AI suggestions from a CV exists, but no provider is approved (D-09): `extractionProvider()` in `src/lib/ai-provider.ts` returns null, so the endpoints return 503 `ai_not_configured` and only tests plug in a fake adapter. `GET`/`POST /api/v1/extraction-consent` and `POST /api/v1/extraction-jobs` are session only (Bearer tokens get 403 `session_required`) and need `cvs:write` and `candidates:write`. Consent is per user and team, tied to a disclosure version that changes with any change to the provider, model, region, retention, training use, cost note, purpose, data sent or limits, and can be withdrawn at any time; a withdrawal stops new requests but cannot recall CVs already sent. Before anything is sent the server checks the base64 content, its size and SHA-256 against the declared file and the CV format; then, under a per-team lock, the disclosure version, consent, an unused request ID and the team budget. Only the CV bytes and MIME type reach the adapter: no file name, other records, account or team details. Limits: 3 MiB per file, 100 requests per team in 24 hours with every attempt counted, and a 30-second deadline; the adapter is never retried and a used request ID is refused. Consent decisions, job starts and outcomes are append-only `ai-extraction` activity events with the digest, size, type, provider, model, outcome and suggested field names, never the file name, CV content or an extracted value; every team member can read them in Activity. The endpoints write only those events and cannot create or change records, candidate states, uploads, bulk items or applications; suggestions reach a record only as human-reviewed values in a bulk import item.

## Identity and tenancy

- Better Auth handles password hashing, database sessions, verification and reset tokens. Registration is invitation-only unless explicitly opened; a configured bootstrap email can create the initial account. A generic successful registration response may conceal a rejected address to avoid account enumeration. Verification and a live membership are required before accessing team records.
- Two-step sign-in (P1-22, job 034, SEC-12): Better Auth's `twoFactor` plugin adds an authenticator-app code and 10 one-time backup codes, stored encrypted in `auth.two_factor`. Owners and admins in any team must use it: until they set it up, `/app` pages redirect to `/two-step-setup`, API routes answer 403 `two_step_setup_required` and every Better Auth endpoint except getting the session, signing out and the setup calls refuses their session, checked live on every request. Turning it on ends every other session of the user, and a user with it on gets a session only from the challenged password sign-in, a code, a backup code or a password change; Google and Microsoft callbacks are refused for them. New API tokens and app connections need it for every role (403 `two_step_required`); existing Bearer tokens are unaffected. A trusted device skips the code for at most 30 days after the code was last entered. An owner of every team a member belongs to can reset that member (owner-run `tenant_context.reset_two_step`, one `account-security` audit row that no runtime role can insert directly), and the database owner can recover the last owner with `npm run two-step:reset`. Every `/sign-in/email` attempt is also charged per email address under a keyed hash (5 free, then 1, 2, 4, 8 and 15 minutes), identically for unknown addresses ([authentication.md](authentication.md#two-step-sign-in)).
- Optional provider sign-in does not auto-link another account by matching an email. Microsoft email claims are not treated as an invitation or a verified local identity by themselves. Validate actual provider flows in staging.
- Every API request resolves a session or a Bearer token. An invalid Bearer header never falls back to cookie privileges. A team header must match current membership or the token's fixed team.
- `/api/mcp` accepts only Bearer credentials and never reads cookies: an API token or an OAuth access token (`ros_oat_…`) bound to the `/api/mcp` audience, which `/api/v1/*` refuses. OAuth access needs a verified team member to approve a consent page naming the client, its return host, the team and the exact scopes. Each approval is an `auth.api_tokens` grant row (with `oauth_client_id`), so it is listed and revocable in Settings, counts towards the 50-token cap, is intersected with the approver's current role on every request and passes the unchanged `tenant_context.install` token checks. Only SHA-256 hashes of codes, access and refresh tokens are stored. Dynamic client registration is the only registration method (the server fetches no client metadata URL), is rate limited, accepts only Claude's two exact callback URIs, ChatGPT's exact stable callback `https://chatgpt.com/connector_platform_oauth_redirect` or `http:` loopback redirect URIs, strips invisible characters from client names and grants nothing. `/oauth/authorize` shows an error page for every invalid request and never redirects to a client; only a signed-in member's approve or deny decision does, and both responses carry `iss` (RFC 9207), equal to the metadata issuer. A `resource` other than `/api/mcp` is refused at authorize and at the token endpoint, and refresh tokens must also carry the `/api/mcp` audience. Codes last 120 seconds, access tokens one hour, grants 30 days; a reused code or refresh token revokes the grant and writes an owner-run `token.revoked` audit row with a fixed reason. MCP tools never return the sensitive candidate fields `explicitGender` and `nationalServiceStatus`, drop evidence entries that mention them, and never match search words against them or against the imported source fields (`rawSource`, `evidence`, `sourceReviews`) that may copy them. Every MCP tool call writes an owner-run `mcp-tool` audit row (no arguments) before the tool runs, and no runtime role can insert such rows directly ([mcp.md](mcp.md)).
- Role scopes are checked on the server. Tokens cannot manage accounts, memberships or other tokens. A comment on a candidate is candidate data: without `candidates:read` it is left out of comment lists and totals and answered as not found (404, or 400 `invalid_reference` for a new comment's parent, the same as a missing record), and adding one also needs `candidates:write` (REST 403, MCP `scope_required`). Every CV read (`listCandidateCvsPage`, `listCandidateCvs`, `getCvDownload`, `getCvManifest`, `getCvChunk`) needs `candidates:read` as well as `cvs:read` and refuses with 403 `scope_required` before any storage call (job 031, SEC-11 and SEC-20). Membership removal/demotion affects subsequent requests; last-owner protection is serialized in the database.
- Business operations run in transactions that first install one HMAC-signed assertion, bound to the backend, the transaction, the database marker, the team, the actor, the auth type, the token and the scopes, and valid for at most 60 seconds. Every application transaction first sets a 10 s statement and a 20 s transaction deadline, transaction-local so a pooled connection never keeps them; a request that reaches one fails with the generic 500 `internal_error`, and a connection the server ends is logged by SQLSTATE only. An owner-controlled function verifies it and rechecks membership and token state. Row policies on every recruitment table derive team, actor and write access from that verified context and ignore settings such as `app.team_id`, so savepoint rollback, pooled-connection reuse and expired or revoked assertions do not carry access over. Explicit team predicates and composite foreign keys stay as defence in depth. Private candidate states, saved views, notification reads and private activity are limited to their own user. New activity rows must name the context's own actor and token, so audit events cannot be forged under another member. Limits: this protects against SQL on the recruitment-data role only. The application process, the signing key, the identity role and the database owner are trusted. The design is tested on local PGlite and a throwaway local PostgreSQL 18 cluster. In the owner's run on the Neon Preview database, the role template is applied, `scripts/db-role-evidence.ts` passes with zero drift, and `npm run test:live-roles` passes 27/27 through the transaction-mode pooler and 27/27 direct, with all fixtures removed. It still needs independent review (DEC-02/DEC-03) and Production verification ([identity-boundary-plan.md](identity-boundary-plan.md#signed-tenant-context)).
- Production refuses owner/superuser/BYPASSRLS runtime connections. RLS must be deployed with the separate restricted runtime role; tests exercise a nonowner role locally.
- Hosted and `NODE_ENV=production` startup has no blanket database block; it refuses with 503, and no environment variable bypasses these checks:
  - before any pool exists: `DATABASE_MODE=pglite` or `ALLOW_LOCAL_DB=true` (`local_db_disabled`); `DEV_MAIL_MODE=console` or any `DEV_SEED_PASSWORD` (`development_setting_refused`); a missing or malformed `TENANT_CONTEXT_SIGNING_KEY` (`tenant_context_unavailable`); a missing data or identity URL, URLs for different endpoints or databases, unsupported URL parameters or a non-empty `PGOPTIONS` (`unsafe_database_connections`);
  - remote pools always use `sslmode=verify-full` with certificate verification;
  - after connecting: a session login that differs from the effective role, or an unsafe runtime role safety, marker or per-role boundary result (`unsafe_database_role`). The safety query rejects elevated attributes, broad `pg_*` roles, protected-object ownership, ownership of the current database (directly or through any membership, NOINHERIT included), database `CREATE`/`TEMPORARY`, grant options and `public` schema access;
  - a missing or mismatched connection marker, the same role on both pools, or a role able to assume the other (`unsafe_database_connections`); a missing or different storage schema version (`storage_schema_mismatch`).

  Startup checks that the signing key is set and well formed. Whether it is installed is enforced per transaction: `tenant_context.install` rejects an uninstalled or retired key (403 `tenant_context_denied`). Hosted sign-in opens only through the readiness checks in `getAuthOptions()` (Vercel production runtime, HTTPS origin, usable secret, Resend mail and the same pre-pool refusals as `createDbPair()`), which also gate API tokens; Blob CV storage accepts only the request's OIDC token, and console mail is ignored when hosted.

## API and write integrity

Cookie-authenticated writes require the exact configured origin. Auth routes additionally bound input size and reject unexpected origins. No permissive CORS is supplied. JSON bodies are streamed with size limits, domain inputs are strict and bounded, reference kinds are checked, and Drizzle parameterises database values. Arbitrary import URLs, filesystem paths, shell execution and client-owned object keys are not accepted.

Record updates use versions; stale writes return 409. Creation supports actor/team/operation-scoped idempotency keys, rejects different payloads under the same key (even after the key expires), and commits the audit and record change together. Expired idempotency keys never re-run a create: an identical retry reconciles to the original record in the caller's team, or returns 409 `idempotency_expired` when it no longer exists. Bulk vacancy assignment re-runs instead, because active candidate/vacancy pairs are never duplicated. Every error response carries a fresh correlation ID; 500s log only that ID and a safe category (error class and SQLSTATE), never messages, stacks, request data or record contents. Audit history is append-only. Comments are append-only and use the authenticated actor. Personal-note/comment bodies are excluded from audit metadata. Import provenance is explicitly marked and cannot fabricate observed stage changes.

Bulk CV intake is a server-enforced review workflow (`src/lib/bulk-intake.ts`). Each item is created in one transaction under the team lock: the server refuses it with 503 `STORAGE_SETUP_REQUIRED` before any write when CV uploads are unavailable, with 400 `bulk_review_required` unless the caller confirms both the factual review and the duplicate review, and with 409 `bulk_duplicates_changed` when it re-runs the exact email/phone match and finds a current match the caller did not acknowledge. A batch holds at most 200 items, the item ID binds the file metadata and a payload hash (409 `bulk_item_conflict` for anything else), and a repeat of a created item returns it unchanged instead of creating a second candidate. The candidate is created with review status Reviewed, and its `created` activity event records the review evidence (batch and item IDs, both confirmations, the number of possible duplicates and whether the match was limited), so the evidence outlives the recovery rows. Source fields (`rawSource`, `evidence`, `sourceReviews`) are not accepted on this path. The general `POST /api/v1/candidates` is a separate path and is not review-gated; review cannot be enforced for direct record creation.

API tokens contain at least 256 random bits; only SHA-256 hashes are stored. The plaintext is shown once. Tokens have an explicit expiry (maximum 365 days), selectable current-role scopes, revocation and database-backed rate limits. Treat a token as a credential: use separate minimal tokens per client, never put them in prompts, repository files, public screenshots, browser URLs or query strings. Rate limits complement provider/project budgets; they are not a complete denial-of-service defence.

Rate-limit rows never hold a client address: both `auth.api_rate_limits` and Better Auth's `auth.rate_limit` store keyed HMAC hashes derived from `BETTER_AUTH_SECRET` (session `ip_address` is unchanged). Only an unknown token hash counts against a client's invalid-token budget; revoked and expired credentials do not. While a client address is over budget, a well-formed token whose hash matches a live row is still admitted (tokens carry 256 random bits, so admission tells a guesser nothing usable, and a shared egress address such as an AI provider's or an office NAT must not lock out its valid tokens); every other token from that address gets 429 `token_guess_rate_limited` without growing the count. There is no in-process pre-check any more, so each over-budget request costs one indexed identity lookup (job 031, SEC-04). Spent rows are purged, at most 500 per table at a time and at most once a minute per server instance from requests that already use a rate limit: rate-limit rows 10 minutes after their last use, OAuth codes and tokens one day after expiry (replay detection keeps working until then) and OAuth clients that no one approved after one day. While 1,000 clients without a grant exist, registration is refused. Details: [authentication.md](authentication.md#rate-limit-keys-and-retention).

Each export writes one `records.exported` activity row with the list, row count and applied filter keys, never values. The keys of the exporter's private state are left out (`PRIVATE_EXPORT_FILTER_KEYS` in `src/lib/records.ts`): `shortlisted`, and on candidates `status`, which is the exporter's personal follow-up status. Saved views reach the export only as ordinary query keys, so no view ID or name is stored. The filters still apply, and the CSV's own "Filters" line, written only into the exporter's file, still names them. The row count can still hint that some filter was applied. Rows written before this change may list `shortlisted` or `status`; they are not rewritten.

**Speed measurement (P1-18).** Vercel Speed Insights is a recipient of Web Vitals with scrubbed route patterns, loaded only on the signed-in app (`src/app/app/layout.tsx`) and the landing page (`src/app/page.tsx`), never on sign-in, password reset, invitation or OAuth pages, and only in production builds (in development the package would load a remote debug script). It uses no Speed Insights Plus feature, `dsn`, custom endpoint or script source. The CSP is unchanged: `script-src` and `connect-src` add no host, so only the same-origin `/_vercel/speed-insights/*` endpoints are reachable. The built-in speed log (`POST /api/v1/speed-samples`, `GET /api/v1/teams/speed`, `app.speed_samples`) stores timings and route names per team, never record ids, names, content, query values or user ids: action names come from a fixed list and route names must be `<METHOD> /api/v1/<pattern>` with only plain lowercase words and `[id]`. Timestamps are rounded to the hour, rows are kept 30 days (each team's write purges at most 1000 older rows and reads filter to 30 days), only owners and admins can read the summary, Bearer tokens are refused, and nothing is audited. Every `runApi` response carries `Server-Timing: total;dur=…, db;dur=…, dbrt;desc="…"`, which exposes only two durations and a round-trip count, never query text or values.

## Logging

Server code logs only fixed event names, error classes, SQLSTATE codes and correlation IDs, never messages, stacks, record contents, tokens, URLs or client addresses:

- every error response body carries `error.correlationId`, the same ID as its `X-Correlation-Id` header;
- an unexpected error is a 500 `internal_error` and logs `internal_error correlationId=<uuid> category=<class>[ sqlstate=<SQLSTATE>]`;
- a client that aborts its request, or whose body read fails (for example `ECONNRESET`), gets 499 `request_cancelled` and nothing is logged; any other unexpected error with a live request still logs `internal_error`;
- a CV storage setup refusal answers 503 `STORAGE_SETUP_REQUIRED` with the generic message and logs `storage_configuration_error correlationId=<uuid> code=STORAGE_SETUP_REQUIRED reason=<reason>`, where the reason is a fixed code per cause (for example `not_configured` or `oidc_expired`), never the refusal's own text;
- a failed rate-limit or OAuth purge logs `auth_purge_failed category=<class>[ sqlstate=<SQLSTATE>]` and never changes the response;
- a server-ended database connection logs `database_connection_error category=pool|client[ sqlstate=<SQLSTATE>]`, and Better Auth errors log only "An authentication operation failed.".

Framework and Better Auth output is not suppressed or patched. `tests/log-canary.test.ts` seeds fictional canaries (an email, phone, comment body, API-token plaintext, unknown Bearer token, signed-URL-like meeting URL and client address), drives record creation, a forced 500, a storage setup error, Bearer guesses past the budget, an export searching for the email, an aborted body and a Better Auth sign-in, and checks that no console output, rate-limit key or export audit row contains any of them. Monitoring, alerting and a log drain are not set up (SRS-OPS-07, D-17).

## CV handling

Legacy, dormant S3 option (explicit `CV_STORAGE_PROVIDER=s3` only): S3 objects remain private with public access blocked. The server chooses a team/candidate-scoped key and reserves quota before issuing a short-lived signed POST limited to the exact expected size/type. Validation reads bounded data from an exact object version and stores that VersionId. Downloads are signed for that same version and expire quickly; a replayed upload cannot silently replace the already validated version. Signed URLs are bearer credentials until they expire, so anyone deliberately given one can use it within that period.

The reservation response tags its upload protocol (`s3-form-v1` or `blob-put-v1`) and clients switch on that tag, never on a hostname. Private Vercel Blob is the hosted provider (DEC-01, 7 November 2026). `getStorage` builds the Blob client only on Vercel, with the request-context OIDC token checked by `assertHostedOidcToken` and an explicit store id equal to the binding's `BLOB_STORE_ID`, and refuses while `BLOB_READ_WRITE_TOKEN` is present at all; the SDK's own credential fallback is never used. A `blob-put-v1` ticket is a private, exact-path, no-overwrite PUT of at most the reserved size and type, valid for at most 5 minutes inside a 15-minute reservation. The provider's own limits are not trusted: the owner's live run showed a wrong content type accepted and a multipart upload past the size limit. Completion first checks the object's size and type with `head` and rejects a mismatch without opening it, then reads the whole object under the same 15 s deadline, validates it and stores the SHA-256 and exact size of those same bytes; a client-supplied hash is never used. Blob CVs are downloaded through `GET /api/v1/cvs/{id}/manifest` and `/chunks?index=N`. Every chunk request is authorized again, reads the whole object and releases at most 4 MiB only after the full digest matches; the browser checks the final SHA-256 before saving the file. No Blob URL is ever given to a caller. Blob provider reads are limited across server instances by short database leases (2 per team, 8 per store, each expiring after 30 s; placeholders until hosted measurement); a read over either cap fails at once without contacting the provider. Every storage setup refusal shows users the same plain message, which names no provider or setting.

A rejected, expired or abandoned Blob upload keeps its charge retained until its object is deleted after expiry: the cleanup deletes only once the reservation expired at least 10 minutes ago (a still-valid ticket recreated a deleted object in the live run), confirms the object missing with `head`, and only then frees the charge through the owner-run `tenant_context.release_blob_charge`; a failed deletion is repeated by every later sweep. The list pass also confirms every object it deletes missing with `head`, and counts one still present as a failure. The sweep is team-scoped, lists only `teams/<team>/cvs/`, runs best effort on each new Blob reservation (at most 5 rows), automatically after each completion that settles a Blob upload ready or rejected, and fully through the owner or admin `POST /api/v1/cvs/storage-reconciliation`, and returns counts only. A team's full sweep runs at most once per 10 minutes, whatever triggers it, through the owner-run `tenant_context.claim_blob_reconciliation` (migration `0019`); the endpoint answers 429 `STORAGE_RECONCILIATION_COOLDOWN` with the seconds left in `Retry-After` inside that time. Each Blob reservation gets at most 5 PUT tickets in all, counted in `app.uploads.put_tickets_issued` under the row lock and guarded to grow only by one on a pending Blob row; more returns 409 `CV_UPLOAD_TICKET_LIMIT`. With a team upload rate set, an over-rate new reservation is refused before the best-effort row pass makes any provider call. The sweep is still not a scheduler: objects are cleaned only when a later trigger runs (job 031, SEC-01, SEC-08 and SEC-09). Team storage limits and the per-team upload rate limit are application controls, off by default, set by owners and admins and audited as `storage-settings` activity rows written only by the owner-run `tenant_context.set_storage_limits`. Residual risk: multipart with a valid PUT ticket can bypass the size limit, and uncompleted parts cannot be listed or deleted by the application, so store usage can exceed the ledger until the provider discards them; limits and budgets are not hard provider or billing caps ([blob-security-design.md](blob-security-design.md#residual-risk)).

Bulk CV intake keeps 24-hour private recovery rows (`app.bulk_intake_batches` and `app.bulk_intake_items`, migrations `0015`, `0016` and `0017`) under FORCE row-level security, readable and writable only by the user who created them in their team. They hold the file name, type and size, a SHA-256 of the reviewed candidate data, the review time, the number of possible duplicates and the created candidate and upload IDs and the current CV attempt's upload key; never a candidate's name, email, phone or any other field value. A batch expires 24 hours after it is created and is never extended; an expired batch is refused (409 `bulk_batch_expired`) and hidden from both bulk GETs. The purge is the owner-run definer helper `tenant_context.purge_bulk_intake(keep_batch)`: it needs a verified context with `cvs:write`, takes at most 100 expired, unpurged batches per call (oldest expiry first, rows another transaction holds are skipped) across every team and user, deletes their items and keeps each batch row as a tombstone with `purged_at` set (migration `0017`), and returns nothing, so no other team's count is revealed. A tombstone holds only the batch ID, team, creator and its created, expiry and purge times; file names, types, sizes, hashes and review evidence go with the items. Tombstones are kept indefinitely, as expired idempotency rows are, because any bounded lifetime would reopen the retry hole after it. The client chooses the batch ID, so the tombstone is the server's record of it: item and upload POSTs for an expired or purged batch ID return 409 `bulk_batch_expired` for every client, browser or API token, whoever ran the purge and whenever, and the batch is never recreated or extended; both GETs hide it. Owner-only SELECT, DELETE and UPDATE policies let only that helper act across users and teams; the runtime role's access is unchanged. It runs in its own transaction at the start of every bulk item POST (keeping the requested batch for its caller to refuse) and every list GET, so without a scheduler an expired batch keeps its items until the next such request anywhere in the deployment. The browser also refuses to retry an uncertain create once 24 hours have passed since its batch started. File bytes and drafts stay in browser memory only, never in local storage, session storage or IndexedDB. The bulk upload step reserves the item's CV through the normal reservation with the item's stored file name, type and size; the client chooses neither the metadata nor the key. The first attempt's `clientUploadId` is the item ID. A repeat returns a pending, unexpired or ready attempt unchanged; only a rejected or expired attempt is replaced, once, by a new attempt under a server-chosen key stored on the item through a conditional update, so overlapping calls share it. The bulk path has no provider check of its own: it speaks `blob-put-v1` and `blob-chunks-v1` exactly as single upload does, with the same checks, rate limit and quota, and completes once after a refused Blob PUT because a replayed no-overwrite ticket is refused after a PUT that did store the bytes. Single CV upload (`CvUpload`) sends its bytes through the same `storeCv` step, so it also completes once after a refused Blob PUT; a refused S3 POST still fails without completing. Each rejected or expired Blob attempt keeps its retained charge, so a Blob re-upload uses one more file of the store budget. `bulk-capabilities` reports uploads available only when the environment-only `storageConfigured()` does, so Blob bulk import is available exactly where single upload is: on Vercel with a valid `BLOB_STORE_ID` and no static token. One upload at a time per browser is a client-side Web Lock, not a server control.

Format checks reject obvious type mismatches, malformed/unsafe document archives and excessive expansion. **They are not malware scanning.** PDF/DOC and images can still contain malicious content. **DEC-07 (owner decision, 7 November 2026, SEC-06):** Release 1 has no server-side malware scanner. CVs are served only as attachment downloads (`application/octet-stream`, `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`) and are never rendered inline; the user's endpoint antivirus scans each file on download. Public multi-engine scanners such as VirusTotal are not allowed, because they share uploaded files with third parties. A server-side scanner that never shares files with third parties is a post-Release-1 roadmap item (R15-06). `tests/cv-inline-content.test.ts` enumerates every CV route with a glob and fails until a new one is classified; it checks that only `/api/v1/cvs/{id}/chunks` returns bytes, always as an octet-stream attachment with `nosniff` and `private, no-store` and never the stored type, that every other CV route answers JSON, and that `attachmentDisposition` never yields `inline`. The legacy S3 path relies on the S3 response overrides `ResponseContentType: application/octet-stream` and `ResponseContentDisposition: attachment`, which the same test checks on a locally signed URL. Do not configure automatic noncurrent-version deletion on the CV prefix: ready records can reference older versions. Quota cleanup releases expired database reservations; orphan-object cleanup must be database-aware.

Each CV reference is bound to its provider, environment and store, and a mismatched binding fails closed before any storage call. CV quota is charged in the database by owner-run triggers on `app.uploads`, under a store-wide ledger (`storage_ledger`, owner-only) with approved per-environment budgets, set by the owner outside the app, and optional per-team limits that are off by default. Locks are taken store, then team, then upload; neither runtime role can write either ledger directly. Rejected S3 reservations are released. Expired S3 reservations are released store-wide, for every team, by the owner-run lock helper before any later reservation on that bucket is checked, so abandoned tickets cannot hold the shared budget; a partial index on pending S3 rows (`uploads_pending_s3_expiry_idx`, migration `0008`) serves that scan. Rejected or expired Blob tickets keep a retained charge until cleanup confirms the object deleted. While a team's limits are off, one team can still fill a shared store with live reservations (up to 15 minutes each on Blob) or completed CVs; owners and admins can set a team limit and an upload rate (429 `CV_UPLOAD_RATE_LIMITED`). Database quotas bound accepted CVs and pending reservations, rather than every physical S3 version. Replaying a still-valid signed upload form can create additional unreferenced versions. Use provider budget alarms and database-aware orphan cleanup as part of production operations; do not treat the application quota as a hard AWS billing cap.

## Deployment responsibilities and limits

The implementation is locally validated with fictional data and fake cloud clients. Real Neon connectivity/pooling, the Blob OIDC credential and store scoping, delivered email, optional OAuth, backup restoration, provider quotas and production observability require staging checks after access is supplied. See [deployment.md](deployment.md), [authentication.md](authentication.md), and [s3-setup.md](s3-setup.md).

Recruitment and token changes have application audit events; authentication/team membership changes do not currently have an equivalent application audit feed. Only a verified user who is the initial administrator or owns at least one team can create a team (403 otherwise, through `canCreateTeam` in `src/lib/auth-policy.ts`); the settings page shows the form only to them, and invitation mail passes the team name through `cleanClientName`, so control, bidi and zero-width characters never reach the subject or body (job 031, SEC-13). Team creation is atomic: the team, its creator's owner membership and the active-team selection commit in one database transaction, so a failed owner-member insert leaves no team behind, does not use the slug or the creator's five-team allowance, and keeps initial setup pending; retrying creates exactly one team. The CSP restricts sources and framing but still permits framework inline scripts/styles; its `connect-src` lists only the configured provider's upload hosts: the regional S3 hosts for `s3`, only the path-scoped `https://vercel.com/api/blob/` for `blob` or `vercel-blob`, and no upload host when `CV_STORAGE_PROVIDER` is unset, empty or anything else. It is not a nonce-based strict CSP. Next.js evaluates `headers()` at build time, so `CV_STORAGE_PROVIDER=blob` must be set before the build in every hosted environment; a build without it allows no browser upload host, while `src/lib/storage.ts` still resolves an unset provider to Blob, so uploads fail in the browser until the variable is set and the app rebuilt. Every response also sends `Strict-Transport-Security: max-age=63072000; includeSubDomains` (no `preload`) and `Cross-Origin-Opener-Policy: same-origin` (job 031, SEC-10). COOP severs `window.opener` for pages opened in a popup, including `/oauth/authorize`; a live Claude and ChatGPT connection on Preview must confirm that the connectors do not rely on it. AWS credentials are explicitly supplied; the AWS SDK may still read optional shared SDK configuration flags in a local environment.

Record values are untrusted when rendered. React escapes text, and `safeExternalUrl()` in `src/domain/records.ts` turns an interview meeting URL into a link only when it parses as an absolute `http:` or `https:` URL, even though the write schema already allows only those. `tests/untrusted-rendering.test.tsx` renders record details and a record card with `<script>`, `<img onerror>` and `javascript:`, `data:`, `vbscript:` and relative values and finds no element, event attribute or dangerous link made from the data.

### Nonce-based CSP spike

The current CSP is set in `next.config.ts` and still allows `'unsafe-inline'` scripts and styles; it is not a nonce-based strict CSP. This spike, based on the Next.js 16 guide (`node_modules/next/dist/docs/01-app/02-guides/content-security-policy.md`) and the local build, records what a nonce CSP would take. Nothing was changed: `next.config.ts` keeps its CSP and no `src/proxy.ts` exists.

- **What it needs:** a `src/proxy.ts` that makes a fresh random nonce per request, sends `script-src 'self' 'nonce-<value>' 'strict-dynamic'` (plus `'unsafe-eval'` only in development) on the request and response, and skips `api`, `_next/static`, `_next/image` and prefetches. Next.js reads the nonce from the request's CSP header during server rendering and adds it to its own scripts. That works only for dynamically rendered pages: every page must render per request (for example through `connection()` or another dynamic API in the root layout), so static optimisation and ISR end for the whole app, and the CSP would move out of `next.config.ts` headers for pages.
- **What blocks `style-src` without `'unsafe-inline'`:** nonces cover `<style>` and `<script>` elements, not `style="…"` attributes. React renders inline `style` props as attributes in server HTML, and the app has 29 of them in 10 component files (for example the OAuth consent page and profile settings). They would need to become classes first, or the policy would keep `style-src-attr 'unsafe-inline'` beside a nonce-only `style-src-elem`.
- **Effect on caching:** per-request nonces make every HTML response unique, so pages cannot be served from the build output or a CDN cache and each view costs a server render; Partial Prerendering cannot be used with nonces. In the local production build (`npm run build`, job 026) only `/`, `/_not-found` and `/forgot-password` are prerendered as static; every other page and every API route already renders per request, so the change would cost those three pages their static copies. API routes are unaffected. The experimental Subresource Integrity mode keeps static pages but covers only script files, not inline scripts or styles.
- **Recommendation:** keep the current CSP for now and leave the decision to the owner. If a strict CSP is required, first replace the inline `style` props with classes, then add the nonce proxy for scripts with `'strict-dynamic'`, accept dynamic rendering of every page, and measure Preview latency before production. Until then the CSP stays disclosed as not nonce-based.

Define organisational retention/deletion, lawful access, offboarding, export handling and incident response before importing real CVs; the Release 1 malware policy is DEC-07 above. Protect local migration reports and exports as candidate data. This repository intentionally contains no real records, legacy files, service credentials or deployment secrets. Dependencies are locked; review updates and rerun tests before release.
