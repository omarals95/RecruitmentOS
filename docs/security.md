# Security and data flows

RecruitmentOS is a cloud application. Its authorised service connections differ from the earlier offline desktop dashboard. This document describes implemented controls and remaining deployment checks; it is not a guarantee that no vulnerabilities exist.

## Intended connections

| Connection                                                                           | Data and purpose                                                                                                                                                                                                                                                                                                                            |
| ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Browser → same-origin Next.js `/api/auth/*`, `/api/v1/*`, `/api/settings/*`          | Sign-in, team-scoped recruitment records, personal settings and upload tickets                                                                                                                                                                                                                                                              |
| Vercel server → Neon PostgreSQL, TLS                                                 | Auth sessions, teams, recruitment facts, personal notes, audit records, token hashes and upload references                                                                                                                                                                                                                                  |
| Browser → configured private S3 bucket                                               | Direct, size/type/key-constrained upload using an expiring signed form; private version-specific download                                                                                                                                                                                                                                   |
| Browser → Vercel Blob API `https://vercel.com/api/blob/` (**disabled**)              | Exact-path, size/type-limited private PUT only; not used while Blob CV storage is disabled                                                                                                                                                                                                                                                  |
| Vercel server → Vercel Blob API (**disabled**)                                       | Signed-token issuance for upload tickets and private, uncached object reads, always with one explicit credential; not wired while Blob CV storage is disabled. Hosted use is chosen to authenticate with request-scoped Vercel OIDC (not yet built); the read-write token is used only by tests and the owner's Preview verification script |
| Vercel server → AWS STS/S3                                                           | OIDC role credentials, versioning/metadata/range checks and download signatures                                                                                                                                                                                                                                                             |
| Vercel server → Resend                                                               | Account email verification, password resets and team invitations; no CVs or recruitment records                                                                                                                                                                                                                                             |
| Browser/server → Google or Microsoft                                                 | Only when an administrator configures that optional sign-in provider and the user chooses it                                                                                                                                                                                                                                                |
| Administrator-run importer → chosen application origin and its signed S3 destination | Only with explicit `--apply`; dry-run reads locally and reports reconciliation                                                                                                                                                                                                                                                              |
| AI client (for example Claude) → `/api/mcp`, `/oauth/*` and `/.well-known/oauth-*`   | The assistant calls MCP tools with an API token or a consented, short-lived OAuth access token; team-scoped, scope-limited records come back as labelled untrusted JSON ([mcp.md](mcp.md))                                                                                                                                                  |

No external AI provider, advertising library, remote font or product analytics service is integrated. API tokens and OAuth connections let an independently authorised AI client call this application; the application does not send its records to that client on its own. Next.js anonymous build telemetry is disabled by the project's command wrapper. Dependency installation contacts npm; that is a development operation, not a candidate-data flow.

## Identity and tenancy

- Better Auth handles password hashing, database sessions, verification and reset tokens. Registration is invitation-only unless explicitly opened; a configured bootstrap email can create the initial account. A generic successful registration response may conceal a rejected address to avoid account enumeration. Verification and a live membership are required before accessing team records.
- Optional provider sign-in does not auto-link another account by matching an email. Microsoft email claims are not treated as an invitation or a verified local identity by themselves. Validate actual provider flows in staging.
- Every API request resolves a session or a Bearer token. An invalid Bearer header never falls back to cookie privileges. A team header must match current membership or the token's fixed team.
- `/api/mcp` accepts only Bearer credentials and never reads cookies: an API token or an OAuth access token (`ros_oat_…`) bound to the `/api/mcp` audience, which `/api/v1/*` refuses. OAuth access needs a verified team member to approve a consent page naming the client, its return host, the team and the exact scopes. Each approval is an `auth.api_tokens` grant row (with `oauth_client_id`), so it is listed and revocable in Settings, counts towards the 50-token cap, is intersected with the approver's current role on every request and passes the unchanged `tenant_context.install` token checks. Only SHA-256 hashes of codes, access and refresh tokens are stored. Dynamic client registration is the only registration method (the server fetches no client metadata URL), is rate limited, accepts only Claude's two exact callback URIs, ChatGPT's exact stable callback `https://chatgpt.com/connector_platform_oauth_redirect` or `http:` loopback redirect URIs, strips invisible characters from client names and grants nothing. `/oauth/authorize` shows an error page for every invalid request and never redirects to a client; only a signed-in member's approve or deny decision does, and both responses carry `iss` (RFC 9207), equal to the metadata issuer. A `resource` other than `/api/mcp` is refused at authorize and at the token endpoint, and refresh tokens must also carry the `/api/mcp` audience. Codes last 120 seconds, access tokens one hour, grants 30 days; a reused code or refresh token revokes the grant and writes an owner-run `token.revoked` audit row with a fixed reason. MCP tools never return the sensitive candidate fields `explicitGender` and `nationalServiceStatus`, drop evidence entries that mention them, and never match search words against them or against the imported source fields (`rawSource`, `evidence`, `sourceReviews`) that may copy them. Every MCP tool call writes an owner-run `mcp-tool` audit row (no arguments) before the tool runs, and no runtime role can insert such rows directly ([mcp.md](mcp.md)).
- Role scopes are checked on the server. Tokens cannot manage accounts, memberships or other tokens. Membership removal/demotion affects subsequent requests; last-owner protection is serialized in the database.
- Business operations run in transactions that first install one HMAC-signed assertion, bound to the backend, the transaction, the database marker, the team, the actor, the auth type, the token and the scopes, and valid for at most 60 seconds. An owner-controlled function verifies it and rechecks membership and token state. Row policies on every recruitment table derive team, actor and write access from that verified context and ignore settings such as `app.team_id`, so savepoint rollback, pooled-connection reuse and expired or revoked assertions do not carry access over. Explicit team predicates and composite foreign keys stay as defence in depth. Private candidate states, saved views, notification reads and private activity are limited to their own user. New activity rows must name the context's own actor and token, so audit events cannot be forged under another member. Limits: this protects against SQL on the recruitment-data role only. The application process, the signing key, the identity role and the database owner are trusted. The design is tested on local PGlite and a throwaway local PostgreSQL 18 cluster. In the owner's run on the Neon Preview database, the role template is applied, `scripts/db-role-evidence.ts` passes with zero drift, and `npm run test:live-roles` passes 27/27 through the transaction-mode pooler and 27/27 direct, with all fixtures removed. It still needs independent review (DEC-02/DEC-03) and Production verification ([identity-boundary-plan.md](identity-boundary-plan.md#signed-tenant-context)).
- Production refuses owner/superuser/BYPASSRLS runtime connections. RLS must be deployed with the separate restricted runtime role; tests exercise a nonowner role locally.
- Hosted and `NODE_ENV=production` startup has no blanket database block; it refuses with 503, and no environment variable bypasses these checks:
  - before any pool exists: `DATABASE_MODE=pglite` or `ALLOW_LOCAL_DB=true` (`local_db_disabled`); `DEV_MAIL_MODE=console` or any `DEV_SEED_PASSWORD` (`development_setting_refused`); a missing or malformed `TENANT_CONTEXT_SIGNING_KEY` (`tenant_context_unavailable`); a missing data or identity URL, URLs for different endpoints or databases, unsupported URL parameters or a non-empty `PGOPTIONS` (`unsafe_database_connections`);
  - remote pools always use `sslmode=verify-full` with certificate verification;
  - after connecting: a session login that differs from the effective role, or an unsafe runtime role safety, marker or per-role boundary result (`unsafe_database_role`). The safety query rejects elevated attributes, broad `pg_*` roles, protected-object ownership, ownership of the current database (directly or through any membership, NOINHERIT included), database `CREATE`/`TEMPORARY`, grant options and `public` schema access;
  - a missing or mismatched connection marker, the same role on both pools, or a role able to assume the other (`unsafe_database_connections`); a missing or different storage schema version (`storage_schema_mismatch`).

  Startup checks that the signing key is set and well formed. Whether it is installed is enforced per transaction: `tenant_context.install` rejects an uninstalled or retired key (403 `tenant_context_denied`). Hosted sign-in opens only through the readiness checks in `getAuthOptions()` (Vercel production runtime, HTTPS origin, usable secret, Resend mail and the same pre-pool refusals as `createDbPair()`), which also gate API tokens; Blob CV storage stays disabled, and console mail is ignored when hosted.

## API and write integrity

Cookie-authenticated writes require the exact configured origin. Auth routes additionally bound input size and reject unexpected origins. No permissive CORS is supplied. JSON bodies are streamed with size limits, domain inputs are strict and bounded, reference kinds are checked, and Drizzle parameterises database values. Arbitrary import URLs, filesystem paths, shell execution and client-owned object keys are not accepted.

Record updates use versions; stale writes return 409. Creation supports actor/team/operation-scoped idempotency keys, rejects different payloads under the same key (even after the key expires), and commits the audit and record change together. Expired idempotency keys never re-run a create: an identical retry reconciles to the original record in the caller's team, or returns 409 `idempotency_expired` when it no longer exists. Bulk vacancy assignment re-runs instead, because active candidate/vacancy pairs are never duplicated. Every error response carries a fresh correlation ID; 500s log only that ID and a safe category (error class and SQLSTATE), never messages, stacks, request data or record contents. Audit history is append-only. Comments are append-only and use the authenticated actor. Personal-note/comment bodies are excluded from audit metadata. Import provenance is explicitly marked and cannot fabricate observed stage changes.

Bulk CV intake is a server-enforced review workflow (`src/lib/bulk-intake.ts`). Each item is created in one transaction under the team lock: the server refuses it with 503 `STORAGE_SETUP_REQUIRED` before any write when CV uploads are unavailable, with 400 `bulk_review_required` unless the caller confirms both the factual review and the duplicate review, and with 409 `bulk_duplicates_changed` when it re-runs the exact email/phone match and finds a current match the caller did not acknowledge. A batch holds at most 50 items, the item ID binds the file metadata and a payload hash (409 `bulk_item_conflict` for anything else), and a repeat of a created item returns it unchanged instead of creating a second candidate. The candidate is created with review status Reviewed, and its `created` activity event records the review evidence (batch and item IDs, both confirmations, the number of possible duplicates and whether the match was limited), so the evidence outlives the recovery rows. Source fields (`rawSource`, `evidence`, `sourceReviews`) are not accepted on this path. The general `POST /api/v1/candidates` is a separate path and is not review-gated; review cannot be enforced for direct record creation.

API tokens contain at least 256 random bits; only SHA-256 hashes are stored. The plaintext is shown once. Tokens have an explicit expiry (maximum 365 days), selectable current-role scopes, revocation and database-backed rate limits. Treat a token as a credential: use separate minimal tokens per client, never put them in prompts, repository files, public screenshots, browser URLs or query strings. Rate limits complement provider/project budgets; they are not a complete denial-of-service defence.

## CV handling

S3 objects remain private with public access blocked. The server chooses a team/candidate-scoped key and reserves quota before issuing a short-lived signed POST limited to the exact expected size/type. Validation reads bounded data from an exact object version and stores that VersionId. Downloads are signed for that same version and expire quickly; a replayed upload cannot silently replace the already validated version. Signed URLs are bearer credentials until they expire, so anyone deliberately given one can use it within that period.

The reservation response tags its upload protocol (`s3-form-v1` or `blob-put-v1`) and clients switch on that tag, never on a hostname. The Blob protocol is implemented locally behind a fake client and stays disabled until live provider tests pass. A `blob-put-v1` ticket is a private, exact-path, no-overwrite PUT of at most the reserved size and type, valid for at most 5 minutes. Completion reads the whole object under a 15 s deadline, validates it and stores the SHA-256 and exact size of those same bytes; a client-supplied hash is never used. Blob CVs are downloaded through `GET /api/v1/cvs/{id}/manifest` and `/chunks?index=N`. Every chunk request is authorized again, reads the whole object and releases at most 4 MiB only after the full digest matches; the browser checks the final SHA-256 before saving the file. No Blob URL is ever given to a caller. Blob provider reads are limited across server instances by short database leases (2 per team, 8 per store, each expiring after 30 s; placeholders until hosted measurement); a read over either cap fails at once without contacting the provider. Every storage setup refusal shows users the same plain message, which names no provider or setting.

Bulk CV intake keeps 24-hour private recovery rows (`app.bulk_intake_batches` and `app.bulk_intake_items`, migrations `0015` and `0016`) under FORCE row-level security, readable and writable only by the user who created them in their team. They hold the file name, type and size, a SHA-256 of the reviewed candidate data, the review time, the number of possible duplicates and the created candidate and upload IDs and the current CV attempt's upload key; never a candidate's name, email, phone or any other field value. A batch expires 24 hours after it is created and is never extended; an expired batch is refused (409 `bulk_batch_expired`) and hidden from both bulk GETs until it is purged. The purge is the owner-run definer helper `tenant_context.purge_bulk_intake(keep_batch)`: it needs a verified context with `cvs:write`, deletes at most 100 expired batches per call (oldest expiry first, rows another transaction holds are skipped) with their items, across every team and user, and returns nothing, so no other team's count is revealed. Owner-only SELECT, DELETE and row-lock policies let only that helper act across users and teams; the runtime role's access is unchanged. It runs in its own transaction at the start of every bulk item POST (keeping the requested batch so it is still refused, not recreated) and every list GET, so without a scheduler an expired row lasts until the next such request anywhere in the deployment. The browser also refuses to retry an uncertain create once 24 hours have passed since its batch started. File bytes and drafts stay in browser memory only, never in local storage, session storage or IndexedDB. The bulk upload step reserves the item's CV through the normal reservation with the item's stored file name, type and size; the client chooses neither the metadata nor the key. The first attempt's `clientUploadId` is the item ID. A repeat returns a pending, unexpired or ready attempt unchanged; only a rejected or expired attempt is replaced, once, by a new attempt under a server-chosen key stored on the item through a conditional update, so overlapping calls share it. The bulk path has no provider check of its own: it speaks `blob-put-v1` and `blob-chunks-v1` exactly as single upload does, behind the same disabled Blob guard, and completes once after a refused Blob PUT because a replayed no-overwrite ticket is refused after a PUT that did store the bytes. Each rejected or expired Blob attempt keeps its retained charge, so a Blob re-upload uses one more file of the store budget. `bulk-capabilities` reports uploads available only when the environment-only `storageConfigured()` does, so Blob stays disabled for bulk import as for single upload. One upload at a time per browser is a client-side Web Lock, not a server control.

Format checks reject obvious type mismatches, malformed/unsafe document archives and excessive expansion. **They are not malware scanning.** PDF/DOC and images can still contain malicious content; production policy may require private quarantine scanning before ready status. Downloads use attachment disposition and an opaque content type. Do not configure automatic noncurrent-version deletion on the CV prefix: ready records can reference older versions. Quota cleanup releases expired database reservations; orphan-object cleanup must be database-aware.

Each CV reference is bound to its provider, environment and store, and a mismatched binding fails closed before any storage call. CV quota is charged in the database by owner-run triggers on `app.uploads`, under a store-wide ledger (`storage_ledger`, owner-only) with approved per-environment budgets and per-team limits that default to the store budget. Locks are taken store, then team, then upload; neither runtime role can write either ledger directly. Rejected S3 reservations are released. Expired S3 reservations are released store-wide, for every team, by the owner-run lock helper before any later reservation on that bucket is checked, so abandoned tickets cannot hold the shared budget; a partial index on pending S3 rows (`uploads_pending_s3_expiry_idx`, migration `0008`) serves that scan. Rejected or expired Blob tickets keep a retained charge (Blob remains disabled). Team limits default to the whole store budget, so one team can still fill a shared store with live reservations (for up to an hour) or completed CVs; issuance is not rate limited. Database quotas bound accepted CVs and pending reservations, rather than every physical S3 version. Replaying a still-valid signed upload form can create additional unreferenced versions. Use provider budget alarms and database-aware orphan cleanup as part of production operations; do not treat the application quota as a hard AWS billing cap.

## Deployment responsibilities and limits

The implementation is locally validated with fictional data and fake cloud clients. Real Neon connectivity/pooling, Vercel OIDC trust, AWS policy enforcement, browser S3 CORS, delivered email, optional OAuth, backup restoration, provider quotas and production observability require staging checks after access is supplied. See [deployment.md](deployment.md), [authentication.md](authentication.md), and [s3-setup.md](s3-setup.md).

Recruitment and token changes have application audit events; authentication/team membership changes do not currently have an equivalent application audit feed. Team creation is atomic: the team, its creator's owner membership and the active-team selection commit in one database transaction, so a failed owner-member insert leaves no team behind, does not use the slug or the creator's five-team allowance, and keeps initial setup pending; retrying creates exactly one team. The CSP restricts sources and framing but still permits framework inline scripts/styles; its `connect-src` lists only the configured provider's upload hosts (the regional S3 hosts for `s3`, only the path-scoped `https://vercel.com/api/blob/` for `blob`, which stays disabled, and neither for any other value). It is not a nonce-based strict CSP. Next.js evaluates `headers()` at build time, so changing `CV_STORAGE_PROVIDER` needs a rebuild before the CSP follows it. AWS credentials are explicitly supplied; the AWS SDK may still read optional shared SDK configuration flags in a local environment.

Define organisational retention/deletion, lawful access, offboarding, export handling, malware policy and incident response before importing real CVs. Protect local migration reports and exports as candidate data. This repository intentionally contains no real records, legacy files, service credentials or deployment secrets. Dependencies are locked; review updates and rerun tests before release.
