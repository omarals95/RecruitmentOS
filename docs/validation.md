# Validation before deployment

## Update: scoped-member speed (R2-PERF-01)

**Method.** Runs were on local PGlite only (PGlite 0.5.15, PostgreSQL 18.6 compiled to WebAssembly), with fictional data, on 10 November 2026 with Node v24.20.0. PGlite never runs `ANALYZE`, so every plan below was made without statistics. None of these timings represents hosted (Neon) timings. "Before" is the code of `main` at `fc85873` and "after" is this branch. The first `npm run bench:round-trips -- --fixture --scoped` ran `main`'s code against the worktree's seeded database. That run built the fixture (2,000 candidates, 20 vacancies, 1,200 applications, 150 on the first vacancy) and the fictional hiring manager. Every later run used a copy of that database taken after that first run, and the branch's first run on a copy applied `0039`. The cause was found with `EXPLAIN (ANALYZE, BUFFERS)` of every statement the hiring manager's overview and lists run. Each statement was captured and explained inside `withTeam`, as `recruitment_bench_runtime` with the hiring manager's signed context installed. The diagnostic scripts are not committed.

**Cause.** Without statistics PostgreSQL estimates about one row for almost every scan. Three costs then grew with the team's size:

1. **The service rule's candidate probe.** `scopeFilter`'s candidate rule (an `exists` over the candidate's applications) was pulled up into a `Nested Loop Semi Join`. Its inner `Index Scan using records_application_candidate_idx on records records_a` had only `team_id` as its index condition, and `records.id = records_a.candidate_id` became a join filter. For each candidate in scope it therefore read the team's applications, each through the `record_scope` policy's `tenant_context.in_scope`. On the candidates list that node ran 648 loops of about 620 applications (`Rows Removed by Join Filter: 209628`, `Buffers: shared hit=3449997`), 18,499 of 18,937 ms. The same node dominated the shortlist, the source-review list (164 loops, 4,101 of 4,103 ms), the overview's coverage (14,384 of 14,395 ms) and its folder categories (13,969 ms).
2. **The candidate lookup in `tenant_context.candidate_in_scope`.** The helper finds its candidate by `k.team_id = c.team_id AND k.kind = 'candidate' AND k.id = $2`. PostgreSQL read that through `records_team_kind_idx` (index condition team and kind, `Filter: (id = $2)`), so each call walked the team's candidates up to the one it wanted. The policy calls it for every candidate row a scoped statement reads. Under the hiring manager's context, `SELECT count(*) FROM app.records WHERE kind = 'candidate'` took 911 ms for 2,007 candidates (about 0.45 ms each, `Buffers: shared hit=395484`), against 61 ms for 1,224 applications. In a rolled-back transaction, 2,007 calls of the helper took 841 ms as it is. They took 108 ms with a partial index on `(team_id, id) WHERE kind = 'candidate'` and 95 ms with one on `(team_id, kind, id)`. A copy of the helper with the kind test hidden from the index took 121 ms.
3. **The policy ran on every row read.** The service rule's correlated probes are not leakproof, so PostgreSQL runs the policy's helper before them on every row. For example, the overview's inventory counted over all 3,252 active team rows (794 ms), 1,934 of which the policy removed.

**Change.**

- `drizzle/0039_candidate_scope_index.sql` adds only `CREATE INDEX records_candidate_id_idx ON app.records(team_id, id) WHERE kind = 'candidate';`. No policy, helper, grant or business row changes, and the storage schema marker stays at 17.
- Statements over many rows use `scopeFilter(ctx, kind, { once: true })`: lists and exports (`recordQuery`), candidate suggestions, and the overview's counts, shortlist and CV counts, coverage, stages, groups, upcoming interviews and overdue tasks. The rule then tests the row's id against `scopedIds` (`src/lib/authz.ts`), the team's records of that kind in scope. `scopedIds` is a union of branches. Each branch takes the rows whose one column is in one set: the units under the home units, the caller's assigned records, or another kind's records in scope. A candidate's set is the candidates of its applications in scope. Each set is an uncorrelated `array(...)` that PostgreSQL computes once per statement. `x = any(array(...))` is leakproof and costs less than ten times `cpu_operator_cost`, so PostgreSQL applies it before the restrictive policy and calls `in_scope` only for rows in scope. Comments keep their per-row walk to the parent.
- Statements about one record or a few keep the per-row form exactly as on `main`: get, reference checks, labels, CVs, assignments and the activity feeds. The overview's recent activity stays per-row as well: its index scan stops after the newest events (4 ms), whereas a set of every record in scope cost about 250 ms.
- `inventory` counts each kind in its own subquery of the same statement, so each count reads only its kind's rows in scope.
- The equivalence of the two shapes is shown by the unchanged `tests/org-scope.test.ts`, `tests/record-scope-rls.test.ts` and `tests/authz.test.ts`, and by one new case in `tests/record-scope-rls.test.ts`. As the superuser, it checks that both shapes select the same records of every scoped kind for every scoped principal there: unit, assigned, mixed, no home units and token.

**After.** The candidates list is now an `Index Scan using records_team_kind_idx` with `Filter: ((archived_at IS NULL) AND (id = ANY ((InitPlan 119).col1)) AND (... tenant_context.in_scope(...)) ...)`. Only the 650 candidates in scope, of 2,009, reach the policy (`Rows Removed by Filter: 1359`). The InitPlan is an `Append` of the four application branches (650 rows, 27 ms), and the statement takes 95.5 ms (it took 18,937 ms). The source-review list takes 97.6 ms (it took 4,103 ms). Per overview statement: inventory 185 ms (was 794), coverage 102 (was 14,395), categories 97 (was 13,969), stages 59 (was 36) and recent activity 4.0 (was 4.2). The whole overview call takes 539 ms (it took 28,690 ms). The dominant nodes left are the policy on the rows in scope (about 50 µs per candidate and 49 µs per application) and the application branch scans that build each statement's sets.

## Update: configuration versions through install (R2a-05)

**Local validation.** On 9 November 2026, with Node v24.20.0, job 046 passed `npm run typecheck`, `npm run lint`, `npm test` (1227 Vitest tests in 90 files, none skipped), `npm run test:storage` (58 native storage tests), `npm run build` (Next.js 16.4.5) and Prettier on every changed file. No dependency was added, so `npm audit` was not rerun (it contacts the npm registry). Migration `0032_config_versions_install.sql` makes `tenant_context.install(text, text, text[])` also return `versions` and `documents`, read after every existing check and the context row, and raises the storage schema marker to 11 ([identity-boundary-plan.md](identity-boundary-plan.md#payload-fields)).

New and changed tests:

- `tests/config-store.test.ts`: on new `ConfigBodyCache` instances, entries are keyed by version id; a body whose hash does not match its text, a non-object and invalid JSON are refused, and one bad row stores nothing of its batch; 24 bodies of 512,000 bytes keep the total at or under 8,388,608 bytes (16 kept, the eight least recently used evicted), and a body over the cap is returned but not stored; a used entry survives eviction; cached bodies are deep-frozen. An install fails closed and caches nothing for a bad hash, a missing body or another object's body. Under the data role, `versions` holds exactly the workspace's non-archived current published versions of company objects and the context's own team's task boards (no archived, draft-only, retired, other-team or other-workspace entry), with verified bodies.
