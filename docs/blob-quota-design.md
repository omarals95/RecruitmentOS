# Blob quota design: proposed invariants

**Ledger implemented locally; Blob CV storage remains disabled.** Migration `0007_blob_allocation_schema.sql` implements the database side of these invariants. It has been tested only on PGlite with fictional data and synthetic roles, and has not been independently reviewed or run on Neon.

## Implementation status

Implemented locally:

- **Store-wide ledger.** The owner-only `storage_ledger.stores` table has one row per `(provider, store)` and covers every team's uploads. Its environment is fixed the first time the store is locked; a later lock with another environment is refused.
- **Approved budgets.** `storage_ledger.budgets` holds Production 600,000,000 bytes / 2,000 files and Preview 200,000,000 bytes / 500 files. Local development uses the Preview figures. Team limits in `app.storage_usage` are null by default and then inherit the budget of the store being charged. The old 10 GiB / 10,000-file defaults are gone.
- **Lock order.** `tenant_context.lock_storage_allocation` locks the store row, then team rows in team order, before any upload row is touched. Charges are taken by owner-run triggers on `app.uploads` from the row's own size, never from caller arguments.
- **Charges.** Each upload is charged its declared size plus one file on insert and settled once on its status change. `ready` moves the charge to used. A rejected or expired **Blob** ticket keeps it as retained, so store and team totals never decrease. A rejected or expired S3 reservation is still released, as before. Status may only move from `pending`, references are immutable, uploads cannot be deleted, and a pathname is never reused.
- **Store-wide S3 expiry.** Before any reservation, completion or cleanup on a bucket, the lock helper releases that bucket's expired S3 reservations for every team, so one team's abandoned tickets cannot hold the shared budget. It reads and updates other teams' rows through owner-only `ledger_owner_read` and `ledger_owner_update` policies, which never match a runtime role.
- **Owner-only accounting.** Neither runtime role can read or write `storage_ledger`, or insert, update or delete `app.storage_usage`; teams can still read their own usage row.
- **Blob upload, completion and download wiring**, behind a fake client only (WP-05). A failed ticket issuance keeps the committed charge and a replay reuses the same pathname. A missing object or a provider timeout at completion leaves the ticket pending; a content failure rejects it and retains the charge.
- **Pending S3 index.** Migration `0008_pending_s3_upload_index.sql` adds the partial index `uploads_pending_s3_expiry_idx` on `(storage_store, expires_at)` for the store-wide expiry scan.

Known limit for both S3 and Blob, a hosted-release blocker:

- Team limits default to the whole store budget, so one team can fill a shared store with live reservations (for up to an hour each on S3) or with completed CVs, and lock other teams out. Issuance is not rate limited. This already applies to the S3 path.

Remaining before Blob can be enabled:

- Cleanup, deletion and reconciliation of retained charges and stored objects. Retained charges are currently permanent, so abandoned Blob tickets are never released, by any team.
- Provider guarantees for one-shot, exact-path, no-overwrite capabilities and for late in-flight uploads (below).
- Live provider results for the wired upload, completion and download protocol. The real client exists (`src/lib/vercel-blob-client.ts`, built only by tests and the live script), and live results from `scripts/blob-live-verify.ts` are outstanding.
- Live Neon, multi-connection race and effective-privilege tests.

## Budget boundaries

- Configure a separate fixed byte and file budget for each store and environment. Set the sum of those budgets below the account's **remaining shared storage allowance**, after subtracting current usage in all other stores and leaving operational headroom. Preview and Production have separate databases, so neither database can atomically check a single account-wide counter; partitioning avoids relying on such a counter only while the partitions and outside usage are controlled.
- The allocation must include every team and every app-issued upload for its store. A per-team limit alone does not bound total store use. A transactional store-level ledger must be visible to the server-side quota operation across all teams, without exposing other teams' records or permitting a caller to modify aggregate accounting directly.
- Control and monitor other writers, including dashboard users, other deployments, integrations, and static read/write credentials. If they can write outside this ledger, the application cannot guarantee a physical store or account limit. On missing, invalid, stale or overcommitted budget configuration, refuse new tickets. Reconcile account usage and allocations before changing budgets or connecting additional stores.
- These budgets cover stored bytes and files only. Blob operations, data transfer and full-object reads used for verified chunked downloads consume separate quotas or billable resources; account plan restrictions and pricing must be checked independently. A budget is not a provider-enforced billing cap.

## Issuance and retained charge

1. Authenticate and authorize the request, validate the declared file size and type, then allocate a cryptographically unpredictable, unique pathname that is never reused. Bind the upload to its environment, store, team, candidate and actor.
2. In one database transaction lock the store usage row, then the team usage row, then the durable upload/ticket row in a consistent order. Reserve the full maximum permitted bytes and one file against both budgets; enforce database constraints against negative or overflowing totals and prevent concurrent oversubscription. Commit before issuing or returning any upload capability. A crash or uncertain issuance outcome must leave the full charge retained.
3. Persist the ticket/path and its reservation independently of short-lived request idempotency records. A retry for the same upload must preserve its original path and full charge and must not generate an untracked path or release budget. Limit issuance and retry frequency. No returned URL, callback, log, exception or database record should disclose the delegation signing secret.
4. Issue only a private, short-lived, exact-path, method-specific PUT capability with no overwrite, no random suffix, an approved MIME type and a maximum byte count no greater than the reservation. Do not give the client the delegation signing key, delete permission, a store-wide capability, or credentials for other paths. Vercel documents that the broader `put` delegation scope also covers multipart POST; provider behavior must establish that the specific URL cannot be repurposed for multipart uploads or leave unaccounted parts.
5. Completion must validate the exact received size and format. Transition to ready, rejected or expired idempotently under the same locking order. Transfer any charge from reserved to committed without decreasing the store/team totals. A short or rejected file is still charged its full ticket allowance until safe reclamation is established. Deleting a candidate, team, upload record, or account must not erase a live charge or permit path reuse.

## Candidate identity boundary

This is an unimplemented candidate architecture, not a claim of tenant isolation. A runtime SQL caller can set settings such as `app.team_id` and `app.user_id` to arbitrary values, so a quota function cannot authenticate a principal by trusting those settings or arguments, even when it verifies that the claimed user is a team member. Tenant row policies now use a signed per-transaction context instead ([identity-boundary-plan.md](identity-boundary-plan.md#signed-tenant-context)); quota commands still need the design below. A test-only function with that design was removed after review.

Signing the claimed values is not sufficient while the same role can directly modify authentication state. For example, a caller with runtime SQL execution can currently insert an `auth.api_tokens` record containing the hash of a chosen valid token, a victim's verified user and team, and `cvs:write`. The application would accept that token under the victim's existing membership and could then sign an apparently valid quota command. This scenario requires runtime SQL access or injection; no public HTTP exploit has been established.

One approach to evaluate is to separate recruitment-data access from identity and authorization mutations: give its database role only the minimum safe access to authentication state, and move the auth adapter and required account, membership, session and token mutations to separately constrained access. The runtime role must not be able to assume or inherit that identity-writing role. Narrow identity reads too: broad reads can expose other users' sensitive authentication state. The trusted signer must authenticate the current session or API token, verify team membership and `cvs:write`, and be unable to sign arbitrary caller-selected identities. This separation needs a full review of Better Auth, team management and token creation; applying it only to a quota function would not protect the other tenant data paths, which now rely on the signed per-transaction context. It is intended to address a compromised recruitment-data SQL role, not compromise of the trusted signer, identity service, database owner or application process.

After that boundary is established, a short-lived signed quota command could carry an unambiguous, domain-separated representation of the environment, store, operation, team, actor, session or token identity and scope, candidate, request or ticket ID, pathname, maximum bytes, MIME type, issuance and expiry, nonce and key version. The database verifier must act only on fields from the verified payload, reject missing, ambiguous or out-of-range values, and check time against the actual clock rather than a transaction-start timestamp. Review whether protected current membership, session or token state must be locked and rechecked for concurrent revocation. Assertions are bearer capabilities: prevent them and signing material from appearing in SQL bind logs, errors, application logs or client responses; assess capture and front-running risk. Keep signing keys separate per environment and rotate them under an approved operator process, without exposing key material to the shared runtime role.

The reservation operation must atomically consume a nonce and use immutable idempotency records that bind every security-relevant field. Replays, concurrent requests and changed-field retries must not create extra paths or charges. A legitimate retry needs a new verified assertion or a strictly defined same-request result. Commit the durable store and team charge before producing a storage URL; a rollback, crash or uncertain issuance must never release or erase a charge for a URL that may have been issued. Apply rate and resource limits, and define an audited recovery process that does not bypass these invariants.

Any privileged verifier requires a controlled non-runtime owner, a fixed safe search path, schema-qualified objects, and explicit checks for public, named, inherited and default-ACL grants on its functions, schema, key material and ledger. A possible implementation using Neon `pgcrypto` needs special scrutiny: PostgreSQL states that `pgcrypto` is not designed to resist side-channel attacks and relies on trusted database and system administrators and a secure connection. Test signature verification and error handling without claiming constant-time behavior that has not been demonstrated. See [Neon pgcrypto](https://neon.com/docs/extensions/pgcrypto) and [PostgreSQL pgcrypto security limitations](https://www.postgresql.org/docs/current/pgcrypto.html).

## Reclamation and unresolved races

A SQL caller on the runtime role can still set `app.team_id` and `app.user_id` to another identity; the application no longer relies on them, and membership checks against such supplied values do not prove who made the request. An isolated security-definer ledger based only on those settings would let a runtime SQL attacker consume another team's quota. The local ledger instead acts only on the team of the verified signed per-transaction context and requires its `cvs:write` scope, rather than a separately signed quota command; that choice is pending review. Token-scoped API requests must also enforce their scopes before any allocation; team membership alone is insufficient.

The conservative baseline is **never release the charge or reuse the path of an issued ticket**, including after expiry, rejection, successful upload, object deletion, or an uncertain network response. This may permanently consume the allowance and needs an operational recovery process. It is intentionally conservative, not a complete user-facing cleanup solution.

An expiry timestamp and a subsequent missing-object check do not prove that an upload started before expiry cannot finish afterward. Before reclaiming capacity, obtain and verify a provider-enforced cancellation or one-shot guarantee, or a documented bound on in-flight completion plus a cleanup and reconciliation process that covers that bound. Deletion must itself be idempotent and verified, and late completion, retries, cleanup failures, concurrent uploads, and uncertain outcomes must remain charged. Synthetic tests can find bugs but cannot prove undocumented provider behavior.

The retained-charge approach can bound application-issued allocation only if the provider guarantees and tests establish that each capability creates at most one object at the exact reserved path, cannot overwrite, cannot exceed its reserved maximum or initiate unaccounted multipart work, and cannot be used after deletion to create additional unaccounted storage. Other writers and existing objects must be included separately. Without those conditions and reliable aggregate usage controls, do not claim a hard physical storage or billing cap.

## Evidence required before enabling

- Transaction and multi-connection tests for competing teams, duplicate requests, retries, failures before and after commit, delayed completions, idempotent state changes, and store/team budget exhaustion.
- Synthetic provider tests for simultaneous same-ticket uploads, replay, overwrites, deletion and recreation, exact size/path/method constraints, multipart attempts, delayed in-flight uploads, and uncertain cleanup outcomes. Confirm behavior against provider documentation or support for any assumption tests cannot establish.
- Verify Preview and Production allocations, external usage, permissions and reconciliation against the real account without real CV data. Independently review the schema, row-level security, accounting functions, provider credentials and recovery procedure. Keep Blob disabled until the required guarantees are demonstrated.
- Verify effective permissions, inherited role memberships, ownership and existing PostgreSQL default ACLs on the actual Neon roles. Revoking `PUBLIC` alone does not remove grants to named or inherited roles.
- Test the SQL-level signer-oracle example, forged team/user settings, direct ledger and identity-table writes, assumed or inherited roles, changed signed fields, expired or duplicate nonces, revocation during reservation and identity/scope changes. None may allocate another team's quota. Exercise concurrent legitimate retries and quotas using independent live Neon connections, and verify owner-controlled role and key separation in each environment without real CV data.
