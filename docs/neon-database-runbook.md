# Neon database setup runbook

This is a preparation checklist. No migration, role creation, grant, credential rotation, or candidate-data import is performed by this document. Preview and Production use independent Neon resources. Work on Preview first, separately from Production, using fictional data only. The detailed, still-blocked Preview proposal is [preview-database-change-plan.md](preview-database-change-plan.md).

## Stop conditions

- The staged connection-boundary checks apply to the paired data/identity pool path. The legacy unhosted single-pool development fallback does not have equivalent URL or environment validation and uses the old shared-role model. Do not use it with real candidate data or treat it as evidence for deployment safety.
- Startup pool checks cover only the connections used for inspection. They do not validate every future checkout or reset a pooled session's role and settings after release. A trusted, fail-closed per-checkout identity/context and transaction-reset strategy, plus real pooler tests, are required before the hosted gate can be removed.
- The staged pool validator rejects URL parameters other than a single supported `sslmode`. In particular, it rejects `channel_binding=require`, which may appear in Neon connection strings: the installed driver has not been shown to enforce that URI requirement. Do not silently remove the parameter or claim channel binding is enforced; resolve and test the driver behavior before live connections.
- Do not run a migration or start the application until Vercel project linking and the required environment settings have been verified. The first administrator's email, setup token, authentication origin and secret, and verified email sender must be configured separately for each environment.
- Migration `0004_protect_initial_admin_claim.sql` restricts direct writes to `auth.initial_admin_claim`. The legacy shared-role fixture has been removed. The split runtime role template [postgres-split-runtime-roles.sql](../infrastructure/postgres-split-runtime-roles.sql) has been verified only on PGlite and a throwaway local PostgreSQL 18 cluster; it is not yet applied to, or approved for, any hosted database, and applying it does not open the hosted `tenant_isolation_pending` guard. Before deployment, independently review the migration's and the template's grant impact and test the protection using real, nonowner Neon roles; embedded tests alone do not prove live role or inheritance behavior.
- Do not attach an owner or migration connection as the deployed `DATABASE_URL`. The production startup guard checks elevated direct or inherited roles, broad predefined memberships, protected-object ownership, schema/database creation privileges and any table, column, sequence, function, schema or database privilege held WITH GRANT OPTION. It is defense in depth rather than a full privilege audit; independently verify effective permissions and test the actual Neon role.
- The runtime guard also refuses a missing protected schema or setup marker, or effective direct, inherited, or PUBLIC write privileges on that marker, including column grants. Checking for schemas and the marker does not verify the entire migration ledger or database schema. It runs only when the database pool is initialized; after any role, membership, grant or ownership change, review the effective privileges and recycle the deployments so the check runs again.
- Stop on unexpected project, branch, database, role, privilege, migration state, connection failure, or authentication behavior. Investigate before retrying. Never log, commit, or put connection strings, passwords, setup tokens, or verification links into chat.

## 1. Identify and prepare both environments

1. In the Neon and Vercel consoles, confirm that the Preview resource points to its own empty database and the Production resource to a different database. Verify project and branch identifiers as well as database names; do not rely on display names alone. Verify that any automated Neon preview branching cannot copy Production candidate data.
2. Confirm the existing Marketplace-injected `DATABASE_URL` role and ownership. Its name and existence do not establish that it is safe for runtime. Plan separate restricted data and identity logins and credentials within each environment; keep each migration-owner credential under separate operator control. The split-role grant template exists and is verified locally only; Neon provisioning, live role tests and the dependent application workflows are not yet done.
3. For each database, obtain its **direct, non-pooler owner connection** for the migration operator. `scripts/migrate.ts` takes a session-level PostgreSQL advisory lock; a transaction-pooled connection does not guarantee that later commands use the session holding that lock. Obtain a separate pooled connection for the restricted runtime role after it is created and reviewed. Verify TLS and hostname for both, without displaying connection strings.
4. Verify the exact environment-specific Vercel settings, including a stable exact authentication origin, independent auth and setup secrets, administrator email, and a working verified email sender. The values must be scoped only to their intended environment. Never put the owner connection in deployed environment variables.

## 2. Migrate one database at a time

1. First review the exact checked-out application revision and the ordered SQL files under `drizzle/`; compare them with the database's `public.recruitment_migrations` ledger if it exists. For any nonempty or previously used database, assess backups and migration compatibility first; the initial-admin migration deliberately closes setup for an existing user or organization.
   Migration 0004 changes the two setup trigger functions to execute as their owner with a fixed search path and removes direct marker-table write grants from PUBLIC and all nonowner grantees, cascading dependent grants. This also removes those writes from maintenance and operator roles, not just the app role; review their recovery workflows first. Existing databases need the new migration and updated grants applied by the migration owner. Preserve a controlled owner-only recovery process. No other table's privileges are intentionally changed.
2. In a controlled operator environment, provide only that database's direct owner connection as `MIGRATION_DATABASE_URL`. Confirm the existing `.env.local` or `.env` will not silently introduce a different database setting: `scripts/load-env.ts` loads one of these files. Confirm that `DATABASE_MODE` does not select PGlite. Do not copy a production owner credential into a local project file or any deployed environment.
3. After all prerequisites and the runtime-privilege design are approved, run `npm run db:migrate` once for Preview. The script takes a session advisory lock and records completed migrations in `public.recruitment_migrations`. Each migration runs inside its own transaction; earlier completed files remain applied if a later file fails. Inspect the ledger and actual schema before deciding on recovery; do not reset or rerun blindly.
4. Check that the expected migrations are recorded, the `auth` and `app` schemas exist, the `auth.initial_admin_claim` singleton and its triggers exist, and the intended `app` tables have row-level security and their expected policies. Check the actual installed revision rather than assuming any fixed migration count.
5. Only after Preview passes the role and application tests below, repeat the process against the distinct Production resource. Production migration must never use Preview's connection, or vice versa.

## 3. Runtime access and verification

1. Review the claim-table and trigger privilege changes first. Confirm both trigger functions are owned by the controlled migration owner, have the fixed safe search path, and execute the intended trigger operations; ensure the app role cannot assume or inherit the owner role. Verify initialization still works with the restricted runtime credentials before considering the migration safe.
2. Create each restricted runtime login **using SQL**, after independently confirming the project, branch and database. Neon roles created through the Console, API or CLI are granted `neon_superuser`; they are unsuitable as this app's restricted runtime login. Once the template is reviewed and approved for that database (it is not yet approved for any hosted database):
   - Run [postgres-split-runtime-roles.sql](../infrastructure/postgres-split-runtime-roles.sql) with psql as the migration owner over the **direct, non-pooler owner connection**: `psql -v ON_ERROR_STOP=1 -f infrastructure/postgres-split-runtime-roles.sql`. It creates `recruitmentos_data` and `recruitmentos_identity` as `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS NOREPLICATION` roles, refuses an existing role with other attributes or any membership, and grants the exact object-by-object matrix in one transaction. It also revokes CONNECT and TEMPORARY on the current database and all access to the `public` schema from PUBLIC and both runtime roles, then grants CONNECT only to the two runtime roles; the owner keeps its own access. Other roles that relied on PUBLIC CONNECT to this database lose it. If PUBLIC still has access afterwards, for example because the runner does not own the database or the `public` schema, the template refuses and rolls back. The role names are the same in each environment's separate database; credentials are distinct.
   - The template closes only the application database. As the owner of each other database on the branch or cluster, or an administrator, run `REVOKE CONNECT ON DATABASE postgres FROM PUBLIC;` and the same for every other database that accepts connections apart from the application database (for example `template1`), and grant CONNECT on none of them to either runtime role. A REVOKE by a role that does not own the database only warns, so confirm afterwards that the evidence script reports no `can connect to database` drift. If the operator cannot close a database, stop and raise it in the Neon provisioning review; do not weaken the check.
   - On PostgreSQL 16 and later, a `CREATEROLE` owner that creates a role is automatically granted membership in it with ADMIN OPTION. The migration owner can therefore alter, drop and reset the password of the runtime roles, grant them to other roles, and grant itself `SET` on them (the automatic grant has no `INHERIT` or `SET` unless `createrole_self_grant` is set). This is operator-level access, and it is accepted: the owner already owns every protected object. It runs in that direction only: neither runtime role becomes a member of the owner, and the template and evidence script refuse any runtime role membership.
   - Set each password separately in psql with `\password recruitmentos_data` and `\password recruitmentos_identity`. Never put a password in the template, SQL history, shell history, logs, source control, or a shared document. Neon documents password reset for existing roles, but verify that the chosen secure method works for a SQL-created role before relying on it.
   - Rerun the template after every migration. A rerun revokes and regrants the matrix, so it removes any extra privilege, grant option included, on the protected schemas and their objects, the `public` schema and the application database. It does not touch parameter, type, language, foreign-data wrapper or server grants, role settings or other databases; the evidence script reports those, and the operator removes them. New owner tables, sequences and functions are unusable by both runtime roles and PUBLIC until the template is updated for them.
   - Run the read-only evidence script with each runtime connection, from a controlled operator environment: `DATABASE_URL=<data role connection> IDENTITY_DATABASE_URL=<identity role connection> npx tsx scripts/db-role-evidence.ts`. It reads only those two variables (never `.env.local`), uses `sslmode=verify-full` for non-loopback hosts, runs every query in a rolled-back `READ ONLY` transaction, and prints one JSON document with role attributes, memberships, effective grants, default privileges, what PUBLIC holds, CONNECT on every database in the cluster, grant options, other ACL entries, per-role settings, the safety and boundary check results, the database name and whether the connection markers match. It never prints passwords, URLs, hosts, ports, setting values or the marker value. It compares each role with the matrix it parses from the template and lists every difference under `drift`. It checks exactly these classes:
     - role attributes, and membership in any role;
     - CONNECT, CREATE and TEMPORARY on the application database, extra or missing, and CONNECT on any other database that accepts connections;
     - USAGE and CREATE on every schema outside `pg_catalog`, `information_schema` and `pg_*`, extra or missing;
     - effective table, view, sequence and column privileges (TRUNCATE included) and EXECUTE on functions in those schemas, extra or missing. Anything outside the matrix that a runtime role can use, such as an extension function, counts;
     - any table, column, sequence, function, schema or database privilege held WITH GRANT OPTION, directly or through a role it belongs to, in any schema or database;
     - explicit grants to the role, or a role it belongs to, on types, languages, foreign-data wrappers and foreign servers, and PUBLIC grants on foreign-data wrappers and foreign servers. PUBLIC USAGE on types and trusted languages is the PostgreSQL default and is not reported;
     - any parameter privilege (`SET` or `ALTER SYSTEM`, PostgreSQL 15 and later) granted to the role, a role it belongs to, or PUBLIC, for any parameter, `session_replication_role` included;
     - settings stored for the role in `pg_db_role_setting` (`ALTER ROLE … SET`), in any database;
     - explicit default privileges for the role or PUBLIC; PUBLIC CONNECT or TEMPORARY on the application database, PUBLIC access to the `public` schema, and PUBLIC EXECUTE on the owner's future functions.

     It does not check large objects, the default PUBLIC privileges on `pg_catalog` and `information_schema` objects, the content of row-level security policies, database-wide settings (`ALTER DATABASE … SET`) or server configuration such as `pg_hba.conf`; review those separately. Exit code 0 means every check passed and nothing drifted, 1 a failed check, any drift in the classes above, or a connection error, 2 refused configuration.

   - Independently inspect the effective role attributes, inheritance and ability to `SET ROLE`, including indirect membership in `neon_superuser`, `pg_read_all_data`, `pg_write_all_data`, and server-file/program roles. Check that the login cannot create roles or databases, replicate, bypass RLS, own or assume ownership of protected schemas, tables, sequences or functions, or create objects in those schemas. Review new tables and grants on every future migration.
3. Only after the implementation, migration, effective grants and any required approvals are complete, configure the Preview data role's pooled connection as Preview `DATABASE_URL` and the Preview identity role's pooled connection as Preview `IDENTITY_DATABASE_URL`. First inspect integration-managed settings and their update behavior; do not blindly overwrite them. Ensure no application runtime setting contains an owner connection. Verify variable names and scopes without printing values. Do not assume that a Vercel integration's initial connection already uses a restricted role.
4. Before real use, verify with synthetic data and the actual runtime connections: initial-admin creation and verification; interrupted setup and replay; concurrent setup attempts; isolation between two teams; RLS denial without the proper team context; expected access within a team; and inability to alter schema or bypass the protected setup state directly. Verify Preview credentials cannot connect to the Production resource and vice versa. Include multi-connection tests against Neon, because in-memory tests alone cannot prove live concurrency behavior.
5. Confirm application startup uses the intended runtime roles and that errors, logs, build output, and support reports contain no credentials or candidate contents. Keep both databases isolated and avoid importing real CV data while testing.

Reference: [Neon connection pooling](https://neon.com/docs/connect/connection-pooling), [Neon roles and managed privileges](https://neon.com/docs/manage/roles), [limited database access](https://neon.com/docs/manage/database-access), and [deployment guidance](deployment.md).
