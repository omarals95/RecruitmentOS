# Using RecruitmentOS

## Start your day

Sign in with your verified email/password, or a configured Google/Microsoft provider. Select your team in the sidebar. **Overview** shows actual candidate, vacancy and workflow counts, upcoming interviews, overdue tasks and recent recruitment activity. Overdue tasks exclude tasks in buckets marked **Counts as completed**. The **Team tasks** count also excludes them; its caption reads "Tasks not in a completed bucket". The **Open vacancies** count includes only vacancies with status Open. Candidate counts describe people; CV counts describe uploaded ready files and can differ. Dark, light and system themes are available in the top bar.

Use the top-bar search (Ctrl/Cmd+K) to find candidates, vacancies, roles and tasks. Search can use a quoted phrase or exclude a word with `-word`. Your team determines which records you can access.

## Candidates and source records

Open **Candidates** to search/filter facts, skills, certifications, source-folder categories, education, experience and review status. Review status is one of two values: **Needs review** (the default for a new candidate) or **Reviewed**; the editor and the **Review status** filter on **Candidates** and **My shortlist** offer only these. **Source review** always shows the candidates that need review, so it has no review status filter. Older free-text values were mapped once: "Verified", "Reviewed", "Complete" or "Completed" (any case) became Reviewed and anything else Needs review; imported source text is kept unchanged in the original source fields. **All of these skills** and **All of these certifications** match candidates holding every listed value, ignoring upper and lower case and surrounding spaces: "react" finds candidates with "React". As you type, each of these inputs suggests the skills or certifications already recorded on your team's active candidates, most common first; a value that differs only in case from one you already chose is not added again. **Education contains** matches text in the degree name, major or university. **Minimum/Maximum stated experience (years)** match the CV-stated years only: a candidate without stated experience is never included in a range, and the filter bar says so. Folder categories reproduce the folders used during import; they do not independently assess job suitability. Missing facts remain missing. When filters leave nothing to show, the list says "No records match these filters" with a **Clear filters** button; **Source review** says "Nothing needs source review" when every candidate has been reviewed.

Open a candidate for education/contact details, source evidence, CVs, related applications and team tasks. The **Interviews**, **Offers** and **Onboarding** tabs list those records from all of the candidate's applications; each interview and offer row also says which application it belongs to ("For {candidate} · {vacancy}"). These tabs have no Add button: add interviews, offers and onboarding from one of the candidate's applications. The **Tasks** tab lists the candidate's active tasks with priority and due date; **Add task** there starts a task already linked to the candidate. Use **Create hire task** to add a task linked to this candidate and, optionally, a vacancy. Use **Assign to vacancy** or the directory's multi-select vacancy action to create applications. Creating a task does not create an application or change a hiring stage. A linked record that was archived shows its name followed by "(archived)"; one you cannot open shows "Unavailable record".

The **My follow-up** area and shortlist are private to your account. Use **Discussion** for shared comments. Save forms explicitly. When a record changes elsewhere, a conflict keeps your draft so you can review the latest version before retrying.

Upload CV files from the candidate's profile after private storage is configured. Until storage is set up, the CV area and **Import CVs** explain that CV uploads are not set up yet and show no file picker; candidate details can still be added and edited. Files upload directly to private storage, then undergo format checks before a download is available. A file's source path is relative historical metadata. In the cloud, Open/Download uses a short-lived private link; it cannot open Windows File Explorer. Multiple CV references can belong to the same candidate.

**Import CVs** on **Candidates** adds several new candidates, each with its CV, once private storage is configured. It works wherever single CV upload works; until then the dialog only explains why import is not available. Before you choose files it states the limits: up to 200 files per import, 10 MiB each, one CV upload at a time in this browser, and import progress kept on the server for 24 hours while the selected files and drafts stay only in this browser. Choosing more than 200 files adds only the first ones and says how many were not added. The selected CVs are listed 25 at a time with **Previous** and **Next**; the list shows the page of the CV you review or the one being imported. AI extraction is not configured, so enter each candidate's details from the CV yourself, check for possible duplicates and confirm both review boxes; the server checks those confirmations again, and if the possible duplicates changed since your check it asks you to check again before importing. If an approved AI service is connected in a later release, the dialog will show what is sent and to whom, ask for your consent, and label every suggestion as unverified until you accept, reject or edit it. Import always creates a new candidate: it cannot attach a CV to an existing candidate, so attach a CV to an existing candidate from that candidate's profile. While an import runs, **Cancel import** stops it after the current request; candidates already created stay in your directory. Another CV upload in a different tab of the same browser must finish first; a browser without the needed locking support cannot upload CVs. If your session, permission or storage setup is lost, the import stops before the next CV and the remaining CVs stay "Not started". If your team's CV upload rate limit is reached, the import pauses before the next CV: wait a minute, then select **Import reviewed** again to continue with the remaining CVs. When an import ends, an **Import summary** lists every selected file under Imported; Candidate created, CV pending; Not imported; Failed; or Outcome unknown. Retry an unknown or pending item with its unchanged draft; this never creates a second candidate. If a CV was rejected or its upload expired after the candidate was created, **Retry import** uploads the same selected file again; to attach a different file, open the candidate and upload it from the profile. A create whose result is uncertain cannot be retried once 24 hours have passed since the import started. **Recent imports (kept for 24 hours)** lists your other imports from the last 24 hours, ten at a time with **Previous** and **Next** when there are more (a later page that empties as imports expire offers **Go to first page**), with each file's outcome (25 at a time per import when it has more) and a link to its candidate; for "CV pending" or "CV rejected" open the candidate to attach the CV. Selected files are not kept, so a recent import cannot be resumed there. After 24 hours an import's progress is gone: check the candidate directory before importing those CVs again.

Use **Source review** to work through incomplete/ambiguous extraction information. Review evidence before correcting facts. The application does not infer sex/gender, national service completion, nationality or residence from a name or photo.

**Export** saves every record matching the current filters as `RecruitmentOS-{list}-{date}-{time}.csv` (Asia/Dubai time). The server builds the file from one consistent read of the records, so the row count always matches the rows. The file starts with labels: the list (for example Candidates; My shortlist and Source review appear in the filters as "My shortlist only" and "Needs source review"), when it was exported (Asia/Dubai), the environment (Production, Preview or Local development), the filters used, the row count and a data-protection notice, then a blank line and the usual columns. An export of more than 100,000 records is refused; narrow the filters instead. Every export is recorded in **Activity** (record type **export**): who exported, when, which list, how many rows and which filters were used, but never the filter values or search text. If that record cannot be written, no file is produced. Exports contain personal data and need the same care as the source CVs; store and share them only as your team's data-protection rules allow.

## Roles, vacancies and applications

Create reusable **Job roles** with title, department, description, requirements and skills. Create a **vacancy**, optionally copying a role's details into the draft; only vacancies with status Open count as open. The **Vacancies** screen lists every vacancy, from draft to closed. Changes to a role do not silently rewrite existing vacancies. To bring later role edits into a vacancy created from a role, open the vacancy and select **Review changes from role**. It lists each role detail that now differs, with the vacancy's and the role's current values, all unticked. Tick the ones to copy and select **Apply selected changes**; nothing else changes. If the role was archived, its details can no longer be copied.

**Org unit of a vacancy.** A vacancy can belong to one unit of your company's organisation. In the vacancy editor, the **Org unit** section shows the vacancy's unit as "Name (CODE)", or "No org unit". Choose a unit with **Choose an org unit**: the list shows the top units first, then the units below the one you chose. **Remove org unit** takes the unit away. The change is saved with **Save changes**; if the unit is no longer a current unit of your company, the editor says so next to the unit and saves nothing. Its applications, interviews, offers, onboarding, checklist items and comments follow the vacancy's unit. The unit decides which vacancies members with a role limited to their org unit see; exports, search results and connected AI apps never show it.

**Job title of a vacancy.** In the vacancy editor, **Job title** lists the titles of your company's published job architecture by name, each with its grade ("Fictional Payroll Lead · G7"). Under it the editor shows the chosen title's grade ("Grade: G7 · Senior"). People a company owner has given **Plan & pay access** also see the grade's salary bracket ("Salary bracket: AED 12,345 to AED 18,000 a month, midpoint AED 15,000.50 · basic salary only · version 2"), "No salary bracket for this grade." or "No salary brackets are published yet."; nobody else sees a figure, and their page never asks for one. A vacancy without a title offers **No job title**; once a title is saved it can be changed to another title but not removed. The change is saved with **Save changes**. A saved title that a later version of the job architecture removed stays selected as "<key> (not in the published job architecture)" and is kept when you save other changes. A title removed from the published version while the editor was open is refused next to the picker with "This job title is not in the published job architecture. Choose another job title." With no published job architecture the editor says "No job architecture is published yet, so no job title can be chosen." A role whose field rule hides the job title shows no picker, and a read-only rule shows the title and grade as text.

Use **Applications** to link a candidate and vacancy. Move the application through the pipeline explicitly. Without a vacancy filter the board shows the current page only. Choose a vacancy in the filters to see its whole pipeline: the board then loads every matching application of that vacancy, the column counts add up to the total, and the footer reads "{n} matching applications · board shows all of them". A vacancy with more than 1,000 matching applications is not shown as a board; use **Show as table** or narrow the filters. If the pipeline changes while it loads, the board says so; refresh to see every application. Dragging has a keyboard-accessible Move alternative. If someone else changed a card since the board loaded, your move is not applied: the board reloads the latest version and explains what happened, and **Move to … again** repeats your move on the latest version (or **Dismiss** leaves it). Application stage, vacancy status, task bucket, offer status and onboarding status are separate choices. Marking an offer accepted does not automatically mark an application hired, and changing a vacancy's status leaves its applications as they are.

## Team tasks

Use **Tasks** (shown as **Team tasks**) for your team's workflow. Add and reorder buckets; choose their names and colours. A bucket is a task's status. Tick **Counts as completed** on a bucket whose tasks are finished: those tasks no longer count as overdue and give no reminders. New teams get a **Done** bucket with the box ticked. Existing teams' buckets named Done were ticked once by the upgrade; tick the box yourself on any other finishing bucket. Add custom fields (text, number, date, dropdown, checkbox) and choose which are required. Archiving a field retains old values. Archiving a populated bucket asks for a destination and moves every active task in it together, including tasks your role does not show you; at least one bucket must remain. Only a member whose role shows all team tasks can archive a bucket: anyone else is told "Your role sees only some tasks, so you cannot archive a bucket. Ask a colleague who sees all tasks."

Custom values are checked when you save. An archived field's value is kept: you cannot change or remove it. A field that becomes required does not stop you editing older records that leave it empty, but once a required value is filled it cannot be emptied. This applies to team task fields today, and to company custom fields on every kind of record once they can be published.

Forms and record details follow your company's screens: a create screen, an edit screen and a view screen for each kind of record, optionally one per record type, each with its own sections, field order, hidden fields and required fields. A field hidden on a screen keeps its saved value when you save. A field marked required on the create screen must be filled to create a record, and a required field that is already filled cannot be emptied when you edit. Fields a company publishes in **Admin portal > Fields** (see **Fields** under Team and account settings) apply at once to saving and exports: export columns take their published names in the published view screen's order, and a field published as required must be filled when a record is saved. Forms and record details in the app still show the built-in fields, in the built-in order and with no inputs for custom fields, until a later release shows the published ones.

Tasks can link candidates and vacancies, or retain a free-text context. Set an owner, due date and priority. The owner stays a free-text label; assignees are the team members the task is assigned to.

**Assignees.** In the task editor, **Assignees** lists your team's members by name, each with a checkbox, and **Filter members** narrows the list. A task takes up to 10 assignees; the editor shows "N of 10 selected" and, at 10, the remaining boxes are unavailable. Only members of the team can be chosen. A person who has left the team stays on the task as **Former member** and cannot be removed. If your role shows only some tasks (your org unit or assigned records), you cannot add or remove yourself: ask a colleague who sees all tasks. Assigning a task to someone whose role shows only assigned tasks lets them see it. Saving the task changes the assignees only when you changed the selection. The board card and the task's details show "Assigned:" with the names; if the member list cannot be loaded, the editor says so and only the assignee list is unavailable.

**Linked records.** **Linked record type** links a task to one job role, vacancy, bucket, custom field or other task, chosen with **Linked record**; **None** removes the link. Links to candidates, applications, interviews, offers, onboarding and checklist items are not available yet, because erasing a candidate would then have to change these tasks too. You can only link a record your role lets you see. The card and the task's details show "Linked record:" with the record's type and name, "(archived)" for an archived record, or "Unavailable record" when your role does not show it. A link does not change who can see the task.

**Assigned to me.** Tick **Assigned to me** in the Tasks filters to show only the tasks assigned to you, on the board and in the table. While it is on, **Export** is unavailable and says "Turn off Assigned to me to export.": an export cannot use this filter. Exports never contain assignees. Edit or move cards with buttons as well as dragging. Quick moves show at once: a moved card appears in its new column straight away while it saves, and its move control stays unavailable until the save finishes. If the save fails, the card goes back to where it was with a message saying the move was undone. The same applies to application stage changes, archiving and restoring, your private follow-up and marking reminders read. Tabs you have opened show their last data immediately when you come back and refresh in the background. Saved views retain filters so frequently used searches are easy to revisit; views are private to your account.

**Task boards.** A task board shows some of your team's buckets as its columns, in an order you choose, and can keep only the tasks of one vacancy, of one linked record, or with one value of a dropdown custom field (for example a fictional "Project" field). Choose a board in **Task board** in the Tasks toolbar; it works with every view and by keyboard. **All buckets**, always first, is every active bucket in position order with no filter: the board every team has, which cannot be changed or retired. With another board chosen, the list and the board show only the tasks in its buckets that match its filter, still only the tasks your role lets you see, and a card moves only between that board's columns. A bucket archived since the board was made has no column; if none of a board's buckets is active, the board says so. While a board other than All buckets is chosen, **Export** is unavailable and says "Choose All buckets to export.". Your choice lasts until you leave the screen. If the board you chose is retired, the screen goes back to All buckets and says "The task board you chose is no longer available, so All buckets is shown." A bucket marked **Counts as completed** keeps its effect on overdue tasks, the Overview count and reminders whichever board you look at, and boards never change a task, bucket or custom field.

Team owners and admins make boards on the **Task boards** tab of the team's detail page, **Admin portal > Teams > the team > Task boards** (see **Team detail** under Team and account settings); recruiters and viewers, and company authority without the team role, cannot open it, and API tokens cannot change boards. **New board** asks for a name (the board's key is made from it, so choose a name no other board of the team has used, retired boards included), the buckets as checkboxes with **Move up** and **Move down** for the ticked ones' order, and **Filter tasks by**: None, Vacancy, Linked record (a type, then the record) or Task field (one of the team's dropdown fields, then one of its values). **Save draft** keeps it as a draft; the list shows each board's name, key, state ("Draft", "Published (version N)" or "Published (version N), draft in progress"), columns and filter, with **Edit draft** and **Publish**, or **New draft** once published. A board appears in Task board when it is published. **Retire board** asks you to confirm and takes the board off the Tasks screen for good. A board can only name active buckets, records and fields of your team that you can see; anything else is refused in plain words next to the form or row, and nothing is saved. Every draft, publish and retirement appears in **History** as "Task board: <key>", for company owners and admins of the same team only. Another team never sees or changes your boards.

## Interviews, offers and onboarding

Schedule interviews against an application, with interviewer, duration, location or meeting URL. Calendar dates/times display in **Asia/Dubai (UTC+4)**. Use day, week, month or list views and update completion/cancellation manually. A month day shows its first 3 interviews and a week day its first 20; when a day has more, a **+N more** button opens that day's view with all of them.

Track offer amount/currency, pay period, dates, status and decline reason separately from the application stage. **Activity** shows each offer status change as two badges, for example Draft → Sent. Onboarding links to an application and contains document, orientation, training or other checklist items. Progress uses complete/waived items out of configured active items; an empty checklist is not automatically complete.

Notifications collect due tasks, interviews, expiring offers, vacancy targets and onboarding items. Tasks in a bucket marked **Counts as completed** give no reminders. Marking visible reminders read affects your account. Analytics distinguish current inventory from changes actually observed by RecruitmentOS. Imported records do not invent old transition dates or time-to-hire values. **Hiring analytics** states the range it shows, for example "Showing observed activity from 6 Oct 2026 to 4 Nov 2026 · Asia/Dubai (UTC+4)"; without a chosen range it is the last 30 days. **Export statistics** starts its file with the same date range, the timezone, the export time and the environment.

## Team and account settings

Personal settings hold three sections, for everyone: **My profile** (your name, password, two-step sign-in and signed-in devices), **API tokens** (your own tokens and connected apps) and **About**. After them, an **Admin portal** link shows for anyone who can open at least one Admin portal page (see **Admin portal** below). Team settings live in the Admin portal: owners and admins of a team manage it on its detail page, **Admin portal > Teams > the team** (see **Team detail** below). **Team & access** (`/app/settings/team`, also reached by **Team & settings** in the sidebar) is now only for people who are not an owner or admin of the current team, and for creating a first team: it lists your teams with **Open team** to switch, the current team's name and your role, the team's member list (read only; a company owner also sees the **Configured role** column) and **Create a team** when you may create one. An owner or admin of the current team who opens it goes to the **Members** tab of the team's detail page instead.

Owners/admins manage team details, invitations and permitted membership changes on the team's detail page. Only owners manage ownership; a team retains at least one owner. Only the initial administrator and people who own a team can create another team (up to five); for everyone else the **Create a team** form is hidden, and someone who has not joined a team yet is asked to accept the email invitation from their team owner. Recruiters work with recruitment records; viewers read them. Team switching changes the active workspace. If you have unsaved changes (an open editor, a follow-up or comment draft, or unfinished CV imports) or a save is still running, the sidebar team picker first asks **Switch team?**. **Stay in {team}** keeps everything as it was; **Switch team** discards the drafts, stops waiting for running saves, and the new team shows a notice naming the team you left. A save that was running may or may not have completed, so check that team before redoing it. Changing a member's role, removing a member, revoking an API token, signing out a device and closing or removing CV import drafts also ask for confirmation in the same kind of dialog; Escape or **Cancel** changes nothing.

**CV storage settings.** Owners and admins see the **CV storage** panel on the **CV storage** tab of the team's detail page (**Admin portal > Teams > the team > CV storage**) with the team's current usage: stored CVs, uploads in progress and files waiting for cleanup, in decimal MB and GB (1 MB = 1,000,000 bytes). **Limit this team's CV storage** sets a maximum storage (MB or GB, up to 3 decimal places) and a maximum number of CV files; **Limit CV upload requests** sets how many new CV uploads the team may start per minute. Both are off by default, and **Save** records each change in Activity as "Updated CV storage settings". A limit below current usage is allowed: existing CVs stay available, but new CV uploads are refused until usage is below the limit. **Connected AI apps can read CV contents** is on by default: apps connected through MCP with CV permission can then read the text of the team's CVs, and each read is recorded in Activity on the candidate. Turn it off and select **Save** to stop every connected app from reading CV contents; the change is recorded in Activity as "Changed whether connected AI apps can read CV contents". These are application limits, not hard provider caps; the store-wide budget set by the RecruitmentOS owner still applies. Rejected or abandoned uploads count as files waiting for cleanup until they are deleted, a little while after their upload time ran out.

**Speed.** Owners and admins see the **Speed** tab of the team's detail page (**Admin portal > Teams > the team > Speed**). It lists how long common actions (moving a task, changing a stage, opening each main tab, opening and saving a candidate, scheduling an interview) and API requests take for your team, as the typical time (median) and the slow time (95th percentile), with the number of samples and, for API requests, the database time. It holds the last 30 days of timings and route names only, with no names, ids or content, and has no settings to change. Recruiters and viewers who open the old address `/app/settings/speed` see that only owners and admins can view speed timings; owners and admins of the current team who open it go to its **Speed** tab.

**Organisation levels and units.** Your company's structure is built from levels and units. A level is a layer such as Company, Division or Department: the top level has depth 0, and a company has at most 8 levels. A unit, such as Sample Division, sits on one level, either at the top or under a unit on a higher level; each unit has a name and a code that no other current unit uses. A company owner, or a company admin with the organisation area, creates and renames levels and units and archives a level no unit uses. Only a company owner moves or archives a unit, because who can see a record follows the unit it belongs to and the units above it (for roles limited to an org unit), so a move or archive changes who sees those records. A unit with current units below it cannot be archived; move or archive those first. Archiving is permanent. Every change appears in Activity. There is no screen for this yet: the changes are made through the organisation routes in [API examples](api-examples.md#organisation-levels-and-units), which need a signed-in session.

**Configured roles.** Besides the four team roles, a company can define its own roles, each a narrower version of admin, recruiter or viewer: for example a recruiter who cannot upload CVs. Only a company owner can give a member such a role, or take it away; team owners and admins, company admins and API tokens cannot. Giving the role also sets the member's team role to the role's level (admin, recruiter or viewer) when a team owner or admin could make that change; otherwise the role is saved and the narrower of the two applies until the team role is changed on the team's **Members** tab in the Admin portal. Taking the role away leaves the team role as it is. A member keeps only what both their team role and their configured role allow, and a configured role that is later archived or changed so it cannot be used gives the member no access until a company owner gives them another role or takes it away. Team owners always keep the Owner role. A role can also limit the records a member sees to their org unit or to records assigned to them (see **Roles & permissions** below); such roles, including copies of the hiring manager and interviewer templates, are given like any other. A company owner gives or takes away a role on the **Members** tab of the team's detail page in the Admin portal (see **Team detail** below), or, in a team where their team role is recruiter or viewer, in **Team & access**: the **Configured role** column of the member list has, for each member who is not a team owner, a list of the published roles that can be given ("Team role only (no configured role)" takes the role away) and **Save configured role**, which asks you to confirm. Team owner rows say "Team owners keep the Owner role". Nobody else sees the column. A member whose role has been archived or unpublished shows **Role no longer available** with the role's name: choose another role and **Save configured role**, or **Clear role**. Until then that member is refused every page and action with "Your role is no longer available. Ask a company owner to choose a role for you." If the role is saved but the team role could not be changed, the page says so; try again, or ask a team owner or admin to check the team role. Every assignment is recorded for the company owners, who see the last seven days of assignments in **Recent access changes (last 7 days)** on the **History** tab of the Admin portal, and activity about company structure and roles appears in the activity list only for people with company authority.

**Admin portal.** The Admin portal, at `/app/admin`, brings together the settings you manage. The **Admin portal** link in personal settings shows for anyone who can open at least one of its pages, a company owner or admin whose team role is recruiter or viewer included, and for nobody else; it stays hidden while your access is loading. Opening `/app/admin` shows the **Admin home**: one card for each page you may open, with its name, one sentence about it and a link to it, under the name of its group. A sidebar beside the page (above it on narrower screens) lists the same pages in groups: **Overview** holds **Admin home**; **People** holds **Users**, **Teams**, **Organisation** and **Directory**; **Access** holds **Company authority** and **Roles & permissions**; **Configuration** holds **Fields**; **Integrations** holds **API tokens**; and **Monitoring** holds **History**. A group with no page you may open is hidden, and the groups for later pages (Look & feel and Communication) do not appear yet. The page you are on is marked in the sidebar in bold with a bar at its start. The portal shows only the pages you may open. **Users**, described below, shows for company owners and for company admins given the People area, whatever their team role; a team role alone, even owner, never shows it. **Teams**, described below, shows for team owners and admins and for company owners and admins; from it, each team you own or administer opens its own detail page. Team owners and admins see one team page, **API tokens**: a short description and a button to **API tokens** in personal settings. A team's members, settings, CV storage, speed, task boards and activity are tabs of its own detail page under **Teams** (see **Team detail** below); company authority never shows them. Company owners and company admins also see **History**, whatever their team role; a team role alone, even owner, never shows it. **Configuration history** lists the company configuration changes made in any team of the workspace, newest first, 25 at a time with **Show older changes**: the time, the change (Draft created, Published, Retired, Archived or Layout changed), what was changed (for example Workflow or Record fields, with its key), the version and who made it. It never shows the configuration itself. Company owners also see **Recent access changes (last 7 days)**: role assignments and home-unit changes in every team, with the members affected (named when they are in your current team, otherwise shown as "A member of another team"), the role and who made the change; when there were more changes than the list can hold it says only the latest changes are shown. Company owners also see **Company authority** and **Roles & permissions**, described below; company admins and team owners do not. **Organisation** shows for company owners and for company admins given the Organisation area, whatever their team role; a team role alone never shows it. **Directory** shows for anyone whose role includes viewing the directory, which today means team owners and admins (and configured roles copied from the Admin template that keep it). Both are described below. If you have no page, or open a page you may not use, the portal shows only "You do not have access to this page", with no sidebar; this is checked on the server before the page is shown. The other company configuration pages arrive in later releases.

**Teams.** **Admin portal > Teams** (`/app/admin/teams`) shows for the owners and admins of your current team, and for company owners and company admins whatever their team role; recruiters and viewers without company authority see "You do not have access to this page". It is decided on your current team: an owner of another team who is a recruiter in the current one switches teams first. The table lists, by name, each team's name, identifier, created date and **Your access**: Owner, Admin, Recruiter, Viewer, or "Not a member". A team owner or admin sees the teams where they are owner or admin. A company owner or admin also sees every other team of the company: a team they are not in shows "Not a member", and one where they are a recruiter or viewer shows that role. **Open** on each team you own or administer, your current team or another, opens that team's detail page, described below, without changing your current team. Any other row has no button or link: company authority never shows another team's members, member count, records, storage or activity. **Create a team** sits under the list, as in **Team & access**, for the initial administrator and for anyone who owns a team: it takes the same team name and identifier, creates the team in the company, makes it your current team and opens its Overview. Creating a team makes you its owner and gives you no company authority. If the team is created but its task board cannot be prepared, the page says so and the list reloads.

**Users.** **Admin portal > Users** (`/app/admin/users`) shows for company owners and for company admins given the **People** area, whatever their team role; anyone else, team owners and company admins without People included, sees "You do not have access to this page". It lists everyone in every team of the company, including teams you are not in, and everyone with a pending invitation to one of them, by name (by email for an invitation). The columns are **Name**, **Email**, **Teams** (one line per team of this company: the team, the team role and, when the person has one, their configured role, for example "Fictional Studio · Recruiter · Sourcer"), **Company level** (Company owner, Company admin or None), **Status** (Active, Invited or Deactivated), **Last sign-in** and **Two-step** (On or Off). Last sign-in is when the person's newest stored session began; sessions end at sign-out, so it shows "Not recorded" when none is stored. An invited row shows "Invited" as its name, the teams it was invited to with the invited role ("Role not recorded" when the invitation names none), "Not signed in yet" and Off; an expired, accepted or cancelled invitation does not appear, and neither does an invitation to someone who is already in a team of the company. Filter by **Team**, **Status** (Active, Invited or Deactivated), **Company level** (including "No company authority") and **Configured role**, then **Apply filters**; the list then starts again with the first people for those filters. It shows 25 people at a time with "Showing N people" under the table; **Show more** adds the next 25 and disappears once everyone is shown. The list shows names, emails, teams and roles only: never a team's records, candidates, CVs, storage or activity. Each person's name opens their detail page; an invited row has none. Under the list, **Invite to teams** invites one email address to several teams at once (see below). Deactivating, signing out everywhere and clearing a sign-in lockout are on each person's **Security** tab (see **User detail**); the list has no bulk actions, and groups and bulk invite arrive in later releases.

**User detail.** A person's page (`/app/admin/users/<id>`) opens for the same people as **Users**; anyone else sees "You do not have access to this page", and a person who is in no team of your company shows "This person is not in any team of your company.". It shows their name and five tabs; the arrow keys, Home and End move between them, and `?tab=` (`profile`, `teams`, `authority`, `security` or `activity`) opens one directly. **Profile** shows the name, email, status (Active or Deactivated) and last sign-in. **Teams & roles** lists each team of your company they are in, with their team role and their configured role, or "Team role only". **Company authority** shows their level, areas, Plan & pay access, since when and whether it is suspended, or "No company authority". It is read only: a company owner sees **Change on Company authority**, which opens the **Company authority** page; anyone else sees "Only a company owner can change company authority.". **Security** shows the person's **Status** (Active or Deactivated), whether two-step sign-in is on and how many devices are signed in (sessions that have not ended or expired). For a deactivated person it adds "Deactivated: this person cannot sign in, and their sessions, API tokens and connected apps are refused. Their teams, roles and history are kept." **Reset two-step sign-in** shows only when the person is not you, has two-step sign-in on and is in a team you own as team owner; it works as in Team & access: you confirm, you may be asked to confirm it's you, and the person is signed out everywhere. Below it are the account actions. A company owner sees them on anyone else's page; a company admin with People sees them only for a person without company authority, and for a company owner or admin reads "Only a company owner can deactivate, sign out or clear the lockout of a company owner or admin."; nobody sees them on their own page.

- **Deactivate** ("Deactivate <name>?"): the person can no longer sign in, and their sessions, API tokens and connected AI apps stop working in every team of your company. Their teams, roles and history are kept. The page then says "<name> is deactivated." The last active company owner cannot be deactivated.
- **Reactivate**, shown instead for a deactivated person ("Reactivate <name>?"): they can sign in again and get back exactly the access they had before. The page says "<name> is active again."
- **Sign out everywhere** ("Sign <name> out everywhere?"): every device they are signed in on is signed out; their API tokens and connected AI apps are not affected. The page says "<name> has been signed out everywhere." and Signed-in devices shows 0.
- **Clear sign-in lockout** ("Clear <name>'s sign-in lockout?"): if they had to wait after too many sign-in attempts, they can try again straight away. The page says "<name>'s sign-in lockout was cleared."

Each action asks you to confirm first, may ask you to confirm it's you, and is recorded in your team's activity and on the person's **Activity** tab. A deactivated person who signs in with the right password sees "This account has been deactivated. Ask a company owner or admin to reactivate it.", and every page or connected app they still have open is refused with "Your account has been deactivated. Ask a company owner or admin to reactivate it.". **Activity** lists, newest first, the configuration changes the person made and the changes made to their access (configured role assigned or cleared, home units changed, company authority changed, two-step sign-in reset, Deactivated, Reactivated, Signed out everywhere, Sign-in lockout cleared), with when, what and who made it ("This person" for their own changes). It shows the latest 50 changes and says so when there are 50. Nothing else on the page edits the person: no name, team role, configured role or authority change, and no groups yet.

**Anonymise account.** Below the account actions on the **Security** tab, a company owner sees **Anonymise account** on anyone else's page, a deactivated person's included: "Permanently replaces this person's name and email with a placeholder and removes their access to every team of your company. This cannot be undone." A company admin with People sees only "Only a company owner can anonymise an account.", and nobody sees it on their own page. Use it only for data-protection requests; to stop someone signing in, **Deactivate** them instead. **Anonymise account** opens "Anonymise <name>?", which lists what is removed (team memberships, sign-in, API tokens and connected AI apps, two-step sign-in, configured roles, record assignments, company authority, pending invitations to their email, and the details of activity entries about them), what is kept (records, candidates, comments and files they created; the activity they performed, shown under the placeholder name; a record of who anonymised the account and when) and what is not covered (copies outside the app, their directory entry, which you erase separately under **Directory**, and names or emails typed into records). **Cancel** has focus first. Type the person's name exactly as shown under **Type the person's name to confirm** (case matters; spaces at either end are ignored); **Anonymise account** stays disabled until it matches. You may be asked to confirm it's you, over the dialog, which keeps what you typed. If the change is refused, for example because the person is the last owner of a team, is also in a team of another company or is the last company owner, the reason shows in the dialog, which stays open. Once done, the page shows "<name>'s account was anonymised. They no longer appear in Users." with **Back to Users**. The account's name becomes "Former user" and a short code, its email a placeholder that cannot sign in or receive mail, and activity about the person reads "Details removed by user anonymisation". The [erasure runbook](erasure-runbook.md#anonymise-a-user-account) describes the whole process.

**Invite to teams.** On **Users**, **Invite to teams** lists only the teams where you are team owner or admin; company authority alone offers none, because an invitation gives that team's data. If there are none it says "You can invite people only to teams where you are an owner or admin.". Enter an email address, tick each team and choose a team role for it (Owner only in teams you own; Recruiter by default, with the role's description under it), then **Send invitations**. Each team gets its own ordinary invitation, exactly as **Invite a colleague** in Team & access sends it, one after another, and each emails the recipient, who must verify the invited email before joining. One line per team then says "Invitation sent to <team>." or "Not sent to <team>:" with the reason. Teams that were sent are unticked, a failed team stays ticked, and the email is cleared only when every team was sent; the list reloads to show the invitation. With no team ticked it says "Choose at least one team." and sends nothing. An invitation never gives company authority or a configured role.

**Team detail.** **Open** on Admin portal > Teams opens the team's own page, `/app/admin/teams/<team id>`, inside the Admin portal: the sidebar of your current team with **Teams** marked, the team's name as a heading and seven tabs: **Members**, **Settings**, **CV storage**, **Speed**, **Task boards**, **Activity** and **Archive**. Only an owner or admin of that team can open it; this is checked on the server before the page is shown, for the team in the address, whichever team is current, and opening it does not change your current team. A company owner or company admin who is not a member of that team sees only "You are not a member of this team", with no sidebar and nothing about the team: no name, members, counts, records, storage or activity. A recruiter or viewer of the team, and anyone else, sees "You do not have access to this page". The tabs follow the usual pattern: Left and Right arrows move between them, and Home and End go to the first and last. `?tab=members`, `?tab=settings`, `?tab=cv-storage`, `?tab=speed`, `?tab=task-boards`, `?tab=activity` or `?tab=archive` in the address opens that tab, and anything else opens **Members**; switching tabs does not change the address. Every tab reads and changes the team whose page you are on, whichever team is current. **Members** holds the team's member list, the team role changes, **Remove**, **Reset two-step sign-in** (team owners, never on their own row), the **Configured role** column (company owners only), **Invite a colleague** and **Pending invitations** with **Cancel invitation**, with the same confirmations and messages as Team & access had; every change applies to the team whose page you are on. **Settings** renames the team with **Team name** and **Save team name**, which stays disabled until the name changes; after saving, the page reloads with the new name. Under it, **Prepare task board** adds the team's default task buckets when it has none and says "Task board prepared. Existing tasks and buckets were kept."; use it if a new team's task board could not be prepared. **CV storage** holds the team's CV storage panel, **Speed** its timings and **Task boards** its task boards, each described above, with the same controls, checks and messages as before. **Activity** lists the team's own activity, as on the Activity screen: **Search activity**, **Filter activity by record type**, the events newest first with who made each change, and **Previous** and **Next** through 50 events a page.

**Archive a team.** The **Archive** tab of a team's detail page (**Admin portal > Teams > the team > Archive**) shows the team's state, **Active** or **Archived**, and what archiving does: members keep read access to everything, nothing is deleted, and a team owner can restore it at any time. Only an owner of that team can archive or restore it; a team admin sees the state and "Only a team owner can archive or restore this team.", with no button, and a company owner or admin who is not an owner of the team cannot do it either. **Archive team** opens a dialog that says what becomes read-only and what is kept; type the team's name exactly as shown (spaces at either end are ignored, capitals count) and **Archive team** becomes available. **Cancel**, Escape or the close button changes nothing and puts you back on **Archive team**. On an archived team the tab shows **Restore team** instead, with no typed name. After either change the page reloads to show the new state, and each change appears in the team's Activity as "Archived the team" or "Restored the team"; a refusal shows as an alert on the tab or in the dialog. While a team is archived, every member, API token and connected AI app can still open, search, list and export everything in it, but nothing in its data can be changed: creating or editing records, comments and stages, follow-ups and shortlists, CV uploads and bulk CV imports, legacy imports, AI extraction, task boards and **Prepare task board** are all refused with "This team is archived. You can still read everything, but nothing can be changed until a team owner restores it.", and connected AI apps are offered only their read tools. Members and invitations, team roles, two-step sign-in resets, configured roles, the team name, CV storage settings, API tokens and **Permanently erase candidate** keep working. Company configuration that needs the directory or Plan & pay access cannot be changed while your current team is archived; switch to another team first. Archiving deletes nothing and takes effect from the next request: a save that started just before may still finish. Archived teams stay in the team picker, where they read "<team name> (Archived)", and in the Teams list, where **Archived** follows the team's name. While your current team is archived, every page shows "This team is archived. You can read everything, but changes are turned off until a team owner restores it." above its content.

**Old addresses.** Bookmarks of the old team pages keep working. For an owner or admin of your current team, `/app/admin/members` and `/app/settings/team` open that team's **Members** tab, `/app/admin/cv-storage` its **CV storage** tab, `/app/admin/speed` and `/app/settings/speed` its **Speed** tab, and `/app/admin/task-boards` its **Task boards** tab. Anyone else sees what they saw before: "You do not have access to this page" on the four `/app/admin` addresses, the speed notice on `/app/settings/speed` and **Team & access** on `/app/settings/team`. `/app/admin/tokens` and `/app/admin/history` stay where they are.

**Roles & permissions.** Only company owners see this tab of the Admin portal; anyone else who opens `/app/admin/roles` sees "You do not have access to this page". Company authority has its own page, **Company authority**, described below; the tab says so with an **Open Company authority** link. **Roles** lists the built-in Owner, Admin, Recruiter, Viewer, Hiring manager and Interviewer templates. Hiring manager is recruiter membership limited to the vacancies, applications, interviews and offers of their org unit; Interviewer is viewer membership limited to assigned records, with only the candidate's name and job title visible. **View … template** shows a template as text: its membership, pages, actions per resource, field rules and record scope. The Owner template cannot be edited or copied. **Copy to a new role** on any template but Owner asks for a name (1 to 120 characters, "Copy of …" at first) and creates a draft role; the role's key is made from the name, so choose a name no other company role uses. The draft opens in the editor, with standard checkboxes and lists: the role's name, the pages it can open, the actions it allows on each resource (open a resource to see its actions), a rule for each field of each kind of record (Default, Hidden, Read only or Can edit) and the record scope: for vacancies and the pipeline, for candidates and for team tasks, a list of **All records**, **My org unit and below** or **Assigned records**. **My org unit and below** shows the records of the units of the member's current positions in the directory and every unit below them, plus records assigned to them; candidates count when one of their applications does, and tasks when the member created them, is assigned to them or they name a candidate or vacancy the member sees. **Assigned records** shows only records assigned to the member (and, for tasks, the ones they created). A member with no position in the directory sees only assigned records. Only a company owner changes the directory links and positions that set a member's units. Tasks are assigned in the task editor (**Assignees**); other records can be assigned only through the service so far, so a member with **Assigned records** sees the tasks assigned to them and the other records assigned to them through the service. A role keeps the membership (admin, recruiter or viewer) and permissions of the template it was copied from and can only narrow them, so the editor refuses a grant that membership cannot hold: ticking **Edit** on candidates for a viewer role, for example, shows "Viewer membership cannot hold a write action." next to it and a summary at the top, and the draft cannot be saved until it is unticked. Plan & pay access is never part of a role; it is given per person in **Company authority**. Some checkboxes sit under a **Takes effect later** sub-heading: the pages other than Overview, Analytics and Activity, every action on Teams and on Two-step sign-in reset, and the Directory actions other than View, Create, Edit and Archive. Nothing checks those settings yet; they are saved with the role and apply once the screens and actions that use them arrive, so you can set them now. **Save draft** keeps your changes; **Publish**, offered once the draft is saved with nothing refused, asks you to confirm because publishing changes access for every member who holds the role. **Company roles** lists each role as "Draft", "Published (version N)" or "Published (version N), draft in progress", with **Edit draft**, **Publish** or **New draft**. Every draft and publish appears in **History** as "Role: <key>".

**Company authority.** **Admin portal > Company authority** (`/app/admin/company-authority`, first in **Access**, before **Roles & permissions**) lists the company owners and admins and lets a company owner change them. Only company owners see it; anyone else, company admins and team owners included, sees "You do not have access to this page". A company owner holds every company area and manages roles and company authority; a company admin manages only the areas given to them: Record fields, Workflows, Boards, Organisation, Templates and People (only Record fields, Organisation and People have a screen or route today; Record fields is the **Fields** page). **People** shows the names and email addresses of everyone in every team of the company, with their teams and roles, in **Admin portal > Users**; it never opens a team's data. The table shows each holder's **Name** ("(you)" on your own row), **Level**, **Areas** ("All areas" for a company owner), **Plan & pay access** (Yes or No), **Two-step** (On or Off), **Since** (when their authority was last granted, changed or restored) and **Status**. **Plan & pay access** is one switch, a per-person grant that only a company owner gives, to anyone holding a company level, themselves included; no role or team role brings it. It opens the confidential salary brackets, in **Admin portal > Organisation > Job architecture** (see **Salary brackets** below). Recruitment plan figures do not exist yet. A holder reads brackets only in a team where their role gives the plan scopes (a team owner or admin, or a configured role that keeps them). Company owners and admins must use two-step sign-in. Someone shown with two-step **Off** (for example someone who held authority before this rule) keeps their authority, is asked to set up two-step sign-in at their next sign-in, and cannot be given a level, or have their level, areas or Plan & pay access changed or restored, until they do: saving says "This person must set up two-step sign-in before they can hold company authority. Ask them to turn it on in My profile, then try again." Removing their authority is always allowed. To grant or change authority, choose a person (the members of your current team and everyone who already holds authority), a level ("No company authority", "Company admin" or "Company owner"), the areas for a company admin and the **Plan & pay access** switch, then **Save company authority**. **Remove** takes someone's authority away after you confirm. The last company owner cannot be removed or made a company admin: "The last company owner cannot be removed. Make someone else a company owner first." Someone who leaves every team of the company is shown "Suspended: left every team of this company" and holds no authority; after they rejoin a team, **Restore authority** gives back what they held. Restoring someone who is still in no team says "This person is not a member of any team in this company. Invite them to a team first." "Nothing changed." means the grant was already in place. Every change needs a recent sign-in (see **Confirm it's you** below) and is recorded in your team's activity, shown only to people with company authority; a list of authority changes across every team is not available yet.

**Organisation.** Company owners, and company admins given the Organisation area, see this tab of the Admin portal (`/app/admin/organisation`); anyone else sees "You do not have access to this page". **Levels** lists the layers of the organisation, top first, with their depth (0 is the top) and whether they are archived. **Add level** takes a name and one of the depths from 0 to 7 that no level uses yet; **Rename** and **Archive** sit on each current level, and Archive asks you to confirm. The **Org chart** is a list of units that loads one level at a time: at first only the top-level units, then, when you expand a unit with its button (Enter or Space), its positions and the units below it. Collapsing and expanding again does not reload. Each unit shows its name, code and level; each position its title, code and "Manager" when it is a manager position. With directory access, **Show employees** on a position lists the name and employee number of the people who hold it, 25 at a time with **Show more**; work email and phone never appear in the chart. Without directory access the chart says "You need directory access to see who holds these positions." **Add top-level unit** and **Add unit below** take a name, a code and a level; **Rename** changes a unit's name; **Add position** takes a title, a code, a **Job title** from the published job architecture and whether it is a manager position; **Edit** changes a position's title, job title and manager mark; **Archive** on a position asks you to confirm. Moving and archiving a unit, and moving a position, change who can see which records once unit roles arrive, so only company owners see **Move** and **Archive** on units and **Move** on positions. **Move** picks the new place one level at a time ("Top level" for a unit); only the first 200 units of a level are listed, and the picker says so. The **Job title** of a position works as in the vacancy editor: each title shows its grade, the chosen title's grade shows under it, and only people with Plan & pay access see its salary bracket. **No job title** leaves the position without one, or removes it. A saved title a later version removed stays selected as "<key> (not in the published job architecture)" and is not sent again unless you change it; choosing a title that is no longer published is refused in the dialog. Company admins can archive a position, but a position held by an employee linked to a user needs a company owner, and that refusal shows next to the position. Every refusal shows in plain words next to the form or row that caused it, for example when a code is already used, a unit's level is not below its parent's, or a unit would move under itself.

**Org tree.** The **List | Org tree** switch above the org chart shows the same units in a second view; List is where the chart opens, and switching keeps what is loaded and expanded without loading anything. **Org tree** draws the units top-down as boxes joined by lines, each with its name, code and level and, once opened, its number of positions; a unit's positions sit in boxes under it, with title, code and "Manager", and the units below it sit side by side underneath. On a narrow screen (720 px and narrower) the tree becomes an indented outline. It loads one level at a time, as the list does: click a unit's box, or use the keys below, to expand or collapse it. A position that no active employee holds is drawn with a dashed border and the word **Vacant**, and the unit and the line under the toolbar count the vacant positions. Seeing which positions are vacant needs directory access; without it nothing is marked Vacant and the tree says "You need directory access to see which positions are vacant." The tree shows no names of people, employee numbers or contact facts, and has no Rename, Add, Move or Archive: use List for those. **Expand all** opens every loaded unit and loads the units below them, level by level, without loading further pages behind **Show more units**; it stops at 500 units in all, says "Expand all stopped at the limit of 500 units. Expand a unit to see the units below it.", and otherwise "Expand all finished: N units loaded." **Collapse all** closes every unit and keeps what was loaded. **Zoom out**, **Zoom in** and **Reset zoom** draw the tree from 50% to 150% (shown beside them); the tree scrolls inside its own box at any zoom, so nothing needs zooming or dragging to read it. **Export image** saves `org-tree-by-units-<date>.png` with what is loaded and expanded at that moment, at 100% on a white background; the picture is made on your device and nothing is sent to the server. With the keyboard, Tab moves into the tree once; Down and Up go to the next and previous item, Right expands a unit or goes into an expanded one, Left collapses a unit or goes to the unit above, Home and End go to the first and last item, and Enter or Space expands or collapses a unit or shows more units. Each item is announced with its level and its place among its siblings.

**Org tree by people.** If your role has the Directory page and can view the directory, **Org tree** also shows a **By units | By people** switch; By units is where it opens, and without that access there is no switch. **By people** shows who reports to whom, worked out from the manager positions, with nothing stored: a person reports to whoever holds a manager position in their own unit. If that manager position is vacant, or they hold it themselves (a manager), they report to whoever holds a manager position in the nearest unit above that has one. Someone with several positions reports through their primary position, or, if they hold a manager position, through the one nearest the top, and appears once; "+1 more position" counts the others. If a unit's manager position has several holders, the first by name is the manager. People with no manager above them are at the top. Only active employees holding a current position are shown: people who left, archived employees and employees without a position are not in the tree, and no one reports to them. Each box shows the name, the title and unit of the position they report from, how many more positions they hold and how many people report to them; never a work email, phone, employee number or user account, whatever your directory rule. The tree loads one level at a time: first the people at the top, then, when you expand someone, the people reporting to them; expanding them again does not reload, and a long level ends with **Show more people reporting to <name>**. **Expand all** opens everyone loaded and loads who reports to them, level by level, without loading further pages behind Show more; it stops at 500 people in all and says "Expand all stopped at the limit of 500 people. Expand a person to see who reports to them.", and otherwise "Expand all finished: N people loaded." **Collapse all** closes everyone and keeps what was loaded. Zoom works as in the tree by units, and **Export image** saves `org-tree-by-people-<date>.png` with the people loaded and expanded at that moment, made on your device without sending anything to the server. Switching between By units and By people keeps what each has loaded and expanded. The keys are the same as in the tree by units: Tab moves into the tree once; Down and Up go to the next and previous person, Right expands someone who has people reporting to them or goes to the first of them, Left collapses someone or goes to their manager, Home and End go to the first and last item, and Enter or Space expands or collapses someone or shows more people.

**Importing the organisation from Excel.** The same people can import units, positions and employees from one .xlsx workbook with **Import from Excel** at the bottom of the Organisation tab; a workbook with employee rows also needs a role that can add and edit employees in the directory. The workbook has up to three sheets, found by name: **Units** (Code, Name, Level, Parent code), **Positions** (Code, Title, Unit code, Manager) and **Employees** (Employee number, Name, Work email, Work phone, Position codes, Primary position). Row 1 of each sheet names the columns; other sheets and columns are ignored, and empty rows are skipped. Units are matched by code, positions by code and employees by employee number. **Level** is the name of a current level, ignoring case; the import never creates a level or changes a unit's level. A blank **Parent code** puts a unit at the top level. **Manager** is yes or no. **Position codes** lists an employee's positions separated by commas or semicolons, and it is then their whole set of positions; **Primary position** is one of them or blank. Positions may also have **Job title** (a published job title's name or key, ignoring case) and **Grade** (which must agree with that title's grade); an unknown title, a name used by more than one title (use its key instead), a grade that does not agree and a grade without a title each reject the row, and a blank Job title leaves the position's stored job title. Any other column, including salary or pay columns such as Salary, Basic, Bracket or Minimum, is ignored: it is never read or stored, and salary brackets are never imported. A blank cell leaves the stored value unchanged; the import never clears a value. A file over 5 MiB, with more than 20,000 rows, or whose archive holds more than 2,000 files or more than 50 MiB once unpacked is refused before it is read. Choose the file and press **Check file**: nothing is written yet. The result shows, for each sheet, how many rows would be created, updated, left unchanged or rejected, and lists the rejected rows with their row number and the reason (for example an unknown level, a missing or looping parent, a code used twice, a work email or phone that is not valid, an unknown position code or more than one primary position). **Job titles** lists each position row's job title and grade, and **Ignored columns** lists the columns the import does not read. **Flagged cells** lists cells that start with =, +, -, @, a tab or a line break: they are stored as plain text and never run as formulas. **Apply import** asks you to confirm and then writes one sheet at a time (units, then positions, then employees), shows what it wrote and reloads the chart; applying the same file again is safe, and changes nothing that is already in place. If the file changed since you checked it, check it again. Rows that would move a unit to another parent, move a position held by an employee linked to a user, or change such an employee's positions are listed under **Needs a company owner** and are never written by Apply import. A company owner sees **Apply company owner changes**, which asks to confirm separately and writes only those rows (run it after Apply import if they depend on new units or positions); company admins see "A company owner must apply these rows." Employees created by an import are marked as from Excel. The import never links an employee to a user account and never guesses a link, for example from a work email. Importing a workbook that still lists an employee who was permanently erased creates them again, so remove them from your spreadsheets too.

**Job families, titles and grades.** Your company's job architecture lists its job families (such as Finance), its job grades (such as G7, each with a name and a place in the grade order) and its job titles (such as Payroll Lead), each title in one family and one grade. It is one company setting, kept as published versions like a role: company owners, and company admins given the Organisation area, edit a draft and publish it as the next version, and every member of every team in the company can read the published version. A position and a vacancy can each name one of its titles by its key; a key that is not a title of the published version is refused, and a vacancy keeps its title when a later version removes it until someone changes it. It holds names, codes and order only, never salaries, pay figures or brackets. It is managed in the **Job architecture** panel of **Admin portal > Organisation**, below the org chart, and also through the API (`/api/v1/job-architecture`, see the API examples). The panel has three tabs, moved between with the arrow keys, Home and End: **Job grades & salary brackets** (where it opens) lists each grade's code, name, order and number of job titles, lowest order first; **Job titles** lists each title with its key, family and grade ("G7 · Senior"); **Job families** lists each family with its key and number of titles. Company owners and company admins given the Organisation area see the draft when there is one, with "A draft is saved and not published yet.", and otherwise the published version ("Published version 2"). They add with **Add grade** (code, name and order), **Add job title** (name, key, family and grade; it waits, with "Add a job family and a job grade first.", until there is at least one of each) and **Add job family** (name and key), and change a name, order, family or grade with **Edit** on its row. A new key starts as the name in lowercase letters, digits and hyphens until you change it. Changing an existing title's grade takes two steps: **Save job title** first shows, in the dialog, how many current positions, open vacancies and open offers across the whole company use the title ("Changing Fictional Payroll Lead from G7 to G5 affects 2 positions, 1 open vacancy and 1 open offer across the company. They follow the new grade once the job architecture is published.", or "No current position, open vacancy or open offer uses …" when there are none), and the button becomes **Change grade and save**, which saves the change into the draft. **Cancel** closes the dialog and changes nothing; choosing another grade asks for the counts again. The counts are totals only, with no team or record named; open vacancies are those with status Open, and open offers those still Draft or Sent. The new grade applies once the job architecture is published. Codes and keys are fixed once added, because titles, positions and vacancies refer to them. Each change is saved into the draft (the first change makes it), and **Publish job architecture** publishes the draft as the next version: "Published job architecture version 2." A form refuses in plain words, with nothing sent, a missing name, a code or key in the wrong form, a code, key or order another entry already uses ("Another grade already uses this code."), an order that is not a whole number from 1 to 1000, and an entry beyond 200 families, 200 grades or 2,000 titles ("A job architecture holds at most 200 grades."). Anyone else who opens the page sees the published version only, with no Add, Edit or Publish; with nothing published it says "No job architecture is published yet."

**Salary brackets.** A salary bracket is the minimum, midpoint and maximum pay for one job grade, in AED only. Brackets are confidential: only people a company owner has given **Plan & pay access** in Company authority see them, and a company owner needs the grant too; everyone else sees the grades without pay, and the grades tab says so in a **Confidential.** notice. With the grant, and a role in your current team that gives the plan scopes (a team owner or admin), the grades tab shows a **Show salary brackets** switch. It is off every time the page opens, and the brackets are loaded only when you turn it on; without the grant there is no switch and the page never asks for brackets. With it on, a line such as "Brackets in AED, monthly, basic salary only · effective 1 Jan 2027 · version 1" names the published bracket version, and the grades table gains **Minimum**, **Midpoint** and **Maximum** (headed, for example, "AED a month"), amounts such as 15,000 or 15,000.50, and **Range**: a band scaled to the highest maximum with the midpoint marked, read out as "AED 12,000 to AED 18,000, midpoint AED 15,000". A grade without a bracket in that version shows "No bracket"; with none published the line says "No salary brackets are published yet." The table always shows the published version; draft figures appear only in the dialog. Holders who can also change the job architecture get **Edit salary brackets**, which opens **Salary brackets**: **Bracket settings** shows "Currency: AED" (there is no other currency), **Pay period** (Monthly or Annual), **What the bracket covers** (Basic salary only, Basic + housing + transport or Total cash) and **Effective from**; Monthly and Basic salary only are where a first bracket starts. **Brackets** has a Minimum, Midpoint and Maximum for every grade of the published job architecture, entered in AED with up to two decimals and no separators, such as 15000 or 15000.50 ("Enter each amount in AED, such as 15000 or 15000.50, from 0.01 to 1,000,000,000."). A bracket out of order is refused before anything is sent, naming the grade: "The minimum must be at most the midpoint, and the midpoint at most the maximum." Brackets follow the published grades, so a grade added in a job architecture draft gets a bracket only after that draft is published; the dialog says so. Saving keeps the figures in a bracket draft ("A salary bracket draft is saved and not published yet."), and **Publish salary brackets** publishes it as the next version, after **Confirm it's you** when your sign-in is not recent: "Published salary bracket version 2." A published version is never changed; saving again makes a new draft. A draft made before the grades changed says "This draft was made for other job grades. Saving brackets makes a new draft." and cannot be published. Bracket figures are never shown in activity, notifications, search, exports or AI tools.

**Directory.** People whose role includes viewing the directory see this tab of the Admin portal (`/app/admin/directory`); anyone else sees "You do not have access to this page". Filter the employees by **Name or employee number** (part of either), **Unit** (pick it one level at a time; the units below it are included), **Level**, **Position** (the positions of the chosen unit, once a unit is chosen) and **Status** (Any, Active or Left), tick **Include archived employees** to see archived ones, and press **Search**. The table shows 25 employees a page with their name, employee number, positions (primary first), status, retention class, whether they are linked to a user account (never which account) and whether they are archived, with **Previous page** and **Next page** and a line naming the page. **Work email** and **Work phone** columns appear only when your role's directory rule is full; under the basic rule they are not shown at all. Each row has one **Actions** button, which opens the actions you may take on that employee in a dialog; a refusal shows in its own line under the row. With the matching directory actions you can **Add employee** (display name, employee number, work email and phone, status and retention class), **Edit** those facts (the work email and phone only under the full rule) and **Archive** an employee after confirming. **Positions** opens the employee's current positions: choose the primary one, **Remove** one, or add one by picking a unit and a position, then **Save positions**. Linking an employee to a user and changing a linked employee's positions set whose records a person can see once unit roles arrive, so only company owners see **Positions** on a linked employee and **Link to user** and **Unlink user**. **Link to user** lists the members of your current team and asks you to confirm before linking; **Unlink user** asks you to confirm. Company owners also see **Permanently erase employee** under each row's **Actions** and the **Retention review**, described below.

**Fields (job 094, R2b-09).** **Admin portal > Fields** (`/app/admin/fields`, in **Configuration**) shows for company owners and for company admins given the Record fields area, whatever their team role; anyone else, team owners and admins without company authority included, sees "You do not have access to this page", and its API answers them 403. It lists, in one table, every field of the nine kinds of record with fields (candidates, job roles, vacancies, applications, team tasks, interviews, offers, onboarding and checklist items): the built-in **System** fields and the company's **Custom** fields. Each row shows the field's **Name** with its badges (System or Custom, Archived, Sensitive, Required), its **Key** (always shown; a custom field's key is a long code that never changes), its **Type**, its **Record kind** and its **Group** on the kind's edit screen ("No group", or "Not on a screen"). **Record kind** above the table narrows it to one kind ("All record kinds" shows them all). When two fields of one kind have the same name, ignoring case and spaces at the ends, archived fields included, both rows say "Another <kind> field has this name", and so does the name box while you type; the name is still accepted. The page reads field settings only, never a record or a value. Every change is saved into a draft of that kind ("Saved to the Candidate draft. Publish it to apply the change."); nothing applies until the draft is published. **Edit** opens a dialog for the field's name, help text, group and **Required**. A built-in required field, such as a candidate's Name, says "Always required" instead; a system field can be relabelled, given help text, regrouped and made required, but never removed, archived or given another type. A custom field also edits its validation (minimum and maximum, pattern, currency, the record kind a lookup points to and its default); its type is shown and never changes, and its options are fixed once created. **Group** lists the kind's group names: the field moves to the end of that group on every screen that shows it (a new group is added at the end; a group left empty is removed), and an empty Group means no group. **Move up** and **Move down** swap the field with its neighbour in its group on every screen that shows it; a button is greyed out when nothing would move. **Archive**, on custom fields only, asks first and explains that every value already stored is kept; the field stays listed as Archived and is never required. No field can be deleted. **Create field** opens a wizard of five numbered steps, with **Back** and **Next**: 1 the record kind; 2 the type, one of the 18 field types (short text, long text, rich text, number, money, percentage, date, date and time, dropdown, multi-select, checkbox, person, org unit, web address, email, phone, file and lookup); 3 the name and help text; 4 the validation the type takes (Required, minimum and maximum, a pattern for short text, the options one per line for a dropdown or multi-select, the currency for money, prefilled AED, the record kind for a lookup, and a default, except for person, org unit, file and lookup); and 5 the screens to add it to, with the kind's create, edit and view screens ticked. A refused pattern or a maximum below the minimum is explained on its step before anything is sent. **Create field** adds the field with a new key and saves the draft. A custom field cannot yet be required on a create screen, because the app's forms cannot fill it: "<key>: custom fields cannot be required on a create screen yet." Only company owners see **Sensitive** in the editor and the wizard; company admins see the Sensitive badge only. Gender (explicitly stated) and UAE national service (as stated) are always sensitive. A sensitive field is left out of what connected AI apps receive (for team tasks, a sensitive custom field leaves out all task custom values there); everyone with access still sees it in the app and the API. Above the table, each kind with a draft shows "Draft in progress." with what is in force ("Built-in" or "Version 2") and **Publish <kind> changes**. Publishing first shows the changes, each field by name and key under Added, Renamed, Archived, Moved to another group, Made mandatory, Made sensitive or Other changes ("No changes from the published version." when there are none), with **Cancel** first; **Publish** then says "Published Candidate version 2.". A refused publish shows the reason, such as a screen rule the draft breaks, and publishes nothing. A draft that marks or unmarks a sensitive field can be published only by a company owner; a company admin sees "A company owner must publish this draft because it changes which fields are sensitive." and no Publish button. Each draft and publish is listed in **History** as Record fields.

**About.** The footer of every workspace page and the sign-in page show the version you are using, for example "Version 1.0.0 (build 20261108.1430)"; the build number is the build time in UTC. Everyone who is signed in, in any role and also before joining a team, sees an **About** tab in settings with the version, build, commit, environment (Production, Preview or Local development) and build time in UTC. **Copy details** copies three lines for a bug report: the version with build and commit, the environment and the build time. It holds nothing secret and nothing about you, your team or your browser. If your browser cannot copy, copy the details shown on the page instead.

**Two-step sign-in.** Team owners and admins, and company owners and admins, must use two-step sign-in; for everyone else it is optional, but you need it to create API tokens or connect apps. To set it up, open **Turn on** under **Two-step sign-in** in My profile (owners and admins are taken there automatically): enter your password, scan the QR code with an authenticator app or type the setup key shown below it, enter the 6-digit code the app shows, then save the 10 backup codes and tick **I have saved my backup codes** before **Continue**. The codes are shown only once. From then on, signing in asks for your password and then **Enter your sign-in code**: type the current code, or choose **Use a backup code instead** if you do not have your phone; each backup code works once. Tick **Trust this device for 30 days** only on your own device: it skips the code there for 30 days after you last entered one, then asks again. **Create new backup codes** (with your password) replaces all your codes and forgets your trusted devices. **Turn off** asks for your password and a confirmation; owners and admins are asked to set it up again straight away, which is also how you move to a new phone. If someone's role changes to owner or admin, or they hold company authority without it, they set it up at their next sign-in. Someone who has lost their phone and codes can be helped by an owner of every team they belong to: on the team's **Members** tab in the Admin portal, **Reset two-step sign-in** on that member's row signs them out everywhere and removes their authenticator, so they set it up again; the reset appears in Activity. Five wrong passwords for one email in a row make the next sign-in wait a minute, and the wait grows after further wrong attempts; a correct password clears it.

**Confirm it's you.** Publishing a role, giving or clearing a configured role, changing, removing or restoring company authority, resetting a member's two-step sign-in, deactivating or reactivating a person, signing a person out everywhere and clearing a person's sign-in lockout need a recent sign-in: one from the last 15 minutes. If yours is older, the page opens **Confirm it's you** after you save, and after the change's own confirmation if it has one. Enter your password and, if you use two-step sign-in, the current code from your authenticator app, then **Confirm**: the change is then saved once, without asking you to confirm it again, and you stay in the same team. On a team's **Members** tab in the Admin portal this works the same way, and the change still applies to the team whose page you are on. On a device you trusted at sign-in only the password is checked. A wrong password or code shows "That password is not correct." or "That code is not correct." and saves nothing; after a wrong code, enter the new code and **Confirm** again. **Cancel**, Escape or the close button saves nothing and keeps your changes on the page: the open role, the chosen person, level and areas, or the chosen configured role. If you cancel after your password was accepted but before your code was, you are signed out on this device, and the page says "You are signed out on this device. Sign in again to make this change." with a **Go to sign-in** link. Opening any Admin portal page or Team & access never asks.

Profile settings manage your name, password and sessions. Signed-in devices load only when you select **Show signed-in devices**. If your sign-in is not recent, the list asks you to sign out and sign in again before it shows your devices; **Sign out all other devices** works without loading the list. In **API tokens**, create a named token for one integration, choose the smallest necessary scopes and expiry, and copy it once to the integration's secret store. Revoke unused tokens. A token remains tied to your user and team and loses permissions when your role changes or your membership is removed. See [API examples](api-examples.md). To connect an AI assistant such as Claude, see [mcp.md](mcp.md); connected apps appear in the same list with an **OAuth app** badge and are revoked the same way. With CV permissions a connected AI app can read the text of PDF and DOCX CVs and upload CVs, one at a time or as a bulk import that you review in the app; an app that cannot send files gives you a link that opens **Import CVs** on **Candidates**. The app's analysis of a CV is not saved unless you ask it to add a comment or update the candidate's details.

## Data administration

An administrator prepares cloud services and imports legacy files using [deployment.md](deployment.md) and [migration.md](migration.md). The importer starts with a local reconciliation report and requires an explicit apply command. PostgreSQL becomes the canonical store; editing old Excel workbooks does not update the deployed application.

**Permanently erase a candidate (owners only).** For a data-protection request, a team owner opens the candidate's **Full profile** and, under the record details, chooses **Permanently erase candidate**. The dialog lists what is removed (candidate details, applications, interviews, offers, onboarding and checklist items, comments, every member's follow-up notes and shortlist, CV files and AI suggestion records), what is kept (tasks, unlinked from the candidate and with the name replaced; activity entries without personal details; a record of who erased the candidate and when) and what is not covered (CSV exports already downloaded). Type the candidate's name exactly as shown to enable **Permanently erase**. This cannot be undone; to keep the record but hide it, archive it instead. CV files are deleted from storage once their upload links have expired; the confirmation says when. Admins, recruiters and viewers do not see this action. Before and after erasing, follow [erasure-runbook.md](erasure-runbook.md), which also covers requests handled with the owner-run `npm run erase:candidate` script.

**Permanently erase an employee (company owners only).** For a data-protection request about someone in the company directory, a company owner opens **Admin portal > Directory** (`/app/admin/directory`). Type part of the name or the employee number in **Name or employee number**, tick **Include archived employees** and press **Search** or Enter; each row shows the status (Active or Left), retention class (Standard or Extended) and whether the employee is archived. **Actions** on the employee's row, then **Permanently erase employee**, opens a dialog that lists what is removed (the directory entry: name, employee number, work email and phone, status and retention class; the position history; the link to a user account), what is kept (positions and units, the user's account and team memberships, activity entries without personal details, a home-unit change entry for the unlinked user, and a record of who erased the employee and when) and what is not covered (copies outside the app, such as spreadsheets the directory was imported from). Type the employee's name exactly as shown to enable **Permanently erase**. This cannot be undone; for routine cases set the status to Left or archive the employee instead. The page then says "Employee permanently erased." and the directory page and the retention review reload. Company admins, team owners and admins without company authority do not see the action. Follow the "Erase an employee" section of [erasure-runbook.md](erasure-runbook.md#erase-an-employee) before and after erasing.

**Retention review (company owners only).** The **Retention review**, below the directory in **Admin portal > Directory**, lists the employees whose status has been Left for 12 months or more, oldest first, archived ones included, with the date they left and their retention class, 25 at a time with **Show more**. Nothing is erased automatically: review the list and erase an employee only after you have decided their data is no longer needed. The retention class is set when adding or editing an employee in the Directory or through the API (`retentionClass`, Standard by default) and is shown only; owners cannot yet set retention periods. Searching and the review need a team role with directory access (team owner or admin). Both are also available to a signed-in company owner as `POST /api/v1/employees/{id}/erasure` and `GET /api/v1/employees/retention-review` ([api-examples.md](api-examples.md#employee-erasure-and-the-retention-review)); API tokens and AI apps cannot use them.

## Known gaps

- Forms and record details in the app still show the built-in fields, in the built-in order and groups, with no inputs for custom fields, although the fields published on **Admin portal > Fields** already apply to saving, required fields and exports.
- A custom field cannot be required on a create screen, and bulk CV import and connected AI apps cannot fill custom fields other than team task fields.
- A custom field's options cannot be changed after it is created, and an archived field cannot be restored; drafts cannot be discarded, and versions cannot be compared side by side.
- Group and order changes on **Fields** apply to every screen that shows the field; screens cannot yet be designed one at a time.
- A sensitive custom task field leaves every task custom value out of connected AI apps, not only its own.
