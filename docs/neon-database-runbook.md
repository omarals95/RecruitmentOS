# Neon database setup runbook

This is a preparation checklist. No migration, role creation, grant, credential rotation, or candidate-data import is performed by this document. Preview and Production use independent Neon resources. Work on Preview first, separately from Production, using fictional data only. The original Preview proposal, kept as a record, is [preview-database-change-plan.md](preview-database-change-plan.md).

## Stop conditions

- The staged connection-boundary checks apply to the paired data/identity pool path. The legacy unhosted single-pool development fallback does not have equivalent URL or environment validation and uses the old shared-role model. Do not use it with real candidate data or treat it as evidence for deployment safety.
- Startup pool checks cover only the connections used for inspection. They do not validate every future checkout or reset a pooled session's role and settings after release. Each application transaction therefore installs its own signed tenant context and uses only transaction-scoped settings (WP-01, WP-02d; see [§4](#4-connection-pooler-requirements)). In the owner's run on Preview, `npm run test:live-roles` passed 27/27 through the transaction-mode pooler and 27/27 direct (WP-02e). The blanket hosted gate is gone; hosted startup now fails closed on the precise checks in [identity-boundary-plan.md](identity-boundary-plan.md).
- The staged pool validator rejects URL parameters other than a single supported `sslmode`. In particular, it rejects `channel_binding=require`, which may appear in Neon connection strings: the installed driver has not been shown to enforce that URI requirement. Do not silently remove the parameter or claim channel binding is enforced; resolve and test the driver behavior before live connections.
- Do not run a migration or start the application until Vercel project linking and the required environment settings have been verified. The first administrator's email, setup token, authentication origin and secret, and verified email sender must be configured separately for each environment.
- Migration `0004_protect_initial_admin_claim.sql` restricts direct writes to `auth.initial_admin_claim`. The legacy shared-role fixture has been removed. The split runtime role template [postgres-split-runtime-roles.sql](../infrastructure/postgres-split-runtime-roles.sql) has been verified on PGlite, on a throwaway local PostgreSQL 18 cluster and, in the owner's run, on the Neon Preview database: there the template is applied, `scripts/db-role-evidence.ts` passes with zero drift, and `npm run test:live-roles` passes 27/27 through the transaction-mode pooler and 27/27 direct, with all fixtures removed. It is not verified on Production. Before deployment, independently review the migration's and the template's grant impact (DEC-02/DEC-03) and test the protection using real, nonowner roles on the Production database; embedded tests alone do not prove live role or inheritance behavior.
- Do not attach an owner or migration connection as the deployed `DATABASE_URL`. The production startup guard checks elevated direct or inherited roles, broad predefined memberships, protected-object ownership, schema/database creation privileges and any table, column, sequence, function, schema or database privilege held WITH GRANT OPTION. It is defense in depth rather than a full privilege audit; independently verify effective permissions and test the actual Neon role.
- The runtime guard also refuses a missing protected schema or setup marker, or effective direct, inherited, or PUBLIC write privileges on that marker, including column grants. Checking for schemas and the marker does not verify the entire migration ledger or database schema. It runs only when the database pool is initialized; after any role, membership, grant or ownership change, review the effective privileges and recycle the deployments so the check runs again.
- Stop on unexpected project, branch, database, role, privilege, migration state, connection failure, or authentication behavior. Investigate before retrying. Never log, commit, or put connection strings, passwords, setup tokens, or verification links into chat.

## 1. Identify and prepare both environments

1. In the Neon and Vercel consoles, confirm that the Preview resource points to its own empty database and the Production resource to a different database. Verify project and branch identifiers as well as database names; do not rely on display names alone. Verify that any automated Neon preview branching cannot copy Production candidate data.
2. Confirm the existing Marketplace-injected `DATABASE_URL` role and ownership. Its name and existence do not establish that it is safe for runtime. Plan separate restricted data and identity logins and credentials within each environment; keep each migration-owner credential under separate operator control. The split-role grant template is applied and evidenced on Preview (see the role template stop condition above). Production provisioning and live role tests are not done. The owner re-applies the template on Preview after each template or migration change; the pending re-applies are listed in the [requirement register](requirements/register.md).
3. For each database, obtain its **direct, non-pooler owner connection** for the migration operator. `scripts/migrate.ts` takes a session-level PostgreSQL advisory lock; a transaction-pooled connection does not guarantee that later commands use the session holding that lock. Obtain a separate pooled connection for the restricted runtime role after it is created and reviewed. Verify TLS and hostname for both, without displaying connection strings.
4. Verify the exact environment-specific Vercel settings, including a stable exact authentication origin, independent auth and setup secrets, administrator email, and a working verified email sender. The values must be scoped only to their intended environment. Never put the owner connection in deployed environment variables.

## 2. Migrate one database at a time

1. First review the exact checked-out application revision and the ordered SQL files under `drizzle/`; compare them with the database's `public.recruitment_migrations` ledger if it exists. For any nonempty or previously used database, assess backups and migration compatibility first; the initial-admin migration deliberately closes setup for an existing user or organization.
   Migration 0004 changes the two setup trigger functions to execute as their owner with a fixed search path and removes direct marker-table write grants from PUBLIC and all nonowner grantees, cascading dependent grants. This also removes those writes from maintenance and operator roles, not just the app role; review their recovery workflows first. Existing databases need the new migration and updated grants applied by the migration owner. Preserve a controlled owner-only recovery process. No other table's privileges are intentionally changed.
2. In a controlled operator environment, provide only that database's direct owner connection as `MIGRATION_DATABASE_URL`. Confirm the existing `.env.local` or `.env` will not silently introduce a different database setting: `scripts/load-env.ts` loads one of these files. Confirm that `DATABASE_MODE` does not select PGlite. Do not copy a production owner credential into a local project file or any deployed environment. The procedure in [Run the migration against a Neon database](#run-the-migration-against-a-neon-database) does this from a directory with no project env file.
3. After all prerequisites and the runtime-privilege design are approved, run the migration once for Preview with the procedure in [Run the migration against a Neon database](#run-the-migration-against-a-neon-database), not the bare `npm run db:migrate`. The script takes a session advisory lock and records completed migrations in `public.recruitment_migrations`. Each migration runs inside its own transaction; earlier completed files remain applied if a later file fails. Inspect the ledger and actual schema before deciding on recovery; do not reset or rerun blindly. The failed-migration, rollback and restore procedures are in the [recovery runbook](recovery-runbook.md).
4. Check that the expected migrations are recorded, the `auth` and `app` schemas exist, the `auth.initial_admin_claim` singleton and its triggers exist, and the intended `app` tables have row-level security and their expected policies. Check the actual installed revision rather than assuming any fixed migration count.
5. Only after Preview passes the role and application tests below, repeat the process against the distinct Production resource. Production migration must never use Preview's connection, or vice versa.

### Run the migration against a Neon database

`npm run db:migrate` must not be used for a hosted database. It always runs from the checkout root, where `scripts/load-env.ts` loads `.env.local`, or `.env` if there is no `.env.local`, from the current directory. Every local `.env.local` sets `DATABASE_MODE=pglite`, and then the script migrates the local PGlite database even when `MIGRATION_DATABASE_URL` is set, never contacts Neon and still prints a success line. `applyMigrations` (`src/db/index.ts`) also reads `drizzle/` from the current directory. Run the script by path from a separate directory instead; its own imports still resolve from the checkout.

1. Use a checkout of the reviewed revision with `npm ci` done. Below it is `<checkout>`.
2. Create a new empty working directory outside any checkout and copy `<checkout>/drizzle` into it. Confirm with `ls -A` that the directory holds only `drizzle` and contains neither `.env.local` nor `.env`.
3. Open a fresh shell and run `unset DATABASE_MODE ALLOW_LOCAL_DB DATABASE_URL`. Set `MIGRATION_DATABASE_URL` to that database's direct, non-pooler owner connection without echoing it or writing it to shell history, for example `read -rs MIGRATION_DATABASE_URL && export MIGRATION_DATABASE_URL`. Export `TENANT_CONTEXT_SIGNING_KEY` as the key that environment's deployment uses ([deployment.md §3](deployment.md#3-vercel-environment)) the same way: `read -rs TENANT_CONTEXT_SIGNING_KEY && export TENANT_CONTEXT_SIGNING_KEY`.
4. From the working directory, run `node <checkout>/node_modules/tsx/dist/cli.mjs <checkout>/scripts/migrate.ts`.
5. Success prints `PostgreSQL migrations applied.`. If it prints `Local PostgreSQL migrations applied.`, a project env file selected PGlite and Neon was not touched: stop and find the file before anything else. If it prints `Migration failed. …`, stop and follow the [recovery runbook](recovery-runbook.md#failed-migration).
6. Afterwards run `unset MIGRATION_DATABASE_URL TENANT_CONTEXT_SIGNING_KEY`, close the shell and delete the working directory.

The procedure never displays, logs or commits the connection string or the key. Do not paste either into a command line, a file or chat.

## 3. Runtime access and verification

1. Review the claim-table and trigger privilege changes first. Confirm both trigger functions are owned by the controlled migration owner, have the fixed safe search path, and execute the intended trigger operations; ensure the app role cannot assume or inherit the owner role. Verify initialization still works with the restricted runtime credentials before considering the migration safe.
2. Create each restricted runtime login **using SQL**, after independently confirming the project, branch and database. Neon roles created through the Console, API or CLI are granted `neon_superuser`; they are unsuitable as this app's restricted runtime login. Once the template is reviewed and approved for that database (it is not yet approved for any hosted database):
   - Run [postgres-split-runtime-roles.sql](../infrastructure/postgres-split-runtime-roles.sql) with psql as the migration owner over the **direct, non-pooler owner connection**: `psql -v ON_ERROR_STOP=1 -f infrastructure/postgres-split-runtime-roles.sql`. It creates `recruitmentos_data` and `recruitmentos_identity` as `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS NOREPLICATION` roles, refuses an existing role with other attributes or any membership, and grants the exact object-by-object matrix in one transaction. It also revokes CONNECT and TEMPORARY on the current database and all access to the `public` schema from PUBLIC and both runtime roles, then grants CONNECT only to the two runtime roles; the owner keeps its own access. Other roles that relied on PUBLIC CONNECT to this database lose it. If PUBLIC still has access afterwards, for example because the runner does not own the database or the `public` schema, the template refuses and rolls back. The role names are the same in each environment's separate database; credentials are distinct.
   - The template closes only the application database. As the owner of each other database on the branch or cluster, or an administrator, run `REVOKE CONNECT ON DATABASE postgres FROM PUBLIC;` and the same for every other database that accepts connections apart from the application database (for example `template1`), and grant CONNECT on none of them to either runtime role. A REVOKE by a role that does not own the database only warns, so confirm afterwards that the evidence script reports no `can connect to database` drift. Accepted Neon limitation (owner decision A, 2026-11-04): on Neon, `postgres` and `template1` are owned by the platform role `cloud_admin`, and the application owner cannot revoke PUBLIC CONNECT there. The evidence script accepts such a database instead of reporting drift only when all four conditions hold: (1) its owner is neither the application database owner nor either runtime role; (2) it is not the application database; (3) the runtime role holds there only what PUBLIC holds, at most the default CONNECT and TEMPORARY, with no ACL entry for the role or a role it belongs to, no CREATE and no grant option; and (4) a read-only connection to it as the data role (never the identity role) finds none of the schemas `auth`, `app`, `tenant_context`, `db_boundary` or `storage_ledger` and no `recruitment_migrations` relation. The inspection fails closed: if it cannot connect, a query fails or the data role cannot connect there, the database is not accepted and keeps its `can connect to database` drift. Accepted databases are listed with their owner and the reason under `accepted_platform_databases` for each runtime role; review that list on every run and do not ignore it. Any other database that still allows CONNECT keeps failing the check. The inspection runs inside `BEGIN TRANSACTION READ ONLY` with `SET LOCAL search_path = pg_catalog, pg_temp` and `SET LOCAL statement_timeout = '5s'` before its one catalog query, and any failure rejects the database. Its short read-only connection to `template1` (or any other inspected platform database) can make a concurrent `CREATE DATABASE`, which copies `template1`, fail with "source database "template1" is being accessed by other users", so do not run the evidence script while a database is being created on the same branch or cluster.
   - On PostgreSQL 16 and later, a `CREATEROLE` owner that creates a role is automatically granted membership in it with ADMIN OPTION. The migration owner can therefore alter, drop and reset the password of the runtime roles, grant them to other roles, and grant itself `SET` on them (the automatic grant has no `INHERIT` or `SET` unless `createrole_self_grant` is set). This is operator-level access, and it is accepted: the owner already owns every protected object. It runs in that direction only: neither runtime role becomes a member of the owner, and the template and evidence script refuse any runtime role membership.
   - Set each password separately in psql with `\password recruitmentos_data` and `\password recruitmentos_identity`. Never put a password in the template, SQL history, shell history, logs, source control, or a shared document. Neon documents password reset for existing roles, but verify that the chosen secure method works for a SQL-created role before relying on it.
   - Rerun the template after every migration. A rerun revokes and regrants the matrix, so it removes any extra privilege, grant option included, on the protected schemas and their objects, the `public` schema and the application database. It does not touch parameter, type, language, foreign-data wrapper or server grants, role settings or other databases; the evidence script reports those, and the operator removes them. New owner tables, sequences and functions are unusable by both runtime roles and PUBLIC until the template is updated for them.
   - Run the read-only evidence script with each runtime connection, from a controlled operator environment: `DATABASE_URL=<data role connection> IDENTITY_DATABASE_URL=<identity role connection> npx tsx scripts/db-role-evidence.ts`. It reads only those two variables (never `.env.local`), uses `sslmode=verify-full` for non-loopback hosts, runs every query in a rolled-back `READ ONLY` transaction, and prints one JSON document with role attributes, memberships, effective grants, default privileges, what PUBLIC holds, CONNECT on every database in the cluster, the accepted platform databases (each inspected through one more connection with the data role's credentials, changed only in the database name), grant options, other ACL entries, per-role settings, the safety and boundary check results, the database name and whether the connection markers match. It never prints passwords, URLs, hosts, ports, setting values or the marker value. It compares each role with the matrix it parses from the template and lists every difference under `drift`. It checks exactly these classes:
     - role attributes, and membership in any role;
     - CONNECT, CREATE and TEMPORARY on the application database, extra or missing, and CONNECT on any other database that accepts connections, except a platform-owned database that meets the four conditions above, which is listed under `accepted_platform_databases` instead;
     - USAGE and CREATE on every schema outside `pg_catalog`, `information_schema` and `pg_*`, extra or missing;
     - effective table, view, sequence and column privileges (TRUNCATE included) and EXECUTE on functions in those schemas, extra or missing. Anything outside the matrix that a runtime role can use, such as an extension function, counts;
     - any table, column, sequence, function, schema or database privilege held WITH GRANT OPTION, directly or through a role it belongs to, in any schema or database;
     - explicit grants to the role, or a role it belongs to, on types, languages, foreign-data wrappers and foreign servers, and PUBLIC grants on foreign-data wrappers and foreign servers. PUBLIC USAGE on types and trusted languages is the PostgreSQL default and is not reported;
     - any parameter privilege (`SET` or `ALTER SYSTEM`, PostgreSQL 15 and later) granted to the role, a role it belongs to, or PUBLIC, for any parameter, `session_replication_role` included;
     - settings stored for the role in `pg_db_role_setting` (`ALTER ROLE … SET`), in any database;
     - explicit default privileges for the role or PUBLIC; PUBLIC CONNECT or TEMPORARY on the application database, PUBLIC access to the `public` schema, and PUBLIC EXECUTE on the owner's future functions.

     It does not check large objects, the default PUBLIC privileges on `pg_catalog` and `information_schema` objects, the content of row-level security policies, database-wide settings (`ALTER DATABASE … SET`) or server configuration such as `pg_hba.conf`; review those separately. Exit code 0 means every check passed and nothing drifted, 1 a failed check, any drift in the classes above, or a connection error, 2 refused configuration.

   - Independently inspect the effective role attributes, inheritance and ability to `SET ROLE`, including indirect membership in `neon_superuser`, `pg_read_all_data`, `pg_write_all_data`, and server-file/program roles. Check that the login cannot create roles or databases, replicate, bypass RLS, own or assume ownership of protected schemas, tables, sequences or functions, or create objects in those schemas. Review new tables and grants on every future migration.

First inspect integration-managed settings and their update behavior; do not blindly overwrite them. Ensure no application runtime setting contains an owner connection. Verify variable names and scopes without printing values. Do not assume that a Vercel integration's initial connection already uses a restricted role.

It never prints URLs, hosts, ports, usernames, passwords, the marker, the key or its id, payloads, signatures, row data or driver error text. Diagnostics never contain driver messages or any of the values above. An error outside a check still prints only the generic line.

## 4. Connection pooler requirements

The deployed runtime uses the pooled endpoint. These requirements come from the WP-02d local verification; Neon's own pooler settings are not known to agents.

- **Pooling mode.** Transaction pooling (Neon's mode) and session pooling are supported. Statement pooling is not: every tenant-context, lock and lease guarantee needs a multi-statement transaction on one backend.
- **Authentication.** The pooler must log in to PostgreSQL as each client's own role, with no forced or shared server user, so the data, identity and owner connections arrive as `recruitmentos_data`, `recruitmentos_identity` and the owner. The runtime role and pair checks compare `current_user` and `session_user`.
- **Pool size.** An open transaction holds its server connection until `COMMIT` or `ROLLBACK`, so the pool for each role (PgBouncer `default_pool_size`, per database and user) must cover that role's concurrent transactions; otherwise the extra transactions queue in the pooler. The live harness peaks at six concurrent data-role transactions, two identity-role transactions and one owner connection. Each application instance opens up to five connections per runtime role (`pg` pools with `max: 5`).
- **Direct owner connection.** `scripts/migrate.ts` (a session advisory lock) and the role template run over the direct, non-pooled owner connection (see [§1](#1-identify-and-prepare-both-environments) and [§3](#3-runtime-access-and-verification)).
- **No session state.** No `src/` code uses a session-level `SET`, session advisory locks, named prepared statements, `LISTEN` or temporary tables. The only settings are the transaction-local deadlines, and every guarantee is transaction-scoped:
  - the 10 s `statement_timeout` and 20 s `transaction_timeout` are set by `set_config(…, true)` as the first statement of every application transaction (`withDeadlines` in `src/db/deadlines.ts`) and reset at `COMMIT` or `ROLLBACK`, so no backend carries them into another transaction;
  - the tenant context is read (pid, xid, marker, clock) and installed inside the transaction and keyed by `pg_backend_pid()` and `pg_current_xact_id()`;
  - the bootstrap setup lock is `pg_advisory_xact_lock`;
  - storage-ledger reservations and Blob read leases take `SELECT … FOR UPDATE` row locks.

  A transaction pooler keeps one backend for the whole transaction, so these hold whichever backend the next transaction gets.

- **Startup `statement_timeout`.** The harness sends `statement_timeout` (20 s) as a startup parameter. Local PgBouncer 1.26.1 refused such a connection with SQLSTATE `08P01` (unsupported startup parameter) until `statement_timeout` was listed in `ignore_startup_parameters`. It then dropped the parameter, and `SHOW statement_timeout` through the pooler returned `0`, the server default. Through such a pooler the 20 s bound is therefore not enforced. The harness connected through Neon's pooler, so Neon accepts or ignores the parameter; which one is unknown. Check `SHOW statement_timeout` through the pooled connection before relying on the bound. The application does not rely on startup parameters: its deadlines are set inside each transaction, which a transaction pooler keeps on one backend. The harness's own 20 s startup parameter remains as described here.
- **Deadlines through the pooler.** The owner's next Preview run of `npm run test:live-roles` includes `transaction-deadlines` through the pooler. It has passed only on a throwaway local PostgreSQL 18 cluster without a pooler.

**Why six checks failed on the Preview pooler (WP-02d).** The harness captured each client's backend pid once, at start-up, in an autocommit `SELECT pg_backend_pid()`. Behind a transaction pooler an autocommit statement can run on any server backend, and so can each later transaction, so those pids did not identify the backends that ran the checks' transactions. On an idle pool the start-up reads also tended to land on the same backend. Every check that used them failed, and no other check did:

| Check                     | Root cause                                                                                                       | Class                                        |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `bootstrap-claim-race`    | Start-up pids used for distinctness of the two identity backends and for the `pg_locks` wait on the rival insert | Harness assumption under transaction pooling |
| `replay-other-connection` | Start-up pids used for distinctness of the two data backends                                                     | Harness assumption under transaction pooling |
| `last-owner-race`         | Start-up pids used for distinctness and for the `pg_locks` wait on the demotion                                  | Harness assumption under transaction pooling |
| `store-budget-race`       | Start-up pids of the six workers used for distinctness and for the `pg_locks` overlap                            | Harness assumption under transaction pooling |
| `read-lease-team-cap`     | Start-up pids of the six workers used for distinctness and for the `pg_locks` overlap                            | Harness assumption under transaction pooling |
| `read-lease-store-cap`    | Start-up pids of the six workers used for distinctness and for the `pg_locks` overlap                            | Harness assumption under transaction pooling |

No application defect was found. Locally, every outcome, positive control and end state of those six checks held through the pooler: the right inserts were refused with `23514`, exactly the store room was reserved and the rest refused with `RQ001`, the lease caps held and the replay was rejected with `42501`. Only the backend-identity and lock-overlap conditions failed. The harness now reads every pid inside the transaction concerned (see [§3](#3-runtime-access-and-verification), item 4), and `pooled-connection-reuse` follows the same rule.

**Local verification.** PgBouncer 1.26.1 (the official Windows build) ran from the worktree `.data` folder, on a loopback port, in front of a throwaway PostgreSQL 18 cluster on another loopback port. Settings: `pool_mode = transaction`, `auth_type = scram-sha-256` with each role's own credentials and no forced user, `default_pool_size = 10`, `min_pool_size = 0`, `reserve_pool_size = 0`, `max_client_conn = 100`, `server_round_robin = 0` and `ignore_startup_parameters = statement_timeout`.

- The unmodified harness through the pooler failed exactly the six checks above, and it passed 27/27 directly.
- The fixed harness passed 27/27 through the pooler and directly, in the open and closed bootstrap variants, with every fixture removed.
- With `server_round_robin = 1`, the pooler handed the later transaction of `pooled-connection-reuse` to another backend. That check then failed in phase `backend-identity`, and every other check passed.

If the pooled Preview rerun fails only `pooled-connection-reuse` in phase `backend-identity`, Neon's pooler ran the later transaction on another backend, so the check could not observe reuse. Report it rather than relaxing the check.
