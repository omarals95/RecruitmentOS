## Proposed identity separation

Both proposed roles below are separate SQL-created login roles **within the same Preview database** and receive distinct Preview-only credentials. Neither may inherit or assume the other, the migration owner, `neon_superuser`, `pg_read_all_data`, `pg_write_all_data` or other elevated roles. Each must be nonowner and have no superuser, `CREATEDB`, `CREATEROLE`, replication or `BYPASSRLS` privilege. The owner credential is used only by an operator through the direct, non-pooler Preview endpoint and must never be put in the deployed runtime environment.

| Principal               | Intended access boundary                                                                                                                                                               | Still unresolved before grants are reviewable                                                                                                                                                       |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Preview migration owner | Apply the explicitly reviewed migrations and manage the two Preview roles; never serve application requests.                                                                           | Confirm actual owner privileges, target branch/database, applicable migrations and impact on pre-existing roles.                                                                                    |
| Preview data login      | Access only the reviewed application data operations under independently verified tenant and action context. It must not access or mutate protected `auth` identity tables or secrets. | Existing `withTeam()` policies trust caller-set context; replace or formally secure all data RLS paths. `createToken()`/`revokeToken()` and activity-name search still cross the proposed boundary. |
| Preview identity login  | Support the reviewed Better Auth, membership, session, verification and API-token operations without direct recruitment-record access.                                                 | Enumerate needed auth table, column and function permissions; design the narrow, authorized audit mechanism that preserves the existing single transaction and prevents forged events.              |

After migration `0005_database_connection_marker.sql`, each runtime role needs read-only `USAGE` on `db_boundary` and `SELECT` on its `connection_marker`; neither may write, own, alter, grant on, or inherit a role with those capabilities. Verify matching endpoint and marker in the two connections and confirm Preview/Production isolation independently: a clone can copy the marker. Check effective `PUBLIC`, inherited and column privileges, functions, views, foreign tables, default ACLs and ownership—not just explicit grants. The current staged startup guard forbids callable non-system security-definer functions and accessible views/foreign tables, so an audit or tenant-context helper needs an independently reviewed narrow exception and corresponding tests before it can be used.

Do not use blanket `GRANT ... ON ALL TABLES` as a substitute for the template's object-by-object matrix. The data role's existing code touches application records, candidate state, activity, uploads, storage usage, idempotency and notification state. The identity side uses Better Auth user, account, session, verification, rate-limit, organization, member and invitation objects, plus API-token and token-rate-limit objects. These inventories are **not** authority to grant access: final table/column/function privileges depend on the completed integration and must be tested against the actual roles. Limit sensitive identity reads, including session tokens, password hashes, OAuth credentials and token hashes, to the trusted identity path.

## Exact future action sequence

1. **Read-only preflight:** using the identified Preview owner connection under operator control, inspect database identity, data presence, migration ledger, role attributes/memberships, object ownership and effective explicit, inherited, column and `PUBLIC`/default grants. Never copy or print credentials. Verify that no existing unrelated role or grant would be changed. This step does not establish that the application is secure.
2. **Review migration impact:** inspect the exact ordered `drizzle/` files against the actual ledger. The current migration script takes a session advisory lock, so the owner connection must use the direct, non-pooler endpoint. Migration `0004_protect_initial_admin_claim.sql` removes marker-write privileges from all nonowner grantees using `CASCADE`; if it would affect unrelated maintenance/operator roles, stop and resolve that scope before applying anything. Migration `0005` creates the database marker. The separately screened trigger change is not part of an approved operation.
3. **Request the required action-time approval for a concrete reviewed change:** creating two Preview login roles and persistent credentials; applying the specifically reviewed Preview migrations and minimum grants; connecting the two Preview-scoped runtime values; and running synthetic multi-connection tests that write Preview test records. The exact role names, SQL, applicable migration list, changes to integration-managed environment variables, and recovery plan must be ready for review first. No Production or unrelated role/database changes are included.
4. **Execute only that approved Preview change:** create the limited roles with SQL after checking Neon-specific role behavior; create credentials using a secure mechanism that keeps values out of chat, terminal history and logs; apply the reviewed migrations and exact grants. Never place owner credentials in Vercel runtime variables. Verify database identity, migration ledger and effective permissions after each mutation; inspect uncertain outcomes before any retry.
5. **Verify before enabling anything:** using independent Preview runtime connections and synthetic records, verify actual role identities and non-assumability; deny auth writes and sensitive reads from the data role; deny candidate/CV reads and direct activity writes from the identity role; exercise first-admin setup, verification, sign-in, invitations and last-owner safeguards; and verify token creation/revocation and audit insertion commit or roll back together. Test cross-team and private-row denial, forged context, token scope/revocation, expiry, replay, concurrent transactions and connection pooling. Reconcile temporary test records and check that no secrets or fictional assertions were logged.
6. **Hold the deployment gate:** independently review live evidence, complete the implementation and provider-specific security checks, and obtain any required deployment authorization before changing the hosted gate. A passing migration, local unit test, or build alone is not evidence of a secure working deployment. Production is a separate future change with separately verified targets, roles, credentials and approval.
